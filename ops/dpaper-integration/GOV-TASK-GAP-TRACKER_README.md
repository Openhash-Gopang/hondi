# GOV-TASK-GAP-TRACKER 사용법

## ★★★ 근본 원칙(주피터 명시, 2026-08-22) — 왜 원형은 공용이고 인스턴스는 지역별로 분리하는가

전국의 시/군/구·읍면동사무소·광역시·도청은 전국 공용 원형 템플릿(법적
근거·GOV_TASK 파이프라인·콘텐츠)을 전부 공유한다. 그런데도 각 지역마다
별도 인스턴스(city-division-master-data.json 레코드, city-dept-
master-data.json 레코드 등)를 따로 작성하는 이유는 딱 하나뿐이다 —
**혼디 사용자 데이터를 6하원칙(누가·언제·어디서·무엇을·어떻게·왜)에
따라 기록하기 위해서다.** 즉 어느 지역에서 어떤 민원이 얼마나
발생하는지, 어떤 민원의 처리 시간이 얼마나 소요되는지에 대한 통계
데이터를 수집하는 게 목적이다.

이 원칙이 실무에 갖는 함의:
- 원형(콘텐츠) 자체는 100% 재사용 가능 — 법적 근거·절차 안내를 지역마다
  다시 쓸 필요가 없다.
- 하지만 "이 민원이 정확히 어느 시/군/구·어느 과에서 발생·접수·
  처리됐는가"라는 소재지 식별 정보는 인스턴스별로 고유해야 통계가
  의미를 갖는다 — 그래서 시코드+국코드+과코드(또는 도코드+기관코드
  등) 조합마다 별도 레코드가 필요하다.
- 실사(진짜 기관명·연락처)가 없어도 최소한 "이 지역의 이 업무"라는
  식별 단위 자체는 항상 존재해야 하며, GOV_TASK_SUBMIT_REQUEST의
  `agency` 필드가 이 식별자 역할을 한다.
- 그래서 부산 16개 구/군처럼 실사가 부족한 지역도 레코드를 아예
  비우기보다 "확인했으나 불확실"을 명시적으로 남기는 쪽을 택했다
  (city-division-master-data.json 2026-08-22 확장분 참고) — 통계
  귀속 단위가 조용히 누락되는 것보다, 불확실성이 기록으로 남는 게
  낫다.

## ★★★ 클론·승격·전파 메커니즘(주피터 명시, 2026-08-22) — 지역 개선을 원형에 되먹임하는 구조

"인스턴스는 원형을 복제한 뒤, 개별 지역에서 갱신(특히 부서 SP 갱신)을
지향합니다. 어느 한 지역의 갱신과 기능 향상을 원형 템플릿에 반영하고,
재차 여타 지역 인스턴스로 전파될 수 있는 메커니즘"이 필요하다는 지시에
따라, 04-city 과(division) 단위에 3단계 구조를 배선했다
(`04-city/templates/divisions/instance-registry.json`).

**절대다수 지역(현재 부산 16개 구/군 포함)은 이 구조와 무관하다** —
원형 템플릿을 그대로 공유하고 city-division-master-data.json의
자리표시자 값만 채워 쓴다. 이 구조는 어떤 지역이 단순 자리표시자를
넘어 **SP 본문 자체를 로컬로 개선**해야 할 때만 쓰인다.

1. **클론**: 원형 템플릿(`04-city/templates/divisions/*.md`)을
   `04-city/divisions/instances/{시코드}/`에 복제 → `upstream_template`·
   `upstream_version` 헤더 기록 → 로컬 개선 반영 →
   `instance-registry.json`에 등록.
2. **렌더링 우선순위**: `gov-router.js`의 `_fetchCityDivisionText`는
   ①레지스트리에 등록된 인스턴스 클론이 있으면 그걸 그대로 사용(자리
   표시자 렌더링 없음) → ②없으면 기존처럼 원형 템플릿 + 마스터데이터
   자리표시자로 렌더링. 등록 안 된 지역은 동작 변화가 전혀 없다.
3. **승격(지역→원형)**: 로컬 개선이 다른 지역에도 일반적으로 적용
   가능하다고 판단되면, 원형 템플릿 파일 자체에 그 개선을 반영하고
   버전을 올린다(v1.0→v1.1). 승격 완료 후엔 그 지역의 instance 파일을
   지우고 레지스트리 항목도 제거해 다시 원형 공유 상태로 되돌린다.
4. **전파(원형→다른 인스턴스)**: 원형이 갱신되면, 분기하지 않은
   절대다수 지역은 같은 파일을 공유하므로 자동으로 최신 원형을 받는다
   — 별도 작업 불필요. 이미 분기해 레지스트리에 등록된 지역은
   `upstream_version`이 낡은 채로 남으므로, 레지스트리를 주기적으로
   점검해 원형 최신 버전보다 낮은 항목을 찾아 재검토(reconcile)해야
   한다 — 자동 동기화는 하지 않는다(로컬 개선과 원형의 새 변경사항이
   충돌할 수 있어 사람/AI의 판단이 필요).

**2026-08-22 기준 등록된 인스턴스: 0건** — 인프라만 먼저 배선했고,
실제 로컬 개선 사례가 아직 없어 레지스트리는 빈 배열이다. 격리
테스트로 우선순위 로직(클론 우선 → 마스터데이터 → 기본라벨) 3가지
시나리오를 검증했다.

## 복지 계열(WELFARE) 작업 시 반드시 먼저 확인할 것

**2026-08-20 시점 복지위생국 6개과 전부 완료**(위생관리·장애인복지·노인복지·
기초생활보장·여성가족·주민복지, 제주시/서귀포시) — 이 섹션은 앞으로
02-do-dept나 다른 시(市)에 같은 성격의 복지 계열이 나타날 때를 위해 남긴다.

개인 복지급여 신청(장애인등록·기초연금·기초생활보장·한부모가족지원 등)은
전통적으로 **읍·면·동(주민센터)이 1차 접수, 시청 복지 담당국이 최종 심사**
하는 2단계 구조다(`SP-EMD-TEMPLATE_v1.3.md` §3 "주민복지팀" 참조). 05-emd는
이 감사 스캔 대상이 아니라서(정적 파일 없이 동적 렌더링), 시청 SP의
§INPUT_SCHEMA를 그대로 믿고 "시청이 접수까지 다 한다"고 등록하면 사실과
다르다. 대신 복지로(bokjiro.go.kr) 온라인 접수 선례를 따라 "시청 명의
온라인 접수 통로 — 심사는 원래도 시청" 프레이밍으로 SP §1-2에 disclaimer를
넣는 패턴을 확립했다(`SP-CITYDIV-*-WELFARE-*_v1.1.md` 전체 참조).

**예외**: 긴급복지지원(긴급복지지원법 제7조)은 법 자체가 "관할 시장·군수·
구청장에게 구술 또는 서면으로 직접 요청" 가능하다고 명시해 읍면동 경유가
필수가 아니다 — 이런 예외가 있으니 **매번 개별 법령을 웹검색으로 재확인
할 것, "복지=무조건 읍면동 경유"로 일반화하지 말 것.**

## 원본 감사의 구버전 중복 행 주의

`gov-tree-hondi-readiness-audit.xlsx`는 저장소를 한 시점에 스냅샷 스캔한
것이라, 같은 기관·부서의 v1.0/v1.1/v1.2가 각각 별도 행으로 잡혀 있는
경우가 많다(01-do JEJU-DO-SP가 v1.0/v1.4/v1.5 세 행으로 잡힌 것과 동일
패턴, 2026-08-20 서귀포 안전도시건설국 6개과에서도 재확인). **미착수로
보이는 행을 작업하기 전에 항상 `find prompts/gov-tree -iname "*{기관명}*"`
로 실제 디스크의 최신 버전을 먼저 확인할 것** — 이미 상위 버전으로
완료됐는데 구버전 행만 미착수로 남아있는 경우가 있다.
