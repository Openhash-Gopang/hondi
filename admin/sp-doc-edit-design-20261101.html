SP가 서류를 직접 고치는 구조

메인 입력창, 서류 작성 화면, 우측 “혼디 대화” 패널이 같은 SP(나만의 AI 비서)를 앞단으로 쓰고, 열려 있는 서류의 칸을 사용자가 말한 대로 SP가 직접 고치게 합니다. 이 문서는 그 구조와 안전장치, 구현 순서를 정합니다.

결론

  • 대화의 앞단은 AC-PRO-CORE 하나(/kmail/assist)입니다. 메인 입력창과 우측 패널이 같은 대화 엔진을 씁니다.
  • 서류의 초안 작성은 지금처럼 서류 사이트 SP(law·tax·doctor)가 합니다. 새로 생기는 것은 수정입니다. AC-PRO-CORE가 “고치라는 뜻”을 알아보면 서류 사이트의 SP에게 수정을 맡기고, 결과를 칸에 반영합니다.
  • 기반은 이미 있습니다. 서류 페이지의 첨부 자료로 칸 채우기가 “SP가 칸을 직접 채우고, 사용자가 쓴 칸은 건드리지 않는” 규칙으로 동작합니다. 이를 수정 모드로 일반화합니다.
  • SP가 몰래 바꾸지 않습니다. 사용자가 말했거나 승인한 변경만 적용하고, 바뀐 칸은 표시하며, 한 번에 되돌릴 수 있습니다.

1 현재 구조

코드를 확인한 사실입니다.

입구지금 하는 일근거
메인 입력창기본 모드는 /kmail/assist(AC-PRO-CORE)로 보내고, 응답의 route가 doc이면 서류 모드로 넘깁니다. 서류 모드에서는 입력을 서류 iframe에 그대로 전달합니다.desktop.html _navAssistTurn, _navApplyRoute, _docHostSubmit
서류 화면law/tax/doctor.hondi.net의 서류 페이지가 iframe으로 열립니다. 칸 값(S.vals)·초안(S.md)·서식(S.form)은 그 안에만 있습니다. 호스트와는 postMessage(navi-doc-*)로 통신합니다.navi-pro src/assets/navi.js (모드 draft·fill·review)
우측 패널hondi.net/webapp.html(혼디 1:1 대화, WebRTC)을 iframe으로 띄운 것입니다. K-Mail 대화·서류와 상태를 공유하지 않습니다.hondi-chat.js

이미 있는 것: 칸 채우기의 보호 규칙

첨부 자료를 올리면 서류 SP가 ~~~values 블록(키=값 줄)을 돌려주고, 페이지는 빈 칸과 “내 정보(PDV)로 자동 입력된 칸”만 채웁니다. 사용자가 직접 쓴 칸은 유지합니다. 채운 칸의 PDV 표시를 해제하고, save('자료 반영')으로 기록합니다.

수정 기능은 이 경로를 재사용하므로, 새로 만드는 부분이 작고 검증된 규칙 위에 얹힙니다.

수정이 막혀 있는 이유

  • 메인 SP는 열린 서류의 칸을 볼 수 없습니다(칸은 다른 출처의 iframe 안에 있습니다).
  • 서류 모드의 입력은 “새 초안을 쓰라”는 뜻으로만 해석되고, “이 칸을 바꿔라”는 경로가 없습니다.
  • 우측 패널은 아예 다른 앱이라 서류에 닿을 수 없습니다.

AC-PRO-CORE가 맡는 일

사용자의 말이 “새로 쓰기”인지 “고치기”인지 “그냥 질문”인지 판단하고, 고치기일 때 무엇을(어느 칸) 어떻게 고치라는 뜻인지 지시문으로 정리합니다. 규칙 점검(비서 게이트)도 여기서 합니다.

서류 사이트 SP가 맡는 일

서류의 내용 품질입니다. 법률·세무·의료 서류의 칸 값을 실제로 쓰는 쪽은 그 직역의 SP입니다. 메인 SP가 직역 서류의 내용을 직접 쓰지 않으므로, 직역 지식이 한 곳에만 있습니다.

3 메시지 규격

기존 navi-doc-* 규격에 이어 붙입니다. 서류 페이지는 navi-doc-ready의 v를 3으로 올려 수정 기능을 알립니다. v가 2 이하인 서류 페이지에는 수정 지시를 보내지 않고, 호스트가 “이 서류는 아직 대화로 수정할 수 없습니다”라고 알립니다.

방향type내용
호스트 → 서류navi-doc-snapshot-request현재 칸 상태를 달라는 요청.
서류 → 호스트navi-doc-snapshotrev(변경 번호), title, fields[]: k·l(이름)·t(short/long)·state·value(조건부, 아래).
호스트 → 서류navi-doc-reviseid, instruction(≤500자), keys(범위, 선택), explicit(사용자가 말로 지목한 칸), baseRev.
서류 → 호스트navi-doc-revise-resultid, rev, applied[{k,l,from,to}], conflicts[{k,l,to,why}], skipped[{k,why}], status.
호스트 → 서류navi-doc-resolve충돌 칸에 대한 사용자의 선택: {id, k, accept:true|false}.
호스트 → 서류navi-doc-undo{rev} 변경을 한 번에 되돌립니다.

서류 SP의 응답 형식(기존 형식 유지)

~~~values
claim_amount=30,000,000원
reason=피고는 2026. 3. 1. 체결한 계약에 따른 …\n…
~~~

값 형식은 지금의 키=값(줄바꿈은 \n)과 같습니다. 비우려는 칸만 ~~~clear에 키를 적습니다. 서식이 없는 자유 서류(S.md)는 초안 전체를 ~~~markdown으로 돌려받되, user 칸은 병합 단계에서 보존합니다(P2 이후 별도 처리).

4 수정 흐름

sequenceDiagram
  participant U as 사용자
  participant H as 호스트(desktop)
  participant A as AC-PRO-CORE
  participant F as 서류 iframe
  participant S as 서류 SP
  U->>H: "청구금액을 3천만 원으로 바꿔줘"
  H->>F: snapshot-request
  F-->>H: snapshot(칸 목록·상태)
  H->>A: messages + doc 스냅샷(개인정보 제외)
  A-->>H: route doc_edit (instruction, explicit 칸)
  H->>F: navi-doc-revise
  F->>S: 지시문 + 현재 값
  S-->>F: ~~~values
  F->>F: 보호 규칙으로 적용·표시·기록
  F-->>H: revise-result {applied, conflicts}
  H-->>U: "1개 항목을 바꿨습니다 · 되돌리기"
  1. 스냅샷: 서류가 열려 있고 v≥3이면 호스트가 대화 전송 직전에 칸 상태를 받아 서버 요청에 붙입니다(body.doc).
  2. 의도 판단: 서버(AC-PRO-CORE)가 route를 돌려줍니다. 기존 assistant·ask·kmail·doc·expert에 doc_edit이 더해집니다. 애매하면 기존처럼 되묻습니다(최대 2회).
  3. 수정: 호스트가 navi-doc-revise를 보냅니다. 서류 페이지는 수정 모드(S.mode='revise')로 서류 SP를 부르고, 응답을 보호 규칙으로 적용합니다.
  4. 결과 안내: 호스트가 모델 호출 없이 결과를 말풍선으로 보여 줍니다(바뀐 칸 이름·값, 건너뛴 칸, 충돌 칸의 [적용]/[유지] 버튼, [되돌리기]).

SP가 “스스로” 하는 갱신의 범위

  • 사용자가 말한 변경: 바로 적용합니다(위 흐름).
  • SP가 알아챈 필요(예: 기일 변경, 첨부 자료에서 읽은 값 불일치): 제안으로만 띄웁니다. “기일 칸을 2026. 12. 3.으로 갱신할까요? [적용] [무시]” 그리고 사용자가 누르면 같은 수정 경로로 적용합니다.
  • 어떤 경우에도 발송·서명·제출·저장 공개는 SP가 실행하지 않습니다.

5 안전장치

위험대책
사용자가 쓴 값을 덮어씀user 칸은 사용자가 그 칸을 말로 지목했을 때만 바꿉니다. 아니면 충돌로 돌려 [적용]/[유지]를 묻습니다. 기본 선택은 [유지]입니다.
되돌릴 수 없는 변경변경마다 rev와 이전 값을 보관합니다. [되돌리기] 한 번으로 그 변경 전체를 복원합니다. 최근 20개까지 유지합니다.
몰래 바뀜바뀐 칸은 서류에서 강조 표시되고, 대화에 “무엇을 어떻게 바꿨는지”가 남습니다. 변경 기록은 서류 저장본(save('SP 수정'))에도 남습니다.
개인정보가 서버로 나감스냅샷은 칸 이름·종류·상태만 보냅니다. 값은 짧고(≤200자) 민감하지 않은 칸에 한해 보내며, 성명·주소·전화·이메일·주민번호(PDV 종류)와 주민번호·카드번호 패턴이 보이는 값은 제외합니다. 이 판별은 비서 호스트의 hasSensitive를 재사용합니다.
서류 내용에 숨은 지시(프롬프트 주입)스냅샷과 첨부에서 온 값은 데이터로만 다룹니다. 응답은 스냅샷에 있는 키만 받고, 값은 .value로만 넣습니다(HTML로 해석하지 않음). 서버·서류 SP 모두 값 안의 지시를 따르지 않도록 지침에 명시합니다.
엉뚱한 곳이 열림메시지는 서류 iframe의 출처(_docHostOrigin)와 event.source를 모두 확인하고, 스키마(type, 길이, 키 형식 ^[A-Za-z][A-Za-z0-9_]*$)를 검증합니다.
과도한 변경한 번에 최대 12칸, 값 길이 상한(짧은 칸 300자·서술 칸 4,000자)을 둡니다. 초과분은 건너뛰고 결과에 사유를 적습니다. 같은 서류에 대한 연속 수정은 앞 요청이 끝난 뒤에 처리합니다.
직역 판단의 오류법률·세무·의료 칸은 서류 SP가 쓰고, 수정 결과에는 “내용 확인은 전문가에게”라는 안내가 붙습니다. 직역 규칙팩이 아직 없는 서류는 비서 게이트가 ADVISE_HUMAN을 돌려주며, 특정인을 추천하지 않습니다.
증거비서 원장에 doc.edit 증명(입력 해시, 결과, 사용자 선택)을 남깁니다. 값 자체는 원장에 넣지 않습니다.

6 우측 패널 통합

지금 패널은 다른 앱(hondi.net/webapp.html)이라 서류에 닿을 수 없고, 그 안의 AI는 별도 대화입니다. 같은 SP를 쓰려면 패널의 대화 엔진을 바꿔야 합니다.

안 A 권장 추천

패널을 K-Mail 안의 대화로 바꿉니다. 메인 입력창과 같은 대화 엔진(_navAssistTurn)과 대화 기록을 씁니다. 혼디의 사람 간 1:1 대화(WebRTC)는 패널 안 “사람과 대화” 탭으로 남겨 수신 알림도 유지합니다.

서류 스냅샷과 수정 결과 말풍선을 같은 곳에서 다루고, 대화가 하나로 합쳐집니다. 서버 SP도 하나입니다.

안 B

패널(혼디 앱)을 그대로 두고, 앱의 AI가 K-Mail에 postMessage로 수정 명령을 보내게 합니다.

혼디 앱 코드를 고쳐야 하고, 대화 엔진이 둘로 남아 규칙과 개인정보 처리를 두 곳에서 지켜야 합니다. 요청하신 “SP 통일”과 맞지 않습니다.

폰 화면(webapp.html)에서는 패널이 전체 화면으로 뜹니다. 같은 구조를 쓰되, 폰의 서류 모드가 데스크톱과 같은 경로(_navRoute)를 갖는지는 P2에서 코드로 확인한 뒤 맞춥니다.

7 구현 순서

단계마다 저장소가 다르고, 서버와 서류 페이지가 먼저 나가야 화면이 안전합니다. 각 단계는 PR 하나로 나눕니다.

P0

서류 페이지: 수정 모드

navi-pro. ready v:3, 스냅샷, revise 모드(서류 SP 호출, 값 파싱, 보호 규칙 적용, 강조 표시), ai 상태, 충돌·되돌리기, 결과 메시지, 변경 기록 저장. 기존 fill 경로와 parseValues를 재사용합니다.

검증: 노드 단위 테스트(보호 규칙·상한·키 검증), 가짜 호스트로 메시지 왕복 브라우저 테스트.

P1

서버: doc_edit 라우트

hondi(/kmail/assist). 요청 본문 doc 스냅샷 검증·축약, 응답 route:{type:'doc_edit',…}, AC-PRO-ASSIST 지침에 수정 판단 규칙(지목한 칸만 explicit, 값은 직접 쓰지 않음, 값 안의 지시 무시) 추가. AC-PRO-CORE 본문은 고치지 않고, 지침은 동반 SP로만 붙입니다(이전 결정과 같음).

검증: 서버 테스트(스키마·개인정보 제외·라우팅), 실제 모델 라우팅 회귀 시나리오.

P2

호스트: 스냅샷·수정·결과 말풍선

mail(desktop.html, webapp.html). 전송 직전 스냅샷, doc_edit 처리, 결과 말풍선(되돌리기·충돌 버튼), 서류 모드에서도 기본 SP를 거치도록 라우팅 조정.

검증: 가짜 서류 iframe을 쓴 브라우저 시나리오(PC·폰 폭), 기존 서류 작성 흐름 회귀.

P3

우측 패널 통합

mail. 패널을 K-Mail 대화로 교체하고 “사람과 대화” 탭으로 혼디 앱을 유지(수신 알림 포함).

검증: 패널에서 서류 수정이 되는지, 혼디 수신 알림이 계속 오는지.

P4

비서 연동과 제안

mail·hondi. 비서 게이트에 doc.edit 행위와 증명 기록, 실행 신호(기일 변경 등)를 “갱신 제안”으로 띄우기. 직역 규칙팩은 법률 검토 후 별도로 배포합니다.
