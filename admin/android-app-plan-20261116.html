나비웹 안드로이드 앱 전환 계획

현재의 웹앱(naviweb.kr)을 그대로 안드로이드 앱으로 옮기는 계획서 · 2026-11-16 · 초안

1. 왜 앱이 필요한가

웹앱만으로는 아래 항목을 나비웹이 사용자 동의를 받아 직접 설정할 수 없습니다. 브라우저가 사이트에 허용하지 않기 때문입니다.

필요한 것웹앱(PWA)전용 앱
화면이 꺼진 상태에서 대화 요청을 소리로 알림알림 소리·중요도는 폰의 사이트 알림 설정이 결정. 앱이 바꿀 수 없음알림 채널을 "높음/소리"로 직접 생성
배터리 "제한 없음"불가. 사용자가 폰 설정에서 직접 변경시스템 팝업으로 사용자에게 허용 요청(한 번 누르면 완료)
전화처럼 전체 화면 수신 화면불가전체 화면 알림(Full-screen intent) — 스토어 정책 확인 필요
알림이 늦거나 누락되는 문제크롬의 절전 제한에 영향우선순위 높은 FCM 데이터 메시지와 배터리 예외로 개선

2. 방식 비교와 권장안

방식내용장점위험
A. TWA(신뢰 웹 활동)크롬 엔진으로 naviweb.kr을 앱처럼 표시웹 코드를 그대로 사용. 크롬의 패스키(지문)를 그대로 사용알림 채널·배터리 팝업 등 네이티브 기능은 별도 코드가 필요
B. Capacitor/Cordova(WebView)앱 안의 WebView에 웹앱을 표시하고 네이티브 플러그인 연결네이티브 기능 추가가 쉬움지갑이 쓰는 WebAuthn(PRF) 지문 기능이 WebView에서 동작하지 않을 수 있음 (실기 검증 전)
C. 완전 네이티브화면까지 새로 개발최고 품질비용·기간이 가장 큼. "웹앱을 그대로 전환"이라는 목표와 맞지 않음
권장: A + 네이티브 보강(하이브리드). 화면은 TWA로 현재 웹앱을 그대로 쓰고, 앱 안에 작은 네이티브 부분(FCM 수신, 알림 채널, 배터리 예외 요청)만 추가합니다. 지갑의 지문 인증이 크롬 위에서 그대로 동작해 가장 안전합니다. 1단계 검증에서 WebView 방식도 함께 시험해 결정을 확정합니다.

3. 앱 구조

  • 앱 이름·패키지(안): 나비웹 / kr.naviweb.app — 패키지 이름은 한 번 정하면 바꿀 수 없음
  • 화면: https://naviweb.kr/webapp.html?pwa=1을 TWA로 표시. 도메인 인증(Digital Asset Links, /.well-known/assetlinks.json)으로 주소창 없는 전체 화면 구현
  • 네이티브 부분(Kotlin, 소규모)
    1. FCM 수신 서비스: 대화 요청·승인 요청 등을 높은 우선순위로 받아 알림 표시
    2. 알림 채널: calls(높음·소리·진동·잠금 화면 표시), messages(기본), system(낮음)
    3. 첫 실행 안내: 알림 권한(안드로이드 13+), 배터리 최적화 예외 요청을 사용자 동의 화면과 함께 표시
    4. 알림을 누르면 해당 대화(수락)로 바로 이동하는 딥링크
    5. 선택: 전체 화면 수신 화면
  • 웹과의 연결: 기존 웹 푸시와 새 FCM이 이중 발송되지 않도록, 앱에서는 FCM만 사용하고 웹 푸시 구독은 등록하지 않음

4. 서버 변경

  • FCM 토큰 등록 API: 앱이 토큰을 서버에 등록(지갑 서명 확인은 현재 웹 푸시 등록과 같은 방식). 저장은 PocketBase의 푸시 구독 정보와 같은 곳에 종류 필드를 추가
  • 발송 경로: Worker의 푸시 발송 함수(_sendPushToGuid)가 웹 푸시와 FCM을 모두 지원하도록 확장. FCM HTTP v1(서비스 계정 인증, 우선순위 high)
  • 호출 신호 유지: 호출 신호 3분 보관, 응답 대기 2분 유지
  • 준비물: Firebase 프로젝트, 서비스 계정 키(Worker 비밀값으로 등록)

5. 웹앱 변경(최소)

  • 앱 안에서 실행 중인지 감지해, 웹의 "알림 소리·배터리" 안내창 대신 앱의 네이티브 안내를 사용
  • 앱에서는 웹 푸시 구독을 건너뛰고 앱이 FCM 토큰을 등록
  • 매뉴얼 가입하기 장에 "앱 설치하기" 절 추가

6. 일정(안)

단계내용기간(안)
0. 준비개발자 계정, Firebase 프로젝트, 서명 키, 패키지 이름 확정1~2일
1. 검증TWA와 WebView 두 방식으로 지갑 지문(PRF)·로그인·알림 실기 시험, 방식 확정3~5일
2. 앱 뼈대TWA 앱, 도메인 인증, 아이콘·스플래시, 내부 테스트 배포3~4일
3. 알림FCM, 알림 채널, 서버 발송 확장, 알림 누르면 수락으로 이동5~7일
4. 설정 안내알림 권한·배터리 예외 동의 화면, 시험 알림2~3일
5. 시험제조사별 폰(삼성·LG·샤오미 등), 화면 꺼짐·절전·재부팅 시나리오5~7일
6. 출시스토어 등록 자료, 개인정보 처리방침, 심사 대응, 단계적 출시5~10일(심사 포함)

일정은 추정치이며 1단계 검증 결과에 따라 달라집니다.

7. 스토어 정책 확인 사항

  • 배터리 최적화 예외 요청: 구글 플레이는 이 권한을 쓸 수 있는 앱 유형을 제한합니다. 메시징·통화처럼 핵심 기능이 영향을 받는 경우에 허용되는 것으로 알고 있으나, 심사 기준을 출시 전에 문서로 확인해야 합니다. (확인 필요)
  • 전체 화면 알림: 안드로이드 14 이후 통화·알람 앱 중심으로 제한됩니다. 나비웹의 대화 요청이 해당되는지 확인이 필요합니다. (확인 필요) 해당되지 않으면 높음 중요도의 일반 알림(헤드업)을 사용합니다.
  • 개인정보: 위치·연락처·알림 권한은 사용 목적을 처리방침과 권한 요청 화면에 명시
  • 스토어 외 배포: 심사 지연에 대비해 APK 직접 설치 링크를 병행할 수 있음(알 수 없는 앱 설치 허용 필요)

8. 위험과 대응

위험대응
WebView에서 지갑 지문(PRF)이 동작하지 않음TWA를 기본으로 하고 1단계에서 실기 확인
제조사별 절전 정책(삼성·샤오미 등)이 앱을 종료제조사별 안내 화면과 시험 목록 운영, 배터리 예외 요청
웹 푸시와 FCM 중복 알림앱 사용 기기는 FCM만 등록, 서버가 기기별 한 경로로만 발송
스토어 심사에서 권한 거절사전에 정책 확인, 거절 시 일반 알림으로 대체
웹 업데이트와 앱 업데이트의 불일치화면은 웹에서 즉시 갱신(앱 재배포 불필요), 앱은 네이티브 부분 변경 시에만 배포

9. 범위 밖

  • 아이폰(iOS) 앱 — 별도 방식이 필요하며, iOS의 웹 푸시는 홈 화면에 추가한 경우에만 동작
  • 화면을 네이티브로 새로 만드는 작업

10. 결정이 필요한 사항

  1. 패키지 이름과 앱 이름: kr.naviweb.app / "나비웹"으로 할지
  2. 구글 플레이 개발자 계정(등록비 25달러)의 소유자: 개인 또는 법인(Naviweb Inc.)
  3. Firebase 프로젝트 생성과 서비스 계정 키 발급(계정 소유자 작업)
  4. 스토어 출시 전에 APK 직접 설치로 먼저 시험할지
  5. 전체 화면 수신 화면을 목표에 포함할지(정책 확인 후 결정)

11. 이 계획서가 확인하지 못한 것

이 작업 환경에서는 안드로이드 앱을 만들거나 폰에 설치해 시험할 수 없어서, 위 내용은 공개된 문서와 일반적인 구현 방식에 근거한 설계입니다. 특히 PRF 동작, 스토어 정책, 제조사별 절전 동작은 1단계 검증과 정책 문서 확인으로 확정해야 합니다.
