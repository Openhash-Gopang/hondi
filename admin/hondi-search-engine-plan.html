한국 논문 중심 파일럿 (개정 4판)

어느 대학의 어느 교수가 언제 어떤 논문을 발표했는지 찾고, 그 내용을 요약으로 확인하고, 원문까지 바로 이어 주는 논문 검색 엔진. 데이터는 한국 학술·연구 기관의 공개 API를 중심으로 모은다.

작성일 2026-10-28 준비 10/29부터 인증키 신청 파일럿 기간 2026-11-02 ~ 12-27 (8주)

1. 요약

이 엔진의 중심은 논문이다. 교수 검색은 논문의 저자·소속에서 만들어지는 “저자 보기”로 둔다. 데이터는 크롤링보다 학술 기관의 공개 API로 먼저 가져오고, 크롤러와 검색 서비스는 API가 채우지 못하는 부분(교수 직위·연락처 확인, 원문 링크 보강)에만 쓴다.

3판에서 달라진 점

  • 수집 방향이 반대가 되었다. 이전에는 교수 목록에서 시작해 논문을 붙였다. 이제는 논문 메타데이터(제목·저자·소속·초록·키워드·DOI)에서 시작해 교수와 대학을 구성한다.
  • 요약과 원문 연결이 핵심 기능이 되었다. 논문마다 초록 기반 한국어 요약을 만들고, DOI와 원문 링크를 확인해 보여 준다.
  • 인증키 신청이 일정의 병목이다. 승인에 걸리는 시간을 모르므로 0주차(10/29~)에 바로 신청하고, 키가 도착하기 전에는 키가 필요 없는 오픈 데이터로 먼저 진행한다.
  • 수집 서버에는 고정 공인 IP가 필요하다. ScienceON이 호출 서버의 공인 IP를 등록하게 하므로, API 수집은 Cloudflare Workers가 아니라 고정 IP 서버에서 실행한다.

2. 목표와 범위

2.1 파일럿 목표

  1. 제목·키워드·주제 문장·저자명·대학 중 무엇으로 물어도 해당 논문을 찾는다.
  2. 논문마다 저자(교수), 소속 대학·학과, 발행연도·학술지, 요약, 원문 링크를 한 화면에서 보여 준다.
  3. 교수 한 사람의 논문 목록을 연도순으로 볼 수 있다.
  4. 수집 → 병합 → 요약 → 색인 → 서비스가 자동으로 돌고, 새 데이터 영역(코퍼스)은 설정 추가로 늘릴 수 있다.

2.2 범위에 넣는 것

  • 파일럿 5개 대학 소속 저자의 국내 학술지 논문(KCI 중심)과 해외 저널 논문(OpenAlex 등 보완)
  • 저자·소속 해석, 동명이인 구분, 학문 분류와 K-EDU 소분류 매핑
  • 초록 기반 한국어 요약, DOI·원문 링크 확인
  • 교수 프로필 보강(직위·전공·대학이 공개한 연락처). 논문 기능이 안정된 뒤 붙인다(5.1의 규칙 적용).

2.3 범위에서 뺀 것

  • 교수·논문의 평가·순위·우수 추천. 인용 수는 사실값으로만 표시하고 정렬 기본값으로 쓰지 않는다.
  • 논문 전문(PDF) 저장·재배포와 전문 기반 요약. 오픈액세스 이용 허락이 확인된 논문만 2단계에서 검토한다.
  • 비공개 개인정보, 개인 휴대전화 번호
  • 학위논문·보고서·특허(2단계 이후)

4.2 API 수집 방식

  • 고정 공인 IP 서버에서 실행한다. 한림 노드 등 고정 IP가 있는 서버에서 수집기를 돌리고, 그 IP를 ScienceON에 등록한다. Cloudflare Workers는 검색 중계에만 쓴다.
  • 초기 적재 후 증분 갱신. 파일럿 대상의 논문을 먼저 적재하고, 이후 주 1회 신규·수정분만 가져온다.
  • 한도 존중. 일 호출 한도의 70% 이하로 스케줄하고, 오류 시 지수 백오프로 재시도한다. 원본 응답(XML·JSON)은 가공하지 않은 채 별도 보관한다.
  • 키 관리. 인증키는 서버 비밀 값으로만 저장하고 저장소에 올리지 않는다.
  • 원천별 약관 요약을 sources에 기록하고, 재배포가 제한된 항목은 화면에 링크로만 표시한다.

4.3 크롤러(구글식 구조): 보조 수집

API가 채우지 못하는 교수 프로필·연락처 확인과 원문 링크 보강에 쓴다. 구글의 수집 구조(시드, 방문 대기열, 예절, 페처, 렌더링, 추출, 정규화, 링크 그래프, 재방문)를 차용하되 범위를 학술·대학 도메인으로 제한한다.

  • 허용 목록 방식. 승인한 대학·연구기관 도메인 안에서만 링크를 따라가고, 목록 밖 링크는 기록만 한다.
  • 예절. robots.txt와 noindex를 지키고, 호스트별 요청 간격 제한, 조건부 요청(ETag·Last-Modified), 식별 가능한 User-Agent를 쓴다. 약관이 자동 수집을 금지한 사이트는 링크 연결만 한다. 중단 요청은 즉시 반영한다.
  • 렌더링과 추출. 정적 HTML을 우선하고 필요한 곳만 헤드리스 브라우저를 쓴다. 구조화 데이터(JSON-LD·메타 태그) → 대학별 규칙 → 보조 추출(LLM) 순서이며, 추출값은 형식·기존 값 일치 검증을 통과해야 저장한다.
  • 링크 그래프와 재방문. 학과 → 교수 → 연구실 → 논문 링크를 저장해 우선순위와 교차 확인에 쓰되, 순위에는 반영하지 않는다. 변경이 잦은 페이지는 짧게, 드문 페이지는 길게 재방문한다.
  • 로그인·개인정보 페이지는 수집하지 않는다. 수집 원문은 근거 보관용이며 재배포하지 않는다.

법적 위험은 구글과 같지 않다. 국내에서는 타인의 데이터베이스를 무단으로 대량 수집·이용한 행위가 부정경쟁방지법이나 저작권법(데이터베이스제작자 권리) 문제로 다투어진 사례가 있다. 수집 범위·빈도·재이용 방식은 착수 전에 법률 검토를 받는다. 이 계획서는 법률 자문이 아니다.

4.4 검색 서비스를 쓰는 보조 발견

크롤러가 교수 프로필 페이지를 찾지 못한 경우에만 “대학 이름 학과 교수” 질의로 후보 URL을 찾는다. 후보는 허용 도메인에 속한 것만 크롤러에 넘기고, 값은 대학 페이지에서 직접 읽어 출처와 함께 저장한다. 검색 서비스의 요약문·순위는 저장하지 않는다.

  • 구글 Custom Search JSON API는 신규 가입이 닫혀 있고 2027-01-01에 종료되므로 쓰지 않는다. 구글 결과를 긁어 오는 서드파티 서비스도 약관 충돌 소지가 있어 제외한다.
  • 후보: Vertex AI Search(5개교 도메인으로 제한), Brave Search API, 네이버 검색 오픈 API. 1주차에 약관·단가·한국어 품질을 비교해 정하거나, 보조 발견 없이 크롤러만으로 시작한다(15장).

4.5 원천 조건표(1주차 산출물)

원천마다 다음 항목을 확인해 표로 만들고, 팀이 승인한 원천만 본 수집에 쓴다: 일 호출 한도, 응답 형식, 재배포·저장 가능 범위, 출처 표기 의무, 상업 이용 가능 여부, 초록 표시 가능 여부, 약관 변경 통지 방식. 조건이 맞지 않는 원천은 “검색에만 쓰고 원문은 링크로 연결”하는 방식으로 낮춘다.

검색 색인은 논문 문서(제목·초록·키워드·요약·저자·소속)가 기본이고, 교수 문서(이름·소속·전공·대표 논문)는 저자 보기용 보조 색인이다.

5.1 연락처 처리 규칙

  • 출처 필수. 값마다 출처 URL, 수집 시각, 검증 상태를 저장하고 화면에 출처 링크와 최종 확인일을 함께 표시한다. 확인 후 90일(시작값)이 지난 값은 “확인 필요”로 표시한다.
  • 이메일. 도메인이 소속 대학 공식 도메인과 일치하면 검증 통과. 다르면 검수 큐로 보내고 기본 표시하지 않는다.
  • 전화. 대학·학과·연구실 전화만 저장하고 휴대전화(010 등)는 수집 단계에서 걸러 저장하지 않는다.
  • 표시와 악용 방지. 이메일은 로그인한 사용자에게만 보이고 전체 목록을 내려받는 API는 만들지 않으며, 계정별 호출 한도를 둔다. 연락처는 검색 색인에서 제외한다.
  • 숨김·정정. 교수 본인의 요청은 즉시 반영하고, 재수집으로 되살아나지 않도록 차단 목록에 기록한다.

6.1 논문 병합

같은 논문이 KCI·ScienceON·OpenAlex에 중복해서 들어온다. DOI가 같으면 같은 논문으로 본다. DOI가 없으면 정규화한 제목, 발행연도, 첫 저자, 학술지를 조합한 키와 제목 유사도로 후보를 묶고, 확신이 낮으면 병합하지 않고 검수 큐로 보낸다. 서로 다른 논문을 합치는 오류가 가장 해로우므로 병합 정밀도를 우선한다.

6.2 저자·소속 해석(가장 어려운 단계)

  1. 소속 정규화. “동아대”, “Dong-A Univ.”, 학과명만 있는 표기를 기관 사전으로 통합한다. 사전은 공공데이터의 대학·학과 코드에서 시작해 실제 표기를 보며 늘린다.
  2. 후보 묶기와 점수. 이름(국문·영문 변형)과 정규화 소속으로 후보를 묶고, ORCID 일치, 공저자 겹침, 키워드·초록 벡터 유사도, 소속 이동의 연속성을 합산한다.
  3. 확신도 분기. 높으면 자동 연결, 중간이면 검수 큐, 낮으면 연결하지 않는다.
  4. 정정 반영. 검수와 정정 요청 결과를 정답 데이터로 쌓아 가중치를 조정한다.

6.3 논문 요약

  • 입력은 초록·제목·키워드. 논문 전문은 입력으로 쓰지 않는다(오픈액세스 허락이 확인된 논문만 2단계에서 검토).
  • 출력은 3문장 이내의 한국어 요약(연구 목적, 방법, 주요 결과). 영문 초록만 있으면 한국어로 요약하고 영문 초록 링크를 함께 제공한다.
  • 자동 검증. 요약에 나온 수치·고유명사·결론이 초록에 있는지 대조해, 근거가 없는 문장이 있으면 그 요약을 저장하지 않고 재생성하거나 비워 둔다.
  • 표시. “AI 요약 · 초록 기반 · 원문 확인 필요”를 붙이고, 사용한 모델과 버전을 저장한다. 초록이 없는 논문은 요약을 만들지 않고 제목·키워드·원문 링크만 보여 준다.
  • 초록 원문 노출 여부는 원천 약관에 따른다. 허용되지 않으면 요약만 보여 준다.

6.4 원문 링크

  • 연결 순서는 DOI(doi.org) → KCI 상세·원문 링크 → 학술지·학회 페이지. 오픈액세스로 확인된 경우 표시한다.
  • 링크는 주 1회 점검(응답 상태 확인)하고, 깨진 링크는 다음 경로로 대체한다.
  • 원문 파일은 저장하거나 재배포하지 않고 링크로만 연결한다.

6.5 분야 분류와 갱신 주기

  • 한국연구재단 학문 분류를 기준 축으로, OpenAlex 주제 분류와 K-EDU 교수 페르소나 소분류를 매핑 테이블로 연결한다. 매핑이 안 되는 항목은 “미분류”로 남기고 주간 점검 목록에 올린다.
  • 논문 증분 수집은 주 1회, 교수 소속·직위 확인은 월 1회, 분류 매핑·동의어 사전은 월 1회 점검한다.

7. 검색 구조

7.1 논문 중심 하이브리드 검색

  1. 키워드 검색(BM25). 한국어 형태소 분석을 적용한다. 필드 가중치는 제목 > 키워드 > 저자·소속 > 초록 > 요약 순으로 시작해 평가 결과로 조정한다.
  2. 의미 검색(벡터). 다국어 임베딩 모델(예: BGE-M3 계열 오픈 모델)을 자체 서버에서 돌려 한국어 질의와 영문 초록이 서로 매칭되게 한다. 질의가 외부 임베딩 서비스로 나가지 않는다.
  3. 결합과 재순위. 두 결과를 합친 뒤 상위 후보에만 재순위 모델을 적용한다. 기본 정렬은 관련도, 선택지로 최신순을 둔다.
  4. 필터. 대학, 학과, 저자, 발행연도, 학술지, 분야, 언어, 원문 링크 유무.
  5. 저자 보기. 논문 점수를 저자별로 모을 때는 상위 N편만 반영하고, 근거 논문을 함께 보여 준다.

7.2 검색 엔진 선택

안구성장점단점
A안OpenSearch 단일 노드(Nori 한국어 분석기 + k-NN 벡터)키워드·벡터·필터·집계를 한 엔진에서 처리, 한국어 분석기가 검증됨메모리 사용량이 큼, 운영 지식 필요
B안Meilisearch(키워드·하이브리드) + Qdrant(벡터)가볍고 설치가 쉬움, 개발 속도가 빠름한국어 형태소 품질과 집계 기능에서 약할 수 있음, 구성 요소 2개

2주차에 같은 평가 질의로 벤치마크해 정하되, 결과가 비슷하면 구성 요소가 적은 A안을 택한다. 엔진은 검색 서비스 뒤에 숨겨 두어 나중에 바꿔도 API와 화면은 그대로 둔다.

7.3 질의 해석

사용자 문장을 LLM으로 필터(대학·학과·연도·저자), 검색어(국문·영문 동의어 포함), 의도(주제 탐색·저자 중심·제목 확인·원문 찾기·협업 탐색)로 바꾼다. 실패하면 원문 그대로 하이브리드 검색을 실행한다. 모델 호출부를 한 곳에 모아 필드 테스트 단계의 모델에서 앱 상용화 단계의 나비 LLM으로 바꿀 수 있게 하고, 질의에는 사용자 개인정보를 넣지 않는다.

7.4 답변 생성 규칙

  • 결과 카드의 저자·소속·학술지·연도·링크는 DB 값만 표시한다(생성 금지).
  • “왜 이 논문이 나왔는가”를 한두 문장으로 말할 때는 근거(제목·초록 구절의 요지)가 있어야 하고, 없으면 만들지 않는다.
  • 결과가 없을 때는 이유와 다른 검색 방법(철자, 연도·소속 범위 넓히기)을 안내한다.

8. 혼디 연동

  • 혼디 검색(상단 검색창). 사용자 안내/개발자 문서 2단 토글과 “전체 없음” 결정을 유지한다. 질의가 논문·교수 의도로 판단될 때만 전용 검색 화면으로 넘기는 방식을 제안한다(15장).
  • K-EDU 교수 페르소나. 논문의 분야를 페르소나 소분류와 매핑해 “이 분야 교수 AI에게 물어보기”를 제공한다. 실존 교수와 페르소나는 별개이며 페르소나는 해당 교수 본인이 아님을 화면에 적는다.
  • 로그인. 모든 화면 우측 상단에 로그인 상태와 아이디를 표시한다. 필드 테스트 기간에는 아이디만으로 로그인하고 과금하지 않는다. 비로그인 사용자는 검색은 가능하되 결과 건수·페이지 수·연락처 등 일부를 제한한다(15장).
  • 행동 연결. 논문 카드에서 “이 논문 인용 형식 복사”, “저자에게 문의 메일 초안”(K-Mail, 발송은 사용자 확인 후)을 제공한다. 서비스별 정액 과금 체계에 맞춰 호출 단위 로그를 남긴다.

9. 화면 구성

  • 검색 첫 화면. 검색창, 예시 질의 5개, 대학·연도·분야 필터.
  • 결과 목록(논문 카드). 제목, 저자와 소속 대학·학과, 학술지와 발행연도, AI 요약(라벨 포함), 원문 링크 버튼과 오픈액세스 표시, 출처와 최종 확인일.
  • 논문 상세. 초록(허용 시), 요약, 키워드, 저자(교수 연결), 원문·DOI 링크, 비슷한 논문.
  • 저자 보기. 소속·전공, 연도순 논문 목록, 분야별 보기, “정보가 틀렸나요?” 정정 버튼.
  • 공통 규칙. 폰트는 Pretendard, 모든 글자를 읽기 편한 크기(본문 18px 이상)로 하고, 사이트 공통 헤더(로그인 상태)를 쓴다.

11. 개인정보·저작권·법

  • API 약관 준수. 원천별 이용 약관(저장 기간, 재배포, 출처 표기, 상업 이용)을 조건표로 정리하고, 허용되지 않는 사용은 링크 방식으로 낮춘다. 데이터의 이용 조건은 코드의 GPL과 별개로 관리한다.
  • 초록·요약의 저작권. 초록은 저자·학술지의 저작물이다. 초록을 그대로 보여 줄지는 약관에 따르고, AI 요약은 초록을 근거로만 만들어 “AI 요약”으로 표시하며 원문 확인을 안내한다. 이 처리가 저작권법상 문제가 없는지는 상용화 전에 검토한다.
  • 수집 최소화. 공개된 직위·소속·연구 업적과 대학이 공개한 이메일·학과 전화만 다룬다. 개인 휴대전화 번호는 수집하지 않는다.
  • 연락처 악용 방지. 5.1의 규칙(로그인 후 표시, 대량 내려받기 금지, 호출 한도, 숨김 요청 즉시 반영)을 따른다.
  • 평가성 표현 금지. 순위·등급·“추천 교수” 표현을 쓰지 않는다. 인용 수는 사실값으로만 둔다.
  • 정정·삭제 통로. 모든 논문·저자 화면에 정정 요청 버튼을 두고, 처리 기한과 담당자를 정해 이력을 남긴다.
  • 사용자 데이터 국내 처리. 질의와 임베딩은 해외 서비스로 이전하지 않는 것을 기본으로 한다. 필드 테스트 중 외부 LLM API를 쓰는 부분은 질의 해석·요약에 한정하고, 개인정보를 제거한 문장만 보낸다.

법률 검토 필요. 대학 홈페이지 정보의 수집·가공 허용 범위, 이름과 연락처를 묶은 데이터베이스의 구축 목적·범위·보관 기간, 초록 이용과 AI 요약의 저작권 문제는 상용화 전에 전문가 검토를 받는다. 이 계획서는 법률 자문이 아니다.

15. 결정이 필요한 사항

  1. 인증키 신청 명의. 법인(AI City Inc.) 명의로 신청할지 개인 명의로 할지. 공문이 필요한 경우 법인 명의가 유리하며, 일부 서비스는 기관 사용자만 신청할 수 있도록 바뀌는 추세다.
  2. 고정 IP 서버. 수집기를 돌릴 서버와 그 공인 IP를 확정할 것.
  3. 파일럿 대학 5곳. 제주 지역 대학을 포함하고 규모·분야가 다른 대학을 섞는 구성을 권한다.
  4. 저장소와 도메인. 별도 저장소(예: search)와 하위 도메인으로 시작할지, 기존 hondi 저장소 안에서 시작할지.
  5. 혼디 검색과의 연결 방식. 8장의 “질의 의도로 넘기기” 방식으로 갈지, 별도 페이지 진입만 둘지.
  6. 검색 엔진. 7.2의 A안·B안은 2주차 벤치마크 후 결정(권고: 결과가 비슷하면 A안).
  7. 비로그인 이용 범위. 검색 가능 횟수, 결과 페이지 수, 정정 요청 가능 여부.
  8. 정정·삭제 요청 처리 주체. 담당자와 기한(예: 접수 후 7일 이내).
  9. 크롤러 운영 방식. 봇 이름·소개 페이지·연락처를 정하고, 약관이 수집을 금지한 대학은 링크 연결만 할지, 대학 측에 사전 협조를 요청할지.
  10. 보조 발견용 검색 서비스. 4.4의 후보를 1주차에 비교해 정하거나, 보조 발견 없이 크롤러만으로 시작할지.
  11. 연락처 표시 범위. 이메일을 로그인 사용자에게만 보여 줄지, 학과 전화까지 같은 기준으로 묶을지, 상용화 이후에도 유지할지.
  12. 초록 노출 방식. 약관이 허용하면 초록 전체를 보여 줄지, 요약만 보여 줄지.

16. 확장 로드맵

  • 2단계(파일럿 직후). 전국 대학 확대, 학위논문·보고서·특허 추가, NTIS 과제와 성과 논문 연결, 공동연구 네트워크 보기, 오픈액세스 논문의 전문 요약
  • 3단계. 출연연·병원 등 다른 기관의 연구 업적 코퍼스. 직종별 법적 표시 의무와 광고 규제를 먼저 검토
  • 4단계. 대학·행정기관·법령 코퍼스로 K-정부 페이지 검색을 같은 엔진으로 통합
  • 5단계. 나비웹 앱에서 나비 LLM이 질의 해석과 요약을 맡도록 전환, 서비스별 과금 체계 연동

파일럿 결과 보고서에는 수집 비용, 서버 자원, 정확도 지표, 정정 요청 건수를 포함해 이후 클라우드 구축 비용 산출의 근거 수치로 쓸 수 있게 한다.
