Overview
이 문서가 왜 있는가

이 문서는 혼디 검색 기능 자체의 사용법이 아니다(그건 docs/design/HONDI_SEARCH_DESIGN.md 참고). 여기서 다루는 건 "새 API 엔드포인트를 하나 추가했는데 배포해도 계속 404/405만 난다", "git am을 분명히 새 브랜치에서 실행했는데 커밋이 main에 가 있다" 처럼, 앞으로도 똑같이 겪을 수 있는 패턴들이다. 전부 이번 세션에서 실제로 발생하고 실제로 해결한 것들이다.

① 정적 파일 경로
GitHub Pages는 리포 트리를 그대로 미러링한다

hondi.net은 리포 루트가 GitHub Pages 소스다 (CNAME, desktop.html, index.html이 전부 루트에 있음). 그래서 public/site-manifest.json으로 커밋한 파일은 hondi.net/site-manifest.json이 아니라 hondi.net/public/site-manifest.json으로 서빙된다 — GitHub Pages는 "static assets 폴더"라는 관례적 개념이 없고, 그냥 리포 경로를 그대로 URL 경로로 미러링할 뿐이다.

함정
Worker가 fetch('https://hondi.net/site-manifest.json')로 정확한 URL을 호출하는 코드를 짜놓고도, 정작 파일을 엉뚱한 하위 폴더에 커밋해서 그 URL이 애초에 존재하지 않았다. 배포 로그도 정상, 코드 문법도 정상이었기 때문에 처음엔 원인을 못 찾았다.

확인법

  • 정적 파일을 새로 추가할 땐, 그 파일이 서빙될 URL과 리포 내 경로가 정확히 일치하는지부터 확인한다 — GitHub Pages 소스가 루트인지 /docs인지 저장소 Settings → Pages에서 재확인.
  • curl -I https://hondi.net/<경로>로 배포 직후 바로 검증한다 (GitHub Pages는 push 후 보통 1분 이내 자동 반영).
② 인프라 — 이번 세션 최대 시간 소모 지점
Route가 있어도 DNS가 안 뚫려있으면 소용없다

Cloudflare에서 hondi.net/hondi-search 같은 요청이 실제로 Worker에 도달하려면 두 가지가 동시에 맞아야 한다. 하나만 맞고 하나가 안 맞으면 증상이 똑같이 "그냥 안 됨"으로 보여서 원인 구분이 매우 헷갈린다.

조건확인 위치안 맞으면
DNS 레코드가 Proxied(주황 구름) DNS → Records → 대상 레코드 Cloudflare가 요청을 아예 안 보고 origin(GitHub Pages 등)으로 직행 — Route를 아무리 정확히 설정해도 무의미
해당 zone에 Workers Route 등록됨 Workers & Pages → 해당 Worker → Domains, 또는 zone → Workers Routes DNS는 Cloudflare를 거치지만 그 경로만 Worker로 안 넘겨져서 여전히 origin이 응답
이번에 실제로 벌어진 순서
  1. DNS가 Proxied인 줄 알고(실제로는 확인 없이 넘겨짚음) Route만 추가 → 안 됨
  2. DNS를 직접 확인 → 실제로는 DNS only(회색)였음
  3. Proxied로 전환 → 됨
1번에서 "Route를 추가했는데 왜 안 되지"로 한참 헤맸다. DNS 색깔부터 먼저 봤으면 그 시간을 아꼈을 것이다.
③ 진단 단축키
코드 문제 vs 인프라 문제, curl 헤더 한 줄로 구분

curl -i https://대상URL 응답의 Server 헤더와 CF-RAY 유무만 보면 즉시 구분된다. 매번 이것부터 확인하고 코드를 의심하는 순서로 가면 헛수고를 크게 줄일 수 있다.

증상의미
Server: cloudflare + CF-RAY 있음 Worker까지 도달함 — 문제가 있다면 코드/로직 쪽. 404/405가 떠도 그게 Worker 자신이 만든 JSON 에러라면 정상 동작.
Server: GitHub.com / Varnish, CF-RAY 없음 Cloudflare Worker에 전혀 안 감 — DNS/Route 인프라 문제. 코드를 아무리 고쳐도 소용없음.
SEC_E_WRONG_PRINCIPAL (SSL/SNI 에러) 더 근본적 — 그 도메인용 인증서 자체가 없음. GitHub Pages라면 저장소 Settings → Pages에 커스텀 도메인이 아예 등록·검증 안 됐을 가능성.

로컬 PowerShell에서 curl.exe -i 대신 Invoke-WebRequest를 쓰면 한글이 깨져 보일 수 있는데 (콘솔 인코딩 문제, 서버 응답 자체는 정상), 필요하면 [Console]::OutputEncoding = [System.Text.Encoding]::UTF8로 해결한다.

④ 세션 최다 반복 사고
git 브랜치 사고 패턴 — 오늘 6번 반복됨

매번 원인이 똑같았다: git checkout -b <name>이 "이미 존재함"으로 실패하면, git은 에러만 찍고 조용히 이전 브랜치에 그대로 남는다. 그 직후 git am이나 git commit을 실행하면 의도한 새 브랜치가 아니라 그 이전 브랜치(대부분 main)에 커밋이 얹힌다. 콘솔 출력만 보면 "Applying: ..." 성공 메시지가 그대로 뜨기 때문에 한참 뒤(push나 PR 생성 단계)에야 눈치챈다.

같은 계열의 변종들
  • git am --abort 자체는 브랜치를 바꾸지 않으므로, 직전에 다른 브랜치로 checkout 해뒀다면 abort는 그 "다른 브랜치"에서 실행된다.
  • git push -u origin <name>은 현재 체크아웃된 브랜치가 아니라, 그 이름을 가진 로컬 브랜치를 push한다 — 만약 그 이름의 브랜치가 예전에 이미 존재했다면(다른 커밋을 가리키고 있어도), 지금 작업 중인 내용이 아니라 그 옛 브랜치가 올라간다.

복구 절차 (실제로 이번에 여러 번 씀)

git branch -f <의도한-브랜치명> HEAD # main 위 커밋을 올바른 브랜치로 이동 git checkout main git fetch origin git reset --hard origin/main # main을 원격과 동일하게 복구 git checkout <의도한-브랜치명> git rebase origin/main # 최신 main 위로 재배치(필요시) git push --force-with-lease origin <의도한-브랜치명>

예방 습관

  • checkout -b 직후 반드시 git branch --show-current로 확인 — 특히 에러가 한 번 이라도 났던 직후, 혹은 이전 세션/터미널을 이어받은 직후.
  • 재사용 가능성이 있는 브랜치명이면 새로 만들기 전에 git branch -D <name> 2>$null로 옛 것부터 지운다.
  • 커밋 직후 git log --oneline -1로 방금 만든 커밋이 붙은 ref 이름(HEAD -> ???)을 눈으로 확인한다.
⑤ 미묘한 함정
스쿼시 머지 후 로컬 브랜치는 "다른 커밋"이 된다

gh pr merge --squash는 원격 main에 완전히 새 커밋을 만든다 — 로컬에 남아있는 그 기능 브랜치의 원래 커밋은 이 새 커밋의 조상(ancestor)이 아니다. 내용은 같아도 커밋 해시와 히스토리가 다르다.

실제로 겪은 증상
스쿼시 머지된(이미 삭제됐어야 할) 로컬 브랜치 위에서 그대로 다음 작업(checkout -b 새브랜치)을 이어서 했더니, git이 "같은 변경을 양쪽이 각자 다시 만든 것"으로 착각해서 내용이 똑같은 한 줄을 놓고 진짜 merge conflict를 냈다. 원인을 몰라서 한참 헤맸는데, git merge-base A B로 두 브랜치의 공통 조상을 찍어보니 예상보다 훨씬 이전 커밋이 나와서 확인됐다.

예방

  • PR이 머지되면 반드시 git checkout main && git pull origin main부터 하고 나서 다음 브랜치를 딴다 — 방금 머지한 그 로컬 브랜치를 이어서 쓰지 않는다.
  • 이상한 conflict가 나면 git merge-base 브랜치A 브랜치B로 공통 조상이 생각한 지점이 맞는지부터 확인한다.
⑥ Windows 환경 특유 함정
PowerShell 파일쓰기 함정 2가지

1) Get-Content | Set-Content는 UTF-8 BOM을 끼워넣는다

wrangler.toml의 값 하나만 바꾸려고 (Get-Content x) -replace ... | Set-Content x를 썼더니, 원본 파일(BOM 없는 UTF-8)의 첫 줄에 BOM이 추가돼 git diff가 "값 하나"가 아니라 "1번째 줄 + 값 줄" 두 군데를 건드린 것으로 잡혔다. 이게 나중에 스쿼시 머지 orphan 문제(⑤)와 겹쳐서 진짜 merge conflict로 이어졌다.

# 이렇게 하지 말 것 (BOM 삽입됨) (Get-Content x) -replace 'old','new' | Set-Content x # 대신 - 원본 인코딩 그대로 보존 $content = Get-Content -Raw -Path x $content = $content -replace 'old', 'new' $fullPath = (Resolve-Path x).Path [System.IO.File]::WriteAllText($fullPath, $content, [System.Text.UTF8Encoding]::new($false))

2) [System.IO.File] 정적 메서드는 PowerShell 현재 위치를 안 본다

[System.IO.File]::ReadAllText("wrangler.toml")처럼 상대 경로를 그대로 넘기면, PowerShell의 Get-Location이 아니라 .NET 프로세스 자체의 작업 디렉터리 (보통 사용자 홈 폴더)를 기준으로 풀린다. 이 둘이 어긋나 있으면 파일을 못 찾거나(에러가 나면 그나마 다행), 최악의 경우 엉뚱한 위치에 새 파일을 만들어버린다 — 위 코드 예시처럼 Resolve-Path로 항상 절대경로를 만들어 넘길 것.

⑦ 오진단 사례
raw.githubusercontent.com 캐시로 "빈 병합"이라고 착각

병합됐다는 PR의 내용이 실제 파일에 반영됐는지 확인하려고 curl https://raw.githubusercontent.com/<org>/<repo>/main/<path>로 조회했는데 옛날 내용이 나왔다. "PR이 빈 병합이었다"고 결론 내리고 똑같은 수정을 처음부터 다시 만들어 사용자에게 재작업을 시켰는데, 나중에 보니 단순 CDN 캐시였다 (branch명 기반 URL은 몇 분간 캐시될 수 있음).

올바른 확인법

SHA=$(git ls-remote origin main | awk '{print $1}') curl -s "https://raw.githubusercontent.com/<org>/<repo>/$SHA/<path>"

커밋 SHA를 URL에 직접 박으면(브랜치명이 아니라) 콘텐츠 주소가 고정되므로 캐시 문제가 원천적으로 없다. branch 이름으로 최신 상태를 확인할 땐 항상 이 방식을 우선한다.

⑧ 배포 설정
Cloudflare KV 네임스페이스 id는 절대 추측하지 않는다

새 KV 바인딩이 필요할 때 wrangler kv namespace create <NAME>을 실행했더니 "이미 존재함" 에러가 났다 — 알고 보니 같은 이름의 네임스페이스가 이미 계정에 있었다(다른 세션에서 만들어졌거나 대시보드에서 수동 생성됨). placeholder id를 임의로 지어내는 대신, wrangler kv namespace list로 전체 목록을 뽑아 title이 정확히 일치하는 항목의 실제 id를 확인해서 썼다.

원칙
wrangler.toml에 새 KV 바인딩을 추가할 때 id를 모르면 REPLACE_WITH_REAL_KV_ID 같은 명백한 placeholder를 넣고 "★ 배포 전 필수" 주석을 남긴다. 절대 그럴듯한 형식의 가짜 id를 지어내지 않는다 — 이건 이 저장소의 wrangler.toml 상단 주석에 이미 명시된 원칙이기도 하다.
⑨ 프롬프트 엔지니어링
SP 우선순위 규칙은 서술형이 아니라 명령형이어야 먹힌다

두 규칙이 충돌 가능한 상황(모호한 질의를 명확화할지, 곧바로 다른 기능으로 위임할지)에서, 처음엔 "규칙 4보다 규칙 1을 우선한다"는 서술형 설명을 별도 항목으로 추가했다. 배포·라이브 테스트까지 마쳤는데도 모델은 여전히 원래 하던 대로 동작했다 — 우선순위 "설명"은 있었지만, 정작 경쟁 관계인 규칙 자체에는 어떤 제약도 걸려있지 않았기 때문이다.

해결은 경쟁하는 규칙 그 자체를 명령형으로 다시 쓰는 것이었다 — "규칙 4는 조건 X가 있을 때만 선택하라. 조건 X가 없다면 규칙 4를 선택하지 마라"처럼, 우선순위를 별도 설명이 아니라 각 규칙의 선택 조건 안에 직접 박아 넣었다. 그제서야 라이브 테스트가 기대한 대로 통과했다.

교훈
LLM에게 "A가 B보다 우선한다"는 메타 설명을 추가하는 것보다, B 규칙 자체에 "이 조건이 아니면 B를 선택하지 마라"는 명시적 금지 조건을 넣는 쪽이 안정적으로 더 잘 먹혔다. 배포됐다고 끝이 아니라, 실제 라이브 응답으로 검증해야 하는 이유이기도 하다.

  • 새 API 경로 추가 시: worker.js 라우트 등록 → wrangler.toml 필요 바인딩 → DNS Proxied 여부 → Workers Route 등록, 네 가지를 전부 확인. 하나라도 빠지면 증상이 똑같이 보인다.
  • "배포했다"와 "머지됐다"와 "실제로 반영됐다"는 전부 다른 사실이다 — 커밋 SHA 기준으로 직접 확인하기 전엔 확정하지 않는다.
  • git 작업 중 에러가 한 번이라도 나면, 다음 명령 실행 전에 git branch --show-current부터 찍는다.
  • PowerShell로 파일을 고칠 땐 Get-Content -Raw + Resolve-Path + [System.Text.UTF8Encoding]::new($false) 조합을 기본값으로 쓴다.
  • SP/프롬프트 규칙 두 개가 충돌 가능하면, 우선순위를 설명하는 별도 문장보다 경쟁 규칙 자체에 선택 조건을 못박는 쪽을 먼저 시도한다.
⑩ 헛수고했던 사례
PowerShell로 한글 API 테스트하면 인코딩이 깨진다

배포·코드·매칭 로직을 몇 번이나 다시 확인하고 재배포했는데도 "내과 의사" 검색이 계속 실패했다. wrangler tail로 실제 Worker에 도착한 요청을 직접 찍어보고 나서야 원인을 알았다 — query="?? ??". "내과 의사"가 애초에 물음표로 깨진 채 서버에 도착하고 있었다. 코드도, 배포도, 매칭 로직도 전부 처음부터 정상이었다.

원인
Invoke-RestMethod -Body '...'로 한글이 포함된 JSON 문자열을 보내면, PowerShell이 요청 본문을 인코딩하는 과정에서 한글이 깨질 수 있다 — 이건 터미널 화면에 물음표로 "보이는" 것과는 다르다(그건 흔한 표시 문제), 실제로 서버에 도착하는 바이트 자체가 깨진 것이라 서버 쪽에서는 그 어떤 로직으로도 복구할 수 없다.

교훈

  • 다국어(특히 한글) 입력이 관련된 기능은, CLI 도구로 아무리 정밀하게 재현해봐도 결론을 내리지 말고 실제 사용 경로(브라우저)로 한 번은 반드시 확인한다 — 이번 경우 브라우저 검색창으로는 이미 정상 동작하고 있었는데, PowerShell 테스트 결과만 믿고 몇 차례나 불필요한 재배포·디버그 로그 추가를 반복했다.
  • 서버 로그(wrangler tail 등)에서 수신한 값 자체를 찍어보는 게, 클라이언트 쪽 도구를 의심하기 전에 코드만 계속 파고드는 것보다 훨씬 빨리 원인을 드러낸다.
  • 정 PowerShell로 한글을 테스트해야 한다면 ConvertTo-Json과 명시적 UTF-8 인코딩([System.Text.Encoding]::UTF8)을 거쳐 바이트를 직접 만들어 보내는 편이 안전하다 — 문자열 리터럴을 그대로 -Body에 넘기는 건 신뢰하지 않는다.
⑪ ④·⑤의 재발 사례
PR 제목과 실제 내용이 다를 수 있다 — 머지 후에도 파일로 직접 확인

이 문서 자체(당신이 지금 읽고 있는 이 파일)를 담은 PR이 "docs: 세션 실전 교훈 매뉴얼 + 인프라 전수 점검 인수인계서"라는 제목으로 성공적으로 병합됐다고 기록에 남아있었는데, 정작 실제 커밋 내용은 완전히 다른 작업(wrangler.toml Route 선언)이었다 — 이 문서와 인수인계서 파일은 머지된 적이 없는 상태로 몇 시간이 지나갔다. ④·⑤에서 다룬 git 브랜치 사고(체크아웃 실패 시 조용히 다른 브랜치에 남는 문제, 스쿼시 머지 후 로컬 브랜치 orphan)와 같은 계열의 사고가, 그 교훈을 문서화한 바로 그 문서 자신에게 벌어진 것이다.

교훈
"PR을 병합했다"는 사실은 그 제목이 맞다는 것도, 원하는 내용이 들어갔다는 것도 보장하지 않는다. 중요한 변경(특히 문서 신설처럼 "머지 안 돼도 에러가 안 나는" 종류)은 병합 직후 파일이 실제로 존재하는지, 원하는 내용이 들어있는지를 커밋 SHA 기준으로 직접 열어서 확인하는 습관을 들인다. "성공했다"는 CLI 출력 메시지 자체를 최종 증거로 삼지 않는다.
