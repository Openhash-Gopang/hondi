# 숫자 코드 등록 "본인 인증 실패" — 전화번호 비교 로직이 통째로 불필요했고,
진짜 원인은 그 아래 깔려 있던 PocketBase `seq=0` 검증 결함이었던 하루
(2026-09-25 ~ 09-26)

혼디 숫자 코드 등록에 문자(SMS) 인증을 붙이는 작업 중, "인증한 전화번호가
이 계정에 등록된 번호와 다릅니다"라는 오류가 계속 재현됐다. 표기 형식 →
저장된 해시 비교 로직 → 두 시스템의 비밀값 불일치까지, 그럴듯한 가설을
순서대로 의심하며 다섯 차례 수정했지만 전부 헛다리였다. 실제로는
① 애초에 "저장된 값과 대조"하는 단계 자체가 불필요하게 새로 만들어 넣은
것이었고, ② 그걸 걷어내고 나서야 드러난 **완전히 다른, 훨씬 근본적인
결함**(PocketBase가 숫자 `0`을 "값 없음"으로 오판)이 처음부터 모든 최초
등록을 막고 있었다. 그 사이사이 배포 파이프라인 자체의 결함 세 가지도
따로 발목을 잡았다. 다음에 "인증은 되는데 저장이 안 된다"류 증상을 보면
여기부터 먼저 확인할 것.

## 1. 증상 — 문자 인증·지문 확인까지 전부 통과하는데 등록이 안 됨

시험 페이지(`test-hondi-digit-v2.html`)에서 번호 등록 흐름(중복 확인 →
문자 인증 → 지문 확인 → 서버 등록)을 진행하면, 인증번호를 정확히 입력하고
지문도 통과했는데 마지막에 "인증한 전화번호가 이 계정에 등록된 번호와
다릅니다"로 거절됐다. 문자 인증 자체는 성공한 뒤에 나오는 오류라 앞뒤가
안 맞는 증상이었다.

## 2. 잘못된 가설 1 — 전화번호 표기 형식이 다르다 (r4)

혼디의 내부 표기(`+82` 뒤에 `0`을 남기는 방식, `+8201096627170`)와 통상
E.164(`0` 제거, `+821096627170`)가 섞여 있을 거라 보고 두 형식을 표준화해
비교하도록 고쳤다. 재현은 그대로였다.

**놓친 것**: 실제로 대조 대상이던 계정의 평문 `e164` 값은 이미 표준형
그대로였다(`+8201096627170`) — 형식 문제가 전혀 아니었는데, 겉보기
증상만으로 가장 그럴듯한 가설부터 짚은 것이었다.

## 3. 잘못된 가설 2 — 오래된 계정은 `e164_hash`가 다른 방식으로
   백필됐을 것이다 (r5~r8)

2026-09-07부터 새 가입 계정은 평문 `e164`가 항상 빈 문자열이고 번호는
`e164_hash`(`HMAC-SHA256(PHONE_VERIFY_SECRET, "e164-lookup:"+e164)`)로만
남는다는 걸 알고, 비교 기준을 평문에서 해시로 바꿨다(r5). 그래도 안 되자
"오래된 계정은 옛 표기로 해시됐을 것"이라 보고 후보 형식을 7가지까지
넓혔다(r6~r8). 매번 실패.

**놓친 것**: 가입 시점 SMS 인증이나 이미 운영 중인 K-Law 로그인·GDC 잔액
조회(`worker.js`의 `_resolveGuidFromPhoneVerifyToken`)는 애초에 **저장된
값과 대조하는 단계가 없다.** 서명·만료·`guid` 바인딩만 확인한다 —
신뢰는 "이 계정 자신의 번호로 요청한 OTP를 자신이 입력해 받은, 자신의
`guid`로 서명된 토큰"이라는 발급 경로 자체에서 나오고 그걸로 충분하다.
숫자 코드 등록에만 "계정에 저장된 값과도 일치해야 한다"는, 다른 어디에도
없는 검사를 새로 만들어 넣은 게 애초의 실수였다. 몇 시간을 들여 형식과
해시를 추측하는 대신, **처음부터 검증된 기존 코드와 한 줄씩 비교했다면
바로 드러났을 문제**였다(실제로 사용자가 "비교해 보라"고 지시한 뒤에야
발견함).

**교훈**: 새 검증 단계를 추가하기 전에, "이미 동등한 역할을 하는 코드가
있는지"부터 저장소에서 찾아 그 패턴을 그대로 따를 것. 결과가 안 맞을 때도
내가 새로 만든 로직의 세부값(형식·해시)을 의심하기 전에, **그 로직 자체가
꼭 필요한지**부터 의심할 것.

## 4. 잘못된 가설 3 — Worker와 PocketBase의 `PHONE_VERIFY_SECRET`이 다르다

r8까지도 실패하자, 두 시스템의 비밀값이 그사이 어긋났을 거라 의심해 SSH로
PocketBase 서버의 실제 값을 확인하고, "지금 비밀값 기준으로 전체
`e164_hash`를 재계산"하는 마이그레이션까지 만들어 돌렸다.

결과: **처리 4건, 값 변경 0건.** PocketBase가 이미 갖고 있던 해시는
처음부터 정확했다. 비밀값은 애초에 다른 적이 없었다 — 가입 자체가
두 시스템이 같은 비밀값으로 서명·검증을 주고받아야만 성립하는 구조라,
논리적으로도 달랐을 수가 없었다. 그 사실을 미리 따져보지 않고 바로 SSH
접속부터 시도한 게 헛수고였다.

**교훈**: "혹시 비밀값이 다른가"는 가장 마지막에, 그것도 실행하기 전에
먼저 "구조적으로 다를 수 있는가"를 논리로 따져 배제할 수 있는지부터 볼 것.
이번 경우 가입 플로우가 이미 그 가능성을 논리적으로 차단하고 있었다.

## 5. 그 와중에 따로 발목을 잡은 배포 파이프라인 결함 세 가지

### 5-1. Cloudflare 엣지 캐시 — `CF_API_TOKEN`/`CF_ZONE_ID` 미등록

정적 페이지(`test-hondi-digit-v2.html`)가 몇 시간째 옛 버전으로 보였다.
`bump-app-version.yml`의 캐시 비우기 단계가 `secrets.CF_API_TOKEN`·
`secrets.CF_ZONE_ID`를 참조하는데, 저장소엔 이름이 다른
`CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID`만 있어 **매 배포마다
조용히 건너뛰어지고 있었다**(실패 표시조차 없음). 정확한 이름으로 두
비밀값을 새로 등록해 해결.

**교훈**: 워크플로가 참조하는 비밀값 이름과 저장소에 실제 등록된 이름이
같은지는, 조용히 skip되는 조건문(`if: env.X != ''`) 특성상 실행 로그
상태(✓)만 봐서는 절대 못 잡는다. 단계별 로그 내용을 펼쳐서 실제로 실행됐는지
확인할 것.

### 5-2. `workflow_dispatch` 수동 재실행 시 변경 파일 목록이 항상 빈 값

`Deploy PB Migrations` 워크플로를 수동 실행(workflow_dispatch)했더니
`git diff --name-only <한 커밋> -- 'pb_migrations/*.js'`가 매번 빈
결과를 냈다. 커밋 하나만 넘기면 "그 커밋 vs 지금 작업 폴더"를 비교하는데,
방금 체크아웃한 작업 폴더가 바로 그 커밋 상태라 차이가 없다고 나온
것 — **수동 재실행으로는 이미 병합된 파일을 다시 적용할 방법이 없는
워크플로 자체의 결함**이다. 우회: 서버에 SSH로 접속해
`SSH_ORIGINAL_COMMAND="<파일명>" /opt/gopang/ops/apply-pb-migrations.sh`를
직접 실행.

### 5-3. 마이그레이션이 실행 도중 실패해도 "적용됨"으로 기록됨

`e164_hash` 재계산 마이그레이션의 첫 실행이 `PHONE_VERIFY_SECRET
미설정`으로 맨 앞부분에서 예외를 던졌는데도(§5-1과는 다른 원인 —
마이그레이션은 `pocketbase migrate up`을 SSH 일회성 명령으로 직접
실행해 systemd의 `EnvironmentFile`을 물려받지 못했다), **PocketBase가
그 파일명을 이미 적용된 것으로 내부 기록해 버려서** 문제(`gopang.env`를
source하도록 배포 스크립트를 고친 뒤) 재실행하면 `No new migrations to
apply.`로 조용히 건너뛰었다. 새 파일명으로 같은 내용을 다시 만들어서야
실제로 실행됐다.

**교훈**: 마이그레이션이 실행 중 실패하면 재시도 전에 "그 파일명이 이미
적용됨으로 기록됐을 가능성"부터 의심할 것. 애매하면 새 파일명으로
재발급하는 쪽이 내부 기록을 직접 지우는 것보다 안전하다.

## 6. `e164_hash` 검사를 완전히 제거한 뒤에도 실패 — 이번엔 502

r5~r8의 저장된-값-대조 로직을 통째로 들어내고, 검증된 패턴(서명·만료·
`guid` 바인딩만 확인)으로 다시 짰다. 문자 인증 오류는 사라졌지만, 이번엔
**502**로 실패가 바뀌었다. 그런데 시험 페이지는 이 경우를 "서버가
연결되지 않았거나 응답하지 않아 이 기기에만 남았습니다"로만 뭉뚱그려
보여줬고, Cloudflare Logs를 봐도 요청 메타데이터(헤더·상태코드)만
있을 뿐 **실제 오류 메시지가 어디에도 남지 않았다** — 원인을 알아낼
방법 자체가 없는 상태였다.

### 6-1. 자체적으로 만든 결함 — `catch`에서 `try` 블록 스코프 변수 참조

502 원인을 남기려고 `catch (e) { console.error(...path...) }`를
추가했는데, 정작 이 로그 코드 자체가 `ReferenceError: path is not
defined`로 죽고 있었다. `try { const path = ...; } catch (e) { ...path... }`
— **JavaScript에서 `try` 블록의 `const`/`let`은 옆 `catch` 블록에서
안 보인다**(서로 다른 렉시컬 스코프). `url.pathname`을 직접 참조하도록
고쳐 해결. 단위 테스트가 이 결함을 즉시 잡아냈다(전체 스위트가
"path is not defined"로 실패).

**교훈**: `try`/`catch`에 걸쳐 변수를 쓰려면 선언을 `try` 밖으로
빼거나, 애초에 `catch` 안에서는 그 스코프에 독립적으로 존재하는 값
(함수 매개변수 등)만 참조할 것.

### 6-2. 진짜 원인 — PocketBase가 숫자 `0`을 "값 없음"으로 오판

로그·화면 노출을 고친 뒤에야 실제 오류가 드러났다.

```
L1 저장 실패 (HTTP 400) {"code":400,"message":"Something went wrong...",
 "data":{"seq":{"code":"validation_required","message":"Missing required value."}}}
```

`digit_claim_records.seq`(순번, `number`, `required: true`)는 **모든
최초 등록에서 항상 `0`이다.** PocketBase(ozzo-validation 기반)의 number
필드 필수값 검사가 "그 타입의 영값(0)"과 "값이 아예 없음"을 구분하지
못해, **처음부터 어떤 번호를 등록하든 최초 등록(`seq=0`)은 항상 이
단계에서 실패하고 있었다** — 오늘 오전부터 의심했던 문자 인증 문제와는
완전히 무관한, 그보다 훨씬 아래(저장 단계)에 있던 별개의 결함이었다.
문자 인증 로직을 몇 번을 고쳐도 이 결함이 그대로면 등록은 절대 성공할
수 없었다.

**수정**: `seq` 필드를 `required: false`로 변경(마이그레이션으로 스키마
수정). 정합성은 `(serial, seq)` 고유 인덱스와 애플리케이션 로직
(`hondi-digit-claim.js`의 `applyRecord`)이 이미 지키고 있어 데이터
손실 위험은 없다.

**교훈**: 숫자 필드에 "필수" 제약을 걸 때, 그 필드의 유효한 값 중에
`0`(또는 그 타입의 영값)이 있다면 검증 라이브러리가 그걸 "없음"으로
오판하지 않는지 먼저 확인할 것. 이번 프레임워크(PocketBase/
ozzo-validation)는 그런 부류였다. 시퀀스·카운터·인덱스처럼 0부터
시작하는 숫자 필드는 특히 주의.

## 7. 오류를 몇 시간이나 못 찾았던 진짜 이유 — 서버 오류가
   화면에도 로그에도 안 남고 있었다

돌아보면 §2~§5의 모든 헛수고는 **애초에 실제 오류 메시지를 볼 수 없었기
때문에** 추측에 의존할 수밖에 없었다. `digit-claim-handler.js`의
catch-all이 예외를 조용히 502 JSON으로만 바꾸고 로그를 전혀 안 남겼고,
시험 페이지도 "서버 미응답"이라는 한 문구로 모든 실패를 뭉뚱그렸다.
`§6-2`의 진짜 원인은, 그 두 가지를 고쳐 **화면에 실제 서버 응답을
그대로 노출**하자마자 한 번에 드러났다.

**교훈**: 오류를 추측하기 전에, 먼저 "그 오류가 실제로 눈에 보이는가"부터
확인할 것. 서버 예외를 사용자 문구로 뭉뚱그리는 방어적 처리는 그 자체로는
좋은 설계지만, **개발·디버깅 중에는 실제 원인을 어딘가에는(최소한 서버
로그에라도) 반드시 남겨야 한다.** 안 그러면 다음에 똑같은 조사를 처음부터
다시 해야 한다.

## 8. 근본 재발 방지 — 자동 검증 CI 신설

이 사고 전체를 관통하는 더 근본적인 문제: `worker.js`(Cloudflare)와
`pb_hooks/main.pb.js`(PocketBase JSVM)에 같은 전화번호 정규화·해시
로직이 손으로 두 번 옮겨 적혀 있는데, **실제로 같은 입력에 같은 출력을
내는지 자동으로 확인하는 수단이 하나도 없었다.** 그래서 §2~§4의 헛다리
짚기가 몇 시간이나 이어질 수 있었다. 게다가 `tests/digit-v2`의 단위
테스트 56개조차 **CI에 전혀 연결돼 있지 않아**, 사람이 `npm run
test:unit`을 손으로 돌릴 때만 실행되고 있었다는 사실도 이번에 함께
발견했다.

**조치**(같은 날 후속 커밋): `tests/cross-validation/`에 두 파일의
실제 소스 텍스트를 직접 읽어 해시 접두어·비밀값 변수명·토큰 형식이
서로 일치하는지 확인하는 테스트와, `.github/workflows/
check-digit-code-tests.yml`(관련 파일 변경 시 단위·교차 검증 테스트를
자동 실행)을 신설.

## 요약 — 다음에 "인증은 되는데 등록/저장이 안 된다"를 보면

1. **먼저 실제 서버 오류를 볼 수 있는지부터 확인.** 클라이언트가
   뭉뚱그린 문구만 보여주고 있다면, 원인 조사 전에 그것부터 고칠 것
   (`§7`).
2. 새로 만든 "저장된 값과 대조"류 검증이 있다면, **그 검증이 이미
   검증된 다른 코드에도 있는 패턴인지**부터 확인. 없다면 애초에
   불필요한 것일 가능성부터 의심할 것(`§3`).
3. 숫자 필드(특히 순번·카운터처럼 0부터 시작하는 값)에 "필수" 제약이
   걸려 있고 그 필드가 저장 단계에서 거절된다면, **검증 프레임워크가
   0을 "없음"으로 오판하는지** 확인할 것(`§6-2`).
4. 두 실행 환경(예: Cloudflare Worker ↔ PocketBase)에 같은 로직이
   중복 구현돼 있다면, 비밀값·형식을 추측하기 전에 **그 로직들이 실제로
   같은 출력을 내는지 자동 테스트부터** 만들 것(`§8`) — 이번처럼 매번
   손으로 다시 조사하지 않도록.
5. 배포 워크플로의 `if: env.X != ''` 같은 조건부 단계는 실행 로그
   상태(✓)만으로 안심하지 말고, **단계 내용을 펼쳐 실제로 실행됐는지**
   확인할 것(`§5-1`).
