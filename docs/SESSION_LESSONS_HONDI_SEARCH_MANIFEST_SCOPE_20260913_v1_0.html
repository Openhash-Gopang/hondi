SITE MANUAL — 2026-09-13 세션 발견 정리

검색창이 엉뚱한 답을 내놓은 이유는 코드가 아니라 데이터였다

desktop.html 상단 검색창에 "혼디 숫자 코드"를 입력하면 전혀 무관한 "하이라이트 번호" 후보가 나오는 버그를 조사하면서 시작했다. 원인은 SP의 의도 파악 로직이 아니라 site-manifest.json이 수기로 작성돼 있어(23개) desktop.html의 실제 메가메뉴(110개+)를 따라가지 못한 것이었다 — 데이터 소스가 하나가 아니라 흩어져 있으면 갱신을 깜빡하는 게 아니라 원리적으로 갱신될 방법이 없다는 게 핵심 교훈이다. 이 문서는 그 진단부터 매니페스트 자동 생성기·CI 가드· 검색 범위(user/dev) 분리 설계, 그리고 실제 배포 과정에서 반복 발생한 실수(빈 브랜치 push, 저장소 간 브랜치 혼동, 패치 파일 경로 착오)까지 전부 정리한다.

대상 저장소 Openhash-Gopang/hondi, Openhash-Gopang/hondi-search-relay 관련 PR hondi#217, hondi-search-relay#2 작성 2026-09-13
Overview
발단 — 사용자가 캡처한 대화 한 장

"혼디 사이트에서 혼디 숫자 코드 페이지를 찾아줘"라는 자연스러운 질문에 검색이 "하이라이트 번호(1번, 2번...)를 찾으시는 건가요?"라고 되묻는 스크린샷 하나가 출발점이었다. SP(hondi-search-relay의 HONDI_SEARCH_SP) 자체의 의도 파악 규칙은 정상이었다 — 단지 참조할 후보 목록(site-manifest.json)에 그 페이지가 아예 없어서, "모호하면 최상위 후보 3개를 제시하라"는 규칙이 완전히 무관한 항목들로 억지 작동한 것이었다.

핵심 교훈
AI 검색·라우팅 계열 버그를 만나면 먼저 SP 프롬프트의 판단 로직을 의심하기 쉽지만, 이번처럼 후보 데이터 자체가 최신이 아닌 경우가 실제로는 더 흔하다. SP를 고치기 전에 "이 SP가 보고 있는 데이터가 진짜 최신인가"부터 확인하는 습관이 시간을 아낀다.
① Root Cause
검색 매니페스트가 손으로 쓰여 있었다

site-manifest.json은 사람이 직접 작성·관리하는 파일이었고 23개 항목뿐이었다. 반면 실제 내비게이션은 desktop.html의 MEGA_MENU_SECTIONS(메가메뉴, 110개+ 링크)와 STANDALONE_PAGES(메뉴에 아예 링크가 없는 SPA 오버레이 9개 포함, 16개) 두 곳에 흩어져 있었다. "혼디 숫자 코드" 페이지(nav-scenarios, loadPage('scenarios'))는 메가메뉴엔 있었지만 매니페스트엔 등록된 적이 없었다 — 갱신 원칙이 코드 주석에 적혀 있었음에도(hondi-search-worker.js의 FALLBACK_MANIFEST 주석) 실제로 지켜지지 않았다는 것을 실측으로 확인했다.

실측 결과

소스개수비고
메가메뉴 전체 링크110개사용자 페이지 + 개발자 문서(HANDOFF·SESSION_LESSONS) 혼재
STANDALONE_PAGES16개이 중 9개는 메가메뉴 어디에도 링크 없음
기존 site-manifest.json23개수기 작성, 오늘 발견된 사고의 직접 원인
자동 생성 후119개user=40, dev=79
② Manifest Automation
매니페스트 자동 생성 + CI 가드

수기 작성 자체가 구조적 원인이므로, tools/generate_site_manifest.py를 신설해 desktop.html의 MEGA_MENU_SECTIONS + STANDALONE_PAGES + 알려진 특수 onclick 패턴 (_openUserDashboard 등)을 전수 파싱해 site-manifest.json을 자동 생성하도록 바꿨다. 미지의 onclick 패턴을 만나면 조용히 건너뛰지 않고 stderr 경고를 내도록 만들어, 다음에 새 메뉴 항목이 추가돼도 같은 유형의 누락이 소리 없이 반복되지 않게 했다.

# 재생성 python3 tools/generate_site_manifest.py # CI에서 쓰는 드리프트 감지 — 어긋나면 exit 1 python3 tools/check_site_manifest_sync.py

tools/check_site_manifest_sync.py는 tools/check_capabilities_registry.py와 같은 철학(자기보고를 믿지 않고 실측 대조)의 CI 가드다 — 오늘 발견한 사고(수기 23개 vs 실제 119개)를 그대로 재현시켜 정확히 실패하는 것까지 확인했다.

③ Scope Split
검색 범위(user/dev) 분리 설계

매니페스트를 전수화하면서, 메가메뉴의 "🛠 개발자 문서"·"⚠ 주의" 섹션(약 79개, HANDOFF·SESSION_LESSONS류)까지 일반 사용자 검색 후보에 섞이는 문제가 새로 생겼다. 검토 끝에 단일 SP + 매니페스트만 scope로 필터링하는 방식(방식 B)을 택했다 — SP 사본을 두 벌 두면 이 저장소가 반복 겪은 "한쪽만 갱신되고 드리프트 나는" 사고 계보와 같은 유형을 또 만든다는 게 이유였다.

핵심 구현

  • desktop.html: 검색창 옆 [사용자 안내] [개발자 문서] 세그먼트 토글, 기본값 사용자 안내, "전체" 옵션 없음
  • hondi-search-relay: normalizeScope()가 scope를 user/dev로 정규화(미지정·잘못된 값은 항상 user), filterManifestByScope()가 요청 시점에 메모리에서 필터링(캐시는 전체 매니페스트 하나만 유지)
  • SP 본문에 §3-2 신설: "매니페스트에 없는 페이지를 억지로 매칭하지 말라" — 오늘 사고를 예시로 명시
  • scope 전환 시 프런트가 대화 세션을 리셋(closePanel()) — 다른 범위의 매니페스트를 전제로 한 이전 turn이 이어지지 않도록
④ Test Debt
기존 스모크테스트 자체에 있던 결함

이전 세션이 이미 tests/live_smoketest/hondi-search.smoke.js를 작성해뒀다는 걸 오늘 발견했는데, 그 안에 assertion 버그가 2건 있었다 — json.url === "/services/klaw"처럼 워커가 실제로 반환하는 값(pc_url, 예: https://klaw.hondi.net)이 아니라 매니페스트의 path 식별자와 직접 비교하고 있었다. 즉 이 테스트는 애초에 통과할 수 없는 조건이었고, 그래서 오늘 사고("혼디 숫자 코드" 케이스 자체가 테스트에 없었던 것과 별개로) 이전에도 이 스위트가 실제로 초록불을 내고 있었는지 의심해봐야 한다.

교훈
매니페스트/후보 목록을 다루는 테스트는 기대값을 하드코딩하지 말고, 같은 매니페스트 파일을 런타임에 조회해서 기대값을 동적으로 구해야 한다 — 그래야 매니페스트가 바뀔 때(오늘처럼 23개→119개) 테스트가 같이 낡지 않는다. 고친 뒤 testHondiDigitCodeRegression(회귀)과 testScopeIsolation(scope 격리) 두 케이스를 추가했다.
⑤ Deploy Pitfalls
배포 실전 함정 — 오늘 실제로 겪은 실수들

패치 파일 2개(hondi용, hondi-search-relay용)를 만들어 전달했는데, 실제 적용 과정에서 반복해서 같은 유형의 실수가 났다. 전부 결과적으로는 해결됐지만, 다음에 패치를 전달·적용할 때 미리 경고해두면 좋을 패턴들이다.

함정 1 — git am 실패 후에도 뒤 명령을 계속 실행

패치 파일이 현재 폴더에 없는 상태로 git am이 fatal: could not open ... No such file or directory로 실패했는데, 그 뒤 git push가 그대로 실행돼 커밋이 하나도 없는 빈 브랜치가 원격에 올라갔다. 다행히 gh pr create가 diff 없음을 감지하기 전에 사용자가 중단해서 실제 PR 생성까지는 가지 않았다.

교훈
git am/git apply 직후엔 반드시 git log --oneline -3로 새 커밋이 실제로 생겼는지 확인한 다음에 push로 넘어간다. "에러 메시지가 안 무섭게 생겼다고 다음 명령을 계속 실행"하는 게 이 사고의 진짜 원인이었다.

함정 2 — 두 저장소 폴더에서 브랜치명이 뒤섞임

같은 이름의 로컬 hondi 폴더에서 작업하다가, 두 번째 저장소(hondi-search-relay)용으로 만든 브랜치명(feature/scope-toggle-user-dev)이 첫 번째 저장소 폴더에 그대로 체크아웃돼 있는 상태로 다음 작업을 이어간 순간이 있었다. git status로 미리 확인하지 않았다면 엉뚱한 브랜치에 패치를 적용할 뻔했다.

교훈
여러 저장소를 오가며 작업할 때는 폴더를 옮길 때마다 git status로 지금 브랜치가 이 저장소용이 맞는지부터 확인한다. 브랜치명에 저장소를 특정하는 접두어 (예: relay/, hondi/)를 붙이는 것도 같은 사고를 줄이는 방법이다.

함정 3 — zip 다운로드 중복·압축 해제 누락

브라우저가 같은 파일을 여러 번 받아 hondi-search-delivery (1).zip 같은 중복 파일이 쌓였고, 처음엔 zip을 아예 풀지 않은 채 .patch 파일 경로를 바로 참조하려다 실패했다.

# 항상 이 순서로 — 파일명이 실제로 뭔지부터 확인 Get-ChildItem C:\Users\주피터\Downloads\*.zip Expand-Archive ".\<실제 파일명>.zip" -DestinationPath .\hondi-search-delivery -Force Get-ChildItem .\hondi-search-delivery
