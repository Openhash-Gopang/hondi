# AC 라우팅 구조 정리 (2026-09-14)

이 문서는 인수인계서(`HANDOFF_2026-09-14_routing-precision-testing.md`)의
"교훈" 절을 근거로, **AC가 사용자 발화를 어디로 보내는지 판단하는 전체
구조**를 한 곳에 정리한다. 오늘 세션에서 같은 오해(특히 공공기관 라우팅을
"틀렸다"고 잘못 판정)가 반복됐던 이유는 이 전체 그림이 문서 하나에 정리돼
있지 않았기 때문이다 — 다음에 라우팅을 손대거나 테스트하는 사람은 이
문서부터 읽을 것.

## 0. 판단은 3단 계층이다

```
사용자 발화
   │
   ├─ §CATALOG 표 안? ──────────► [GWP: id]           (K-서비스, 새 탭/inline)
   │
   ├─ §CATALOG-EXPERT 표 안? ───► [EXPERT: id]          (전문가 페르소나, 1:1 상담)
   │
   └─ 둘 다 아님 ───────────────► [CALL_KINTENT: query=...]  (K-Intent 오케스트레이션)
```

**핵심 원칙(AC-PRO-CORE §CORE ②)**: `CALL_KINTENT`의 진입 조건은
"확신이 없다"가 아니라 **"대상이 두 표 밖이다"**이다. 표 안에서 GWP로 갈지
EXPERT로 갈지 애매한 경우는 CALL_KINTENT로 도망가는 게 아니라 AC가
표 안에서 직접 골라야 한다(코드가 `candidate-prefilter.js`로 이 판단을
돕는다 — 1절 참고). 오늘 실사에서 실패한 사례 대부분이 "CALL_KINTENT로
안전하게 샜어야 하는데 GWP로 잘못 갔다"가 아니라 "GWP와 EXPERT 둘 다
표 안에 있는데 어느 걸 고를지 잘못 골랐다"였다 — 이 구분을 못 하면
채점 자체가 틀어진다.

## 1. GWP 계층 (K-서비스) — `gwp-registry.js`

- 30개 활성 서비스. 각 항목은 `id`/`name`/`triggers`(키워드 배열)/`type`
  (`tab`|`inline`|`switch`|`tool`)을 가진다.
- 1단계 판단은 LLM(AC-PRO-CORE)이 하지만, `candidate-prefilter.js`가
  트리거 문자열 매칭으로 후보를 미리 점수화해 `[ctx]`에 힌트로 얹는다:
  - `findGwpR2Winner()` — GWP끼리 충돌(예: ktax vs kbusiness)할 때
    "더 구체적인 트리거를 포함하는 쪽"을 코드로 확정.
  - `findDominantCandidate()` — 경쟁자가 아예 없는 유일한 비영점 후보를
    코드로 확정(GWP·EXPERT 혼합 후보 풀에서 동작 — 2절과 공유하는 함수).
  - 둘 다 "확신 없으면 아무것도 확정 안 함"이 원칙(잘못 확정 > 확정 안 함).
- **오늘 배운 것**: `kregionalgov`("전국 지방행정 AI")와 `kgov`
  ("K-Public")는 로컬 행정 전반을 받는 범용 게이트웨이로 설계돼 있다.
  아래 2절에서 설명하는 "공공기관은 항상 CALL_KINTENT"라는 가정은
  틀렸다 — 정부기관 관련 발화 상당수가 이 둘로 정상 라우팅된다.

## 2. EXPERT 계층 (전문가 페르소나) — `expert-registry-*.js`

- §CATALOG-EXPERT 표엔 63개 상위 카테고리만 있다(예: `lawyer`,
  `physician`, `professor`). 실제 리프(세부 전공)는 `professor` 밑에만
  158개+ 있고, 이건 1단계 LLM은 존재 자체를 모른다 — 알 필요도 없다
  (아래 2-1절).
- **GWP 기본값 정책(2026-07-25)**: `lawyer`/`tax-accountant`/
  `real-estate-agent`/`appraiser`/`customs-broker` 등은 klaw/ktax/
  kestate 같은 인접 GWP와 겹치는 일반어(예: "변호사"·"소송")를
  트리거에서 **일부러 뺐다** — "GWP가 기본값, EXPERT는 명확한 위임의도
  구(phrase)가 있을 때만 우선"이라는 정책 때문이다. 그래서 "변호사랑
  상담하고 싶어요"만으로는 부족하고 "변호사에게 상담"류의 더 구체적인
  구가 있어야 EXPERT로 간다 — **이건 버그가 아니라 설계다.**
- **트리거 갭이 실제로 흔하다**: description/label이 이미 특정 상황을
  포함한다고 적어놓고 정작 `triggers` 배열엔 그 표현이 없는 경우가
  오늘만 10건 넘게 나왔다. 자연스러운 구어체("~할 사람이 필요해요")도
  자주 누락돼 있다 — 새 EXPERT를 등록하거나 트리거를 검토할 때
  description과 triggers를 항상 대조할 것.

### 2-1. professor 2단계 게이트 — `subject-gate.js`

- 1단계 LLM이 `[EXPERT: professor]`까지만 내면, `refineToLeaf()`가
  `EXPERT_REGISTRY`의 `parentKey` 트리를 **한 단계씩(직계 자식만)**
  내려가며 저지연 모델(`deepseek-v4-flash`)로 재분류한다.
- **2026-08-10에 flat(전체 리프 한 프롬프트)→계층형으로 리팩터됐다.**
  이 날짜를 반드시 기억할 것 — 이 리팩터를 놓친 낡은 테스트/코드가
  실제로 한 달 넘게 남아있었다(`dump_leaves.mjs`, 구
  `subject_gate_live_smoketest.py`). professor/physician/lawyer 세
  루트 전부 이 방식이다.
- 각 단계 후보엔 항상 "해당 없음"(id=그 단계 자신) 옵션이 끝에
  붙는다 — 확신 없으면 여기서 멈추고 더 안 내려간다(안전 폴백).
- 중계열(중간 노드, 예: `professor-materials-series`)의 **라벨이
  실제로 포함된 세부 항목을 안 알려주면 최상위 단계에서부터 매칭에
  실패**한다(예: "재료 중계열"이라는 라벨만으론 반도체공학이 거기
  있는 줄 아무도 모름) — 오늘 라벨 여러 개에 "OOO 포함" 힌트를
  추가한 이유가 이것이다.
- `max_tokens`는 계층형 전환 후에도 특정 발화에서 reasoning만으로
  소진되는 사례가 있어 1500→4000으로 올렸다(2026-09-14, 프로덕션
  코드 자체 수정 — 테스트만의 문제가 아니었다).

## 3. 공공기관 계층 — `gov-router.js` (JEJU-GOV-COMMON)

이게 오늘 가장 많이 오해했던 부분이다. **공공기관은 GWP·EXPERT 표
밖이므로 무조건 `CALL_KINTENT`로 간다"는 전제 자체가 틀렸다** —
`kregionalgov`가 열리면 그 뒤는 `gov-router.js`가 **독자적인 5단계
지방행정 라우팅**을 수행하고, 이 라우팅 자체가 국가기관 지역사무소까지
포함한다.

### 3-1. 두 갈래: 지방행정 vs 국가기관 지역사무소

- **지방행정**(`SP-DO-*`/`SP-CITY-*`/`SP-EMD-*`) — 도청→시/군/구청→
  읍/면/동, 자체 행정 사무(등본·인감·전입신고 등). "지방세"도 여기.
- **국가기관 지역사무소**(`SP-NAT-*`, `JEJU_NATIONAL_TABLE`) — 국세청·
  법원·국민연금공단·건강보험공단·출입국청 등 **중앙부처 산하지만
  제주에 실제 지사가 있는** 기관 34개+. `SP-NAT-TAX`("제주세무서
  (국세청) [국세 — 지방세 아님]")처럼 라벨에 소속과 구분을 명시해둔다.

### 3-2. "정부24 명시 소관기관" ≠ "실제 라우팅 목적지"

`gov24_corpus_live_smoketest.mjs`의 시나리오 350건은 각각
`note`에 "정부24가 명시한 소관기관"(예: 국토교통부)을 담고 있는데,
이건 흔히 **중앙부처**다. 그런데 등본·인감증명·전입신고 같은
실무는 전부 **지방행정 창구**(시/읍/면/동)에서 실제로 처리된다 —
소관 부처(행정안전부)와 실제 창구(지방행정)가 다른 게 정상이다.
**"trace에 그 부처 이름이 그대로 없으면 실패"라고 자동 채점하면
틀린다** — `gov24_corpus_report.py`가 자동 PASS/FAIL 대신 사람이
대조하는 표만 만드는 이유가 이것이다.

반대로 **대학 졸업증명서처럼 "제주"라는 지역 개념 자체가 안 맞는
요청**(발급 주체가 전국 어디든의 특정 대학교)은 지방행정에도 국가기관
지역사무소에도 억지로 끼워 넣으면 안 된다 — `SP-NAT-EDUCERT`를
`domain`/`도코드` 없이 등록해서, 기존에 있던 "[정보 없음] ...
정부24(gov.kr) 또는 110으로 확인" 정직한 폴백(`_fetchNatText()`,
`entry.domain`이 없으면 자동 진입)을 그대로 타도록 만든 게 이 경우의
정답이었다 — **없는 "제주 지역 사무소"를 지어내지 말 것.**

### 3-3. 판단 순서 요약

```
공공기관 관련 발화
   │
   ├─ 제주(또는 해당 시/도) 안의 구체적 지역 개념이 있는가?
   │     ├─ 예, 자체 행정 사무 ──────────► 지방행정 트리(SP-DO/CITY/EMD)
   │     └─ 예, 국가기관의 지역 지사 ────► JEJU_NATIONAL_TABLE(SP-NAT-*)
   │
   └─ 아니오(전국 단위, 특정 기관·학교마다 다름) ─► domain/도코드 없이
                                                    등록 → 정직한 정보없음
                                                    폴백(지어내지 않음)
```

## 4. 테스트 인프라 지도 (어느 걸 언제 쓰는가)

| 계층 | 하네스 | 비고 |
|---|---|---|
| GWP 1단계 | `routing_ABmention_live_smoketest.py` | `[GWP: id]` 정확 일치 채점 |
| EXPERT 1단계 | 〃 (같은 스크립트) | `[EXPERT: id]` 정확 일치 채점 |
| EXPERT 2단계(professor 세부과목) | `subject_gate_live_smoketest.py` + `get_gate_level.mjs` | 트리를 단계별로 직접 호출 — **재구현 아님, production 함수를 그대로 통과** |
| 공공기관 | `gov24_corpus_live_smoketest.mjs`(정부24 실제 350건) + `gov24_corpus_report.py` | 자동 PASS/FAIL 없음, 사람 대조용 표만 생성 |

새 테스트를 만들기 전에 **이미 비슷한 게 없는지 먼저 찾을 것** —
공공기관 계층은 오늘도 처음부터 새로 설계하려다가, 이미 있었지만
결과 검증만 안 끝나 있던 `gov24_corpus` 인프라를 뒤늦게 찾았다.

## 5. 다음에 라우팅을 건드리는 사람을 위한 체크리스트

1. 실패 사례를 봤을 때 "GWP/EXPERT 표 밖으로 새서 CALL_KINTENT로
   갔어야 하는데 안 갔다"인지, "표 안에서 잘못된 형제를 골랐다"인지
   먼저 구분할 것 — 채점·수정 방법이 완전히 다르다.
2. 공공기관 관련 실패는 trace에 기대한 기관명이 그대로 없다고 바로
   "오탐"이라 단정하지 말 것 — `kregionalgov`/`kgov`로 갔다면 먼저
   `gov-router.js`의 해당 라우팅 트리를 직접 읽고 그 안에서 이미
   처리되는 흐름인지 확인할 것.
3. EXPERT 트리거를 추가/검토할 때는 description이 약속하는 항목과
   `triggers` 배열을 나란히 놓고 대조할 것 — 이게 가장 흔한 갭이다.
4. 새 테스트 하네스를 만들기 전에 `tests/live_smoketest/`에 비슷한
   게 이미 없는지, 있다면 최근 프로덕션 리팩터를 반영하고 있는지부터
   확인할 것.
5. 데이터가 없는 대상(예: 전국 단위라 지역 개념이 안 맞는 것)은
   가짜 지역 데이터를 지어내지 말고, 이미 있는 정직한 "정보 없음"
   폴백 경로를 재사용할 것.
