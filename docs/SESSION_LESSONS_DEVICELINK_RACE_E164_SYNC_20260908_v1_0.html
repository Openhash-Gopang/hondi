SESSION LESSONS — 2026-09-08 인증 디버깅 세션

둘 다 "예전에 고친 문제"처럼 보였지만, 진짜 원인은 둘 다 달랐다

오늘 사용자로부터 "PC 로그인이 폰 승인 확인 단계에서 멈춘다 — 이전에도 여러 번 고친 문제인데 또 재발했다"는 신고를 받고 조사한 결과, 실제 원인은 재발이 아니라 최근(2026-09-07) 추가된 지문 인증 강제화가 기존에 있던 10초 자동 재전송 레이스 컨디션을 훨씬 자주 맞히게 만든 것이었다(PR #117). 이 조사 과정에서 완전히 별개로, 어제(2026-09-07) "완료"로 기록됐던 profiles.e164 평문 제거 마이그레이션의 worker.js 쪽 코드가 실제로는 git 히스토리에 한 번도 병합되지 않은 채 유실되어 있는 것을 우연히 발견했다 — pb_hooks는 SSH로 이미 라이브 배포돼 있어서, 서버와 API가 서로 다른 걸 보고 있는 상태였다. 다행히 두 건 모두 실사용자 피해가 확인되기 전에 잡았다.

대상 저장소 Openhash-Gopang/hondi 관련 PR #117(device-link), e164_hash 동기화 수정(별도 PR) 작성 2026-09-08
Overview
개요

사용자 인증(device-link 로그인)과 관련해 오늘 조사·수정한 두 건은 겉보기엔 전혀 다른 증상이었지만 공통된 교훈을 남긴다: "예전에 고친 버그가 재발한 것 같다"는 신고를 받았을 때, 정말 같은 원인의 재발인지 아니면 그 사이에 추가된 다른 변경이 원인인지를 코드로 직접 확인하지 않고 짐작만으로 넘어가면 안 된다는 것이다.

  • 사건 1 — device-link 자동 재전송 레이스: 증상은 2026-07-28 사고 문서(DEVICE_LINK_FULL_CHAIN_INCIDENT)와 비슷해 보였지만, 그 문서가 다룬 원인들(KV 일관성, 도메인 이슈 등)은 이미 다 해결돼 있었다. 실제 원인은 그 문서에 없던, 훨씬 최근에 생긴 완전히 다른 코드 경로였다.
  • 사건 2 — e164_hash 배포 유실: 어제 세션 문서에는 "worker.js — 자동배포로 이미 반영 확인"이라고 적혀 있었지만, 실제 git 히스토리를 git merge-base --is-ancestor로 직접 확인하니 그 커밋이 main의 조상이 아니었다. 문서에 "완료"라고 적혀 있어도 실제 배포 상태와 다를 수 있다는 것을 보여준 사례.
Case 1
device-link 자동 재전송이 옛 세션 폴링을 버리는 레이스 컨디션
PC가 "스마트폰 알림을 확인해 주세요"에서 멈춤 — 폰은 승인했는데 PC가 못 받음

증상

사용자가 PC에서 로그인을 시도하면 폰으로 device-link 승인 알림(웹푸시)이 오고, 지문 인증을 완료해 승인한다. 그런데 PC 화면은 계속 "스마트폰 알림을 확인해 주세요…"에 머물러 있고, 10초마다 "알림을 다시 보냈습니다"만 반복될 뿐 로그인이 끝나지 않는다.

근본 원인

auth/k-service-auth-client.js의 자동 재전송 로직(devlinkAutoResend())이 10초마다 완전히 새로운 device-link 세션을 만들면서, 옛 세션의 폴링을 그냥 버렸다. 코드로는 이런 모양이었다:

devlinkSessionId = data.sessionId; // 옛 sessionId를 덮어씀 devlinkPollTimer = setInterval(devlinkPollOnce, 2000); // 새 세션만 폴링

서버(handleDeviceLinkInit)는 새 세션을 만들 때 옛 세션을 무효화하지 않는다. 그래서 폰이 옛 세션에 대해 10초 안에 승인을 못 끝내면(정상적으로 늦게 승인을 완료해도), 서버는 그 승인을 정상 처리(state: 'delivered') 하지만 PC는 이미 그 세션을 버리고 새 세션만 보고 있어서 영원히 못 받는다.

이 레이스 자체는 이론적으로 예전부터 있었을 수 있지만, 실제로 자주 터지기 시작한 건 바로 어제(2026-09-07) 추가된 지문 인증 강제화 때문이다. 승인 흐름에 WebAuthn 지문/Face ID 프롬프트라는 실제 사용자 상호작용 단계가 새로 끼어들면서, 승인 완료까지 걸리는 시간이 10초를 넘기기 훨씬 쉬워졌다 — 알림을 확인하고, 지문을 대고, 인식이 될 때까지의 시간을 합치면 사람마다 10초는 금방 넘긴다.

핵심 패턴
한 기능(지문 인증 강제화)이 다른 곳(10초 자동 재전송)에 이미 있던 레이스 컨디션의 "당첨 확률"을 크게 올린 경우다. 두 변경 모두 코드만 보면 각자 정상이라, 커밋 로그를 아무리 들여다봐도 "무엇이 고장났는지"는 안 보인다 — 실제 사용자 흐름의 타이밍을 재구성해야 보인다.

수정

단일 devlinkSessionId를 devlinkSessionIds 배열로 바꿔서, 자동 재전송이 일어나도 세션을 교체하지 않고 배열에 추가만 한다 — 옛 세션과 새 세션을 동시에 병행 폴링해 어느 쪽이든 먼저 승인되는 쪽을 채택한다. 개별 세션이 만료되면 그 세션만 배열에서 제거(다른 세션이 남아있으면 계속 대기), verification_failed (서명 위조·불일치)는 실제 보안 실패이므로 다른 세션 대기 없이 즉시 전체 중단 — 이 구분은 그대로 유지했다.

변경 파일은 auth/k-service-auth-client.js 하나뿐이다. 이 파일은 hondi.net/auth/k-service-auth-client.js로 서빙되며 plan.hondi.net·klaw.hondi.net·mail.hondi.net·hondi.net GDC 대시보드가 전부 공유하므로, 수정 하나로 네 곳 모두에 적용된다.

Case 2
e164_hash 마이그레이션 — worker.js만 배포에서 빠져있었다
pb_hooks(서버)는 이미 e164를 비우고 있는데, worker.js(API)는 여전히 평문 e164로 조회

device-link 조사 도중, _l1FindProfileByE164 같은 함수들의 최근 변경 이력을 훑어보다가 이상한 점을 발견했다: 2026-09-07 세션 문서(SESSION_LESSONS_BIOMETRIC_E164_ DEPLOYMENT_20260907)에는 e164 평문 제거가 "worker.js — 자동배포로 이미 반영 확인"이라고 적혀 있었는데, 실제 worker.js를 열어보니 여전히 옛날 방식 (e164='${e164}' 평문 필터)이었다.

확인 방법 — 기록을 믿지 않고 git으로 직접 검증

git merge-base --is-ancestor 7bde761a HEAD && echo "IS ANCESTOR" || echo "NOT ANCESTOR" # → NOT ANCESTOR

e164 평문 제거 커밋(7bde761a)과 그 백필 커밋이 main의 조상이 아니었다 — 즉 그 작업은 어떤 브랜치에서 완료됐지만, main에 실제로 병합된 적이 없었다(브랜치 정리 과정에서 유실된 것으로 추정). 어제 세션의 "완료 기록"은 작업이 끝난 시점의 상태를 적은 것이었고, 그 이후 뭔가(강제 push, 브랜치 삭제, 리베이스 실수 등)가 그 커밋을 main 히스토리에서 떨어뜨려 놓았을 가능성이 크다.

그런데 같은 마이그레이션의 pb_hooks/main.pb.js 쪽은 SSH로 hanlim 서버에 직접 배포돼 있어서 git과 무관하게 살아있었다. L1 서버에 직접 접속해 확인한 결과:

grep -n "e164_hash\|onRecordBeforeCreateRequest" /opt/gopang/pb_hooks/main.pb.js # → onRecordBeforeCreateRequest가 신규 프로필마다 e164_hash를 채우고 # e.record.set("e164", "")로 평문 e164를 항상 빈 문자열로 저장

즉 서버(pb_hooks)는 이미 새 방식으로 동작 중인데, API(worker.js)는 옛 방식으로 조회하고 있어서 서로 어긋난 상태였다. 이 상태가 계속되면, e164_hash는 정상 생성되는데 e164는 항상 비어있으니 — 새로 전화번호 인증한 사용자는 device-link 로그인·GDC 잔액 조회 등 전화번호 조회가 필요한 기능에서 전부 "등록된 계정 없음"을 만나게 된다.

실제 피해 확인 — DB를 직접 열어봄

가정으로 끝내지 않고 실제 라이브 DB를 조회해 피해 범위를 확정했다:

sqlite3 /opt/gopang/pb/hanlim/data.db \ "SELECT COUNT(*) FROM profiles WHERE e164 = '' AND e164_hash != '';" # → 0건 (아직 실제 피해자 없음) sqlite3 /opt/gopang/pb/hanlim/data.db \ "SELECT COUNT(*) FROM profiles;" # → 1488 sqlite3 /opt/gopang/pb/hanlim/data.db \ "SELECT COUNT(*) FROM profiles WHERE e164_hash != '';" # → 4 (어제 백필분과 일치)

전체 1488개 프로필 중 e164_hash가 채워진 건 어제 백필된 4건뿐이었고, 9/7 08:10(마이그레이션 라이브 시각) 이후 만들어진 레코드는 전부 전화번호 없는 게스트성 테스트 계정(fd00:invtest:*)이었다 — 즉 지뢰는 깔려 있었지만 아직 아무도 밟지 않은 상태였다. 다음 실제 전화번호 가입/재인증 사용자가 첫 피해자가 될 뻔했다.

수정

worker.js 한 파일에서, pb_hooks와 정확히 같은 해시 알고리즘(HMAC-SHA256("e164-lookup:"+e164, PHONE_VERIFY_SECRET))으로 5개 지점을 맞췄다:

함수변경
_e164Hash()신설 — pb_hooks와 동일한 해시 계산 헬퍼
_resolveGuidFromPhoneVerifyTokene164='...' → e164_hash='...'
handleUserGdcBalancee164='...' → e164_hash='...'
_l1FindProfileByE164e164='...' → e164_hash='...'
_phoneMatchKeye164에서 뒷 8자리 재계산 → e164_last8 필드 직접 사용
_findGuidByPhoneMatchKeyLIKE 부분일치+앱단 재확인 2단계 → e164_last8 정확일치 1단계로 단순화

새 환경변수는 필요 없었다 — PHONE_VERIFY_SECRET은 이미 Worker에 설정돼 다른 함수들이 쓰고 있었다.

Method
어떻게 원인을 좁혔는가 — 조사 방법 자체를 남긴다

두 사건 모두 "재발처럼 보이는 신고"에서 시작했다. 코드를 바로 고치기 전에 거친 단계를 순서대로 남긴다 — 다음에 비슷한 신고를 받았을 때 이 순서를 따라가면 된다.

  1. 과거의 같은 계열 사고 문서부터 읽는다. desktop.html "⚠ 주의" 섹션에서 device-link 관련 문서(2026-07-21~28)를 먼저 훑어, 이미 알려진 원인들을 배제 목록에 올려둔다.
  2. 최근 커밋 로그에서 관련 파일의 변경 이력을 훑는다. git log --oneline --all -- <파일>로 최근에 무엇이 바뀌었는지 먼저 본다 — 이번엔 지문 인증 강제화 커밋 (2026-09-07)이 바로 눈에 띄었다.
  3. 클라이언트 코드를 직접 읽어 타이밍을 재구성한다. 로그나 커밋 메시지만으로는 레이스 컨디션이 안 보인다 — devlinkAutoResend()가 세션을 교체하는 코드를 직접 읽고서야 "10초"라는 숫자와 "지문 인증에 걸리는 시간"을 연결지을 수 있었다.
  4. "완료됐다"는 기록을 그대로 믿지 않고 git으로 재확인한다. git merge-base --is-ancestor <커밋> HEAD 한 줄이면 그 커밋이 실제로 브랜치에 들어갔는지 바로 알 수 있다. 문서·인수인계·커밋 메시지는 작성 시점의 의도이지, 지금 이 순간의 실제 상태를 보장하지 않는다.
  5. 배포 경로가 여러 개면 전부 따로 확인한다. 이 저장소는 최소 세 가지 서로 다른 배포 경로를 가진다 — 아래 표 참고. 하나만 보고 "배포됐다"고 판단하면 안 된다.
  6. 가정으로 끝내지 않고 실제 데이터로 피해 범위를 확정한다. "이론상 이런 사용자가 영향받을 것이다"에서 멈추지 않고, 실제 DB를 열어 몇 건이 실제로 영향받았는지 숫자로 확인했다 — 덕분에 "아직 피해자 0명"이라는 걸 확신을 갖고 말할 수 있었다.

세 경로가 완전히 독립적이라, "코드는 main에 있다" ≠ "실제로 배포됐다"이고 "pb_hooks가 배포됐다" ≠ "worker.js도 같이 배포됐다"다. 스키마·데이터 형식을 바꾸는 마이그레이션처럼 pb_hooks와 worker.js가 같은 데이터를 다른 방식으로 다뤄야 하는 작업은, 두 파일을 항상 같은 커밋/같은 PR에 넣고 배포 직후 반드시 둘 다 라이브 상태를 직접 확인해야 한다.

Lessons
일반 교훈 — 다음에 비슷한 인증 버그를 만나면
  • "재발했다"는 신고를 곧이곧대로 "같은 원인"으로 단정하지 말 것. 증상이 같아도 원인은 다를 수 있다 — 특히 그 사이에 무관해 보이는 다른 기능이 추가됐다면, 그 기능이 기존의 잠재적 레이스·타이밍 가정을 깼는지부터 의심할 것.
  • 세션 재시도/재전송 로직을 만들 때는 "교체"가 아니라 "추가"를 기본으로 생각할 것. 재시도가 이전 시도를 완전히 무효화·폐기하면, 이전 시도가 뒤늦게 성공하는 경우를 놓친다. 이번처럼 여러 개를 병행 추적하거나, 최소한 서버 쪽에서 최신 시도만 유효하다고 명시적으로 무효화하는 응답을 줘야 한다.
  • 세션 문서의 "완료" 기록은 작성 시점의 스냅샷일 뿐이다. 이후 브랜치 정리, 강제 push, 리베이스로 그 내용이 조용히 사라질 수 있다. 특히 인증·결제처럼 중요한 변경은 git merge-base --is-ancestor로 실제 main 히스토리에 들어있는지 주기적으로 재확인하는 습관을 들일 것.
  • 같은 데이터를 서로 다른 배포 경로를 가진 두 코드가 같이 다룬다면(pb_hooks ↔ worker.js), 스키마·데이터 형식 변경은 항상 "두 쪽 다 배포됐는지"를 각각 독립적으로 확인할 것. 한쪽만 배포되면 서버·API가 서로 다른 진실을 보게 되고, 증상은 보통 "가끔 안 됨"이 아니라 "특정 시점 이후로 전부 조용히 실패"로 나타난다.
  • 가정으로 결론 내지 말고 라이브 데이터로 확정할 것. "이론상 위험하다"와 "실제로 몇 명이 영향받았다"는 다른 문제다. 후자를 먼저 확인해야 얼마나 급한지, 어떤 순서로 고쳐야 하는지 판단할 수 있다.
