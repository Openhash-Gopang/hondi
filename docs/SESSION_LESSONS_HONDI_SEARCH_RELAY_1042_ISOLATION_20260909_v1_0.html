막힌 이유를 알았으면, 같은 사고를 겪을 다음 사람에게 남긴다

직전 세션에서 "검색을 켜면 사이트 전역이 죽는다"는 트레이드오프 때문에 혼디 검색을 꺼둔 채로 끝냈다. 이번 세션은 그 트레이드오프 자체를 우회할 방법을 찾는 데서 시작해, Cloudflare Error 1042의 정확한 작동 범위를 실제 인프라 실험으로 검증하고, 혼디 검색을 완전히 별개인 전용 Worker(hondi-search-relay)로 분리·배포하는 데까지 끝냈다. 그 과정에서 실제 서비스를 전혀 건드리지 않고 인프라 가설을 검증하는 방법, Windows 환경에서만 재현되는 wrangler 배포 함정, 그리고 코드를 직접 추적해서 아키텍처 가정을 검증하는 습관의 가치를 확인했다. 이 문서는 그 시행착오와 확정된 사실을 정리한다.

Overview
이 문서가 왜 있는가

이 문서는 hondi-search-relay의 사용법이 아니다(그건 그 저장소의 README.md 참고). 여기서 다루는 건 "기능 A를 살리면 왜 기능 B가 죽는지, 그 인과관계의 정확한 범위를 실제 서비스를 위험에 빠뜨리지 않고 확인하는 법"과, 이번에 처음 겪은 Windows 환경 특유의 배포 함정들이다. 전부 이번 세션에서 실제로 발생하고 실제로 해결한 것들이다.

① 핵심 발견 — 이번 세션 최대 성과
1042는 zone이 아니라 Worker 단위로 걸린다

직전 세션(HANDOFF_SITEWIDE_1042_CORS_BLOCK_20260909_v1_0.md)은 "hondi.net zone에 어떤 Worker로든 가는 Route가 존재하면 그 zone 전체의 workers.dev 직접 호출이 막힌다"는 가설과 "그 zone에 Route를 가진 바로 그 Worker만 막힌다"는 가설을 구분하지 못한 채 끝났다. 전자라면 혼디 검색을 분리 배치해도 소용없고, 후자라면 분리만으로 완전히 해결된다 — 결론이 정반대로 갈리는 갈림길이었다.

확정된 사실
1042는 후자다. 그 zone에 Route를 가진 바로 그 Worker의 workers.dev 주소만 막히고, 같은 zone의 다른 Worker는 전혀 영향받지 않는다. 실제 hondi-search-relay Worker를 배포하고 hondi.net/hondi-search Route를 살린 상태에서, 완전히 별개인 hondi-proxy의 workers.dev 호출이 여전히 정상 응답하는 것으로 라이브 재확인했다.

이 발견 덕분에, 직전 세션 결론(A안: 50개 파일 상대경로 전환, 또는 B안: 검색 기능 포기)보다 훨씬 저비용인 D안(전용 Worker 분리)이 가능해졌다 — 기존 50개 파일을 한 줄도 안 건드리고 해결했다.

② 방법론
실제 서비스를 안 건드리고 인프라 가설을 검증하는 법

위 가설을 확인하려고 실제 hondi-search-worker.js를 바로 별도 Worker로 옮겨 배포했다면, 만약 가설이 틀렸을 경우 운영 중인 hondi-proxy를 실제로 위험에 빠뜨릴 뻔했다. 대신 어떤 실제 기능도 없는 "hello world" 수준의 완전히 무관한 테스트 Worker(test-route-probe)를 하나 만들어, 거기에만 hondi.net/probe-test Route를 부여하고 hondi-proxy가 영향받는지만 확인했다.

원칙
"이 변경이 위험한 시스템에 어떤 영향을 주는가"를 확인해야 할 때, 가능하면 위험한 시스템 자체가 아니라 그 조건만 재현하는 최소 실험체를 따로 만들어 검증한다. 실패해도 잃을 게 없고, 결론은 똑같이 확정적이다.
③ 배포 설정
Worker를 분리하면 시크릿도 따로 등록해야 한다

hondi-search-worker.js가 쓰는 DEEPSEEK_API_KEY는 이미 hondi-proxy에 등록돼 있었지만, 그건 그 Worker 안에서만 유효하다. Cloudflare Workers의 시크릿은 계정 단위가 아니라 Worker 단위로 격리되므로, 새 Worker(hondi-search-relay)에도 wrangler secret put DEEPSEEK_API_KEY로 동일한 값을 별도로 등록해야 했다.

주의
시크릿 값 자체는 CLI/대시보드 어디서도 다시 조회할 수 없다 — 기존에 값을 보관해두지 않았다면, 새로 발급해서 원래 Worker 쪽도 같이 갱신해야 한다.
④ 이번 세션 최대 시간 소모 지점
Windows: wrangler deploy는 사용자 프로필 트리 밖에서

C:\Users\<사용자>\Downloads\... 안 어디서 wrangler deploy를 실행하든 매번 다음 에러로 실패했다:

증상원인
A permission error occurred while accessing the file system. Affected path: C:\Users\<사용자>\Application Data Application Data는 AppData\Roaming을 가리키는 구식 호환용 Windows junction. icacls 확인 결과 Everyone:(DENY)(RD)가 걸려있는데, 이건 고장이 아니라 Windows 기본 보안 설정이다. wrangler의 자산 스캔이 프로젝트 폴더가 어디든 사용자 프로필 트리를 거슬러 올라가다 이 junction을 만나면 막힌다.

시도했지만 효과 없었던 것: APPDATA 환경변수 확인(정상이었음), wrangler telemetry disable, 최신 버전(4.97.0 → 4.130.0)으로 업그레이드 — 셋 다 같은 에러가 재현됐다.

해결
프로젝트 폴더를 사용자 프로필 트리 완전히 바깥 (예: C:\temp\...)으로 옮기니 즉시 정상 배포됐다. 이 PC에서는 wrangler deploy를 항상 C:\temp 같은 프로필 밖 경로에서 실행할 것 — 이 저장소나 계정 설정 문제가 아니라 이 PC의 Windows 프로필 구조 문제로 보인다.
⑤ ⑩번 교훈의 재발 사례
curl.exe도 한글 파라미터 인코딩이 깨진다

SESSION_LESSONS_HONDI_SEARCH_ROUTING_DNS_20260909_v1_0.html ⑩번은 Invoke-RestMethod -Body가 한글을 깨뜨리는 사례였는데, 이번엔 curl.exe -d '{"message":"내과 의사"}'도 똑같이 깨졌다(서버 응답이 GitHub Pages 404로 온 것처럼 보여서 처음엔 라우팅 문제로 오인할 뻔했다). PowerShell이 작은따옴표 문자열 리터럴 안의 비-ASCII 문자를 콘솔 코드페이지로 처리하면서 깨지는 것으로 보이며, 도구를 바꿔도(Invoke-RestMethod → curl.exe) 근본 원인이 같으면 증상도 같다.

해결책 — 재확인
한글 등 비-ASCII 문자가 포함된 요청 바디는 파일에 UTF-8(BOM 없음)로 먼저 써서, --data-binary "@파일명"으로 보낸다:

[System.IO.File]::WriteAllText("body.json", $json, [System.Text.UTF8Encoding]::new($false))
curl.exe ... --data-binary "@body.json"
⑥ 아키텍처 확인
추측하지 말고 코드를 직접 추적해서 확인한다

세션 초반, "webapp.html에 페르소나 대화 화면이 별도로 구현돼 있어야 한다"는 요구사항을 받고, 실제로 그런지 코드를 추적하지 않은 채 답했다가 정정을 받았다. handleExpertTag() → _gwpLaunch() → getExpertGwpDef()까지 실제로 따라가 본 뒤에야, desktop.html 검색 경로와 webapp.html 채팅 경로가 둘 다 결국 같은 expert-chat.html 로 수렴한다는 게 코드로 확정됐다.

교훈
"이렇게 동작해야 한다"는 요구사항과 "실제로 이렇게 동작한다"는 사실은 다르다. 소스를 열어 호출 체인을 끝까지 따라가기 전에는 두 파일이 같은 것을 가리키는지, 다른 구현체인지 단정하지 않는다 — 특히 여러 진입점(검색창, 채팅창)이 같은 기능으로 수렴하는 구조에서는 더욱 그렇다.

  • Worker를 분리 배포할 땐 시크릿·바인딩 목록을 원본 코드에서 grep -n "env\."로 전수 확인하고, 시크릿은 별도 등록이 필요함을 전제한다.
  • 이 PC에서 wrangler deploy는 항상 C:\Users\<사용자>\... 프로필 트리 바깥에서 실행한다.
  • 한글이 포함된 요청은 PowerShell 문자열 리터럴로 직접 넘기지 말고, UTF-8 파일로 써서 --data-binary "@파일"로 보낸다 — 도구(Invoke-RestMethod든 curl.exe든) 무관하게 적용.
  • 여러 진입점이 하나의 기능으로 수렴하는 구조는, 문서나 요구사항 만으로 판단하지 말고 호출 체인을 코드로 끝까지 추적해서 확인한다.
