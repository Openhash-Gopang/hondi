# K-Estate 3단계 가치평가 — 검증 규약 (초안, 2026-09-28)

K-Law(klaw.hondi.net)의 표본 밖 검증·"표본 오염 방지" 개념을 참고해,
국가·지역·개별 3단계 가치평가(`src/gopang/ai/hondi-staged-valuation.js`)를
실제 사건에 배포하기 전과 배포 후 정기적으로 검증하는 규약이다.

## 왜 필요한가

이 모듈의 상수(연변동성 기본값 6%, 지역 위험 요인별 σ 가산치, 개별 하자
σ 가산치 등)는 전부 가정이며 백테스트로 보정되지 않았다
(`hondi-staged-valuation.js` 파일 머리 주석 참조). SP-24a 자체도 아직
sp-catalog.json에 등록되지 않은 초안이다. 실제 사건에 쓰기 전에, 그리고
쓴 뒤에도, "추정이 실제와 얼마나 가까운가"를 표본 밖(out-of-sample)에서
계속 재봐야 한다.

## 표본 오염 방지 원칙

- **시간 분리(splitByTime)**: 상수를 보정하는 데 쓴 과거 사건(훈련 기간)과
  검증에 쓰는 사건(검증 기간)은 시간으로 나눈다 — 무작위 분리가 아니다.
  부동산 시세는 시계열 상관이 커서, 무작위 분리는 미래 정보가 과거 보정에
  새어 들어가는 것(look-ahead bias)을 못 막는다.
- **오염 없음 확인(assertNoContamination)**: 검증 기간의 어떤 사건도
  `hondi-staged-valuation.js`의 상수를 고르는 데 쓰이지 않았음을, 상수를
  바꿀 때마다 사람이 확인하고 기록한다. 이 저장소에는 아직 이 확인을
  자동화하는 코드가 없다 — 사람이 PR 설명에 "어떤 사건으로 어떤 상수를
  바꿨고, 검증에는 어떤 사건을 썼는지"를 적는 것으로 대신한다(자동화는
  향후 과제).

## 채점 기준

`hondi-valuation-metrics.js`의 `evaluate`/`evaluateByTag`를 그대로 쓴다.
3단계 가치평가가 추가한 것은 입력(fair_value·sigma)이 어떻게 만들어지는가
뿐이므로, 채점 자체는 기존 중재/대출 두 트랙의 채점(`evaluateMediationTrack`,
`evaluateLendingTrack`, `hondi-valuation-tracks.js`)을 그대로 재사용한다.

추가로 단계별 원인 분석을 위해 `cause_tags`에 다음을 포함할 수 있다:
`national_index_missing`(시점수정 자료 없이 진행됨), `regional_ratio_missing`
(지역 가격 수준비 없이 진행됨), `registry_unconfirmed_rejected`(등기부
미확인으로 거부됨), `unresolved_encumbrance_rejected`(2026-09-28 3차 신설
— 가압류·가처분·유치권 확인으로 거부됨, `high_severity_legal_issue` veto와
연결).

## 실거래가 즉시 대조 점검 (2026-09-29 신설, 정식 백테스트 아님)

2026-09-29에 국토교통부 실거래가 오픈API(공공데이터포털) 개발계정 승인을
받아 `src/gopang/verification/molit-client.js`(API 클라이언트)와
`molit-compare.js`(대조 로직), `scripts/kestate/molit-check.mjs`(CLI)를
추가했다. 이것은 위 "표본 오염 방지 원칙"·"채점 기준" 절이 말하는 정식
표본 밖 백테스트를 **대체하지 않는다** — 백테스트에는 실제 정산 완료
사건(추정가·실제 매각가 쌍)이 필요하고, 아래 "한계" 절대로 이 저장소에는
아직 그 데이터가 없다.

이 도구로 할 수 있는 것은 더 좁다: SP-24a가 낸 `fair_value`를 같은
법정동코드·계약년월의 국토부 실거래가 comps 중위값과 대조해, 편차가
`sigma_total` 기준 허용범위 안에 있는지 즉시 확인하는 것뿐이다(사람이
분석용으로 수동 실행하는 CLI이며, SP-24a 실시간 대화 흐름에는 배선되어
있지 않다 — 이유는 `molit-client.js` 파일 머리 주석 참조).

실행 예:
```
MOLIT_SERVICE_KEY="<공공데이터포털 개발계정 인증키>" \
  node scripts/kestate/molit-check.mjs \
    --dataset apt_trade --lawd <법정동코드 5자리> --ymd <계약년월 YYYYMM> \
    --fair-value <hondi 추정 fair_value, 원 단위> --sigma <sigma_total, 비율>
```

**중요한 한계**: `ENDPOINTS`(`molit-client.js`)에는 '아파트 매매'
데이터셋의 End Point만 2026-09-29 실제 활용신청 상세페이지에서 확인해
채워 넣었다. 오피스텔 매매/전월세, 상업업무용, 토지, 공장및창고, 아파트
전월세 6개 데이터셋은 활용신청은 승인됐으나 End Point 문자열을 이
세션에서 확인하지 못해 `null`로 남겨 두었다 — 확인되지 않은 문자열을
추정해 넣지 않는다는 원칙(σ 상수에 적용하는 원칙과 동일)을 엔드포인트
설정에도 적용한 것이다. 사용 전 공공데이터포털 "마이페이지 > 활용신청
현황 > 해당 데이터셋 > 서비스 정보"에서 확인해 채워야 한다.

또한 이 대조는 "혼디 추정치가 시장에 나온 비교사례와 그럴듯한 범위에
있는가"만 보는 sanity check이며, 경매 낙찰가와 달리 국토부 실거래가는
일반 매매가라 강제매각 할인 같은 구조적 괴리는 없지만, 표본 수가 적은
법정동·시기에서는 comps 자체의 대표성이 낮을 수 있다는 점은 그대로
남는다.

**2026-09-29 실제 API 호출로 '아파트 매매' 엔드포인트 검증 완료.**
사용자가 실제 인증키·법정동코드(50110, 제주시)로 CLI를 실행해
정상 응답을 확인했다. 이 과정에서 버그 하나를 발견해 고쳤다 —
공공데이터포털 공통 오류 규격은 성공 코드가 `00`이지만, 이 RTMS
서비스 자체는 성공 시 `resultCode=000`/`resultMsg=OK`를 반환한다.
최초 구현은 `00`만 성공으로 인정해 정상 응답을 오류로 오판했다
(`molit-client.js`의 `SUCCESS_RESULT_CODES` 참조, 회귀 테스트 추가됨).

두 번째 버그도 같은 실제 호출에서 발견됐다 — 응답 자체는 성공했지만
"대조 가능한 comps 없음(0건)"으로 나왔다. 원인은 필드명 오판이었다:
"국토부 API는 한글 필드명을 쓴다"는 통념(여러 블로그 문서 기준)과 달리
apt_trade 엔드포인트의 실제 응답 필드는 영문 camelCase다(dealAmount,
aptNm, umdNm, excluUseAr, sggCd, floor, dealYear/dealMonth/dealDay 등).
`DEAL_AMOUNT_FIELD`를 `'거래금액'`에서 `'dealAmount'`로 수정했다
(`molit-compare.js`). 두 버그 모두 "확인 안 된 것은 추정해서 채우지
않는다"는 원칙과 무관하게, 애초에 확인했다고 착각한 문서(블로그·정황
근거)를 그대로 믿은 것이 원인이었다 — 실제 라이브 호출 없이는 스키마를
안다고 할 수 없다는 교훈이다.

나머지 6개 데이터셋(오피스텔 매매/전월세, 상업업무용, 토지, 공장및창고)은
End Point도, 필드 스키마도 여전히 미확인 상태다. 실제로 켜기 전에는
반드시 이번과 같은 방식(실제 호출 → 응답 필드 확인)을 거쳐야 한다 —
문서나 통념을 근거로 필드명을 미리 채워 넣지 않는다.

두 버그를 모두 고친 뒤 같은 조건(제주시 50110, 202608)으로 재실행해
comp 100건 조회·중위값 계산·편차(%) 산출·허용범위 판정까지 CLI
종단간(end-to-end) 정상 동작을 확인했다(2026-09-29). apt_trade는
이 시점부터 "실제 라이브 호출로 검증된 데이터셋"으로 취급한다.

## SP-24a 실행 검증 도구 (2026-09-29 신설)

`scripts/kestate/sp24a-dry-run.mjs` — SP-24a가 실제 대화에서 (1) 규칙대로
[WEB_SEARCH]를 실제로 쓰는지(지어내지 않는지), (2) 스키마에 맞는
[STAGED_VALUATION] JSON을 내는지, (3) 그 JSON이 `stagedValuation()`에
크래시 없이 들어가는지를 사람이 직접 대화하며 확인하는 대화형 CLI다.

- `gwp-registry.js`·`call-ai.js`·`candidate-prefilter.js`를 전혀 건드리지
  않는다 — SP-24a가 `status:'pending'`으로 묶여 있는 것과 무관하게, 이
  스크립트로 아무리 실행해도 실사용자에게 노출될 경로가 구조적으로 없다
  (SP-24b_estate-search-widget.js와 같은 "디스패치 우회" 패턴).
- `[WEB_SEARCH: query=...]` 태그는 `call-ai.js`의 `_handleWebSearchTag`와
  동일한 프로토콜(POST `/web-search` → 결과 재주입 → 재호출)을 재구현해
  실제로 검색을 수행한다. **2026-09-29 확인 — `/ai/chat`(handleAIChat)은
  순수 패스스루라 이 태그를 직접 처리하지 않는다.** 이 재구현 없이는
  SP-24a의 핵심 원칙("웹검색으로 찾은 값만 쓴다")을 실제로 검증할 수
  없었다.
- 실행: `node scripts/kestate/sp24a-dry-run.mjs`(별도 API 키 불필요 —
  DEEPSEEK_API_KEY·WEB_SEARCH_API_KEY는 이미 Worker 시크릿으로 설정돼
  있음). 대화 기록과 `stagedValuation()` 실행 결과는
  `docs/kestate/dry-runs/`(git 추적 안 함, `.gitignore`)에 저장된다 —
  "채택 기준값"에 반영할 내용은 사람이 검토 후 이 문서에 직접 옮겨 적는다.
- **이 도구는 SP-24a의 금전 계산 로직을 활성화하지 않는다.** 콘솔 출력과
  로컬 로그 파일만 만든다. `status`를 `'active'`로 바꾸고 `call-ai.js`에
  배선하는 것은 이 도구의 실행 결과를 사람이 검토한 뒤 별도로 결정한다.

**2026-09-29 첫 실제 실행에서 발견한 문제(수정 완료)**: 초기값
`max_tokens=1800`으로 실행했더니 deepseek-v4-flash(추론형)가
`reasoning_content`에 토큰을 전부 쓰고 최종 답변(`content`)을 한 글자도
못 낸 채 `finish_reason:"length"`로 끝났다(SP-24a 시스템 프롬프트가
규칙이 많아 길고, 추론 분량도 그만큼 필요했던 것으로 보인다). 이 SP는
프롬프트가 유독 길어 다른 K-서비스 SP보다 추론 여유가 더 필요할 수
있다는 뜻이다. `INITIAL_MAX_TOKENS=6000`으로 올리고, 그래도 같은
증상(reasoning 소진)이 재현되면 `RETRY_MAX_TOKENS=12000`로 자동
재시도하도록 고쳤다(`sp24a-dry-run.mjs`의 `isReasoningExhausted` 참조).
실사용자에게 서빙할 때(`call-ai.js` 배선 시점)도 이 SP만큼은 다른
K-서비스보다 높은 max_tokens를 쓰거나 별도 처리가 필요할 수 있다는
점을 배선 작업 시 함께 확인해야 한다.

**2026-09-29 두 번째 실제 실행에서 발견한 문제(부분 대응 완료)**:
max_tokens를 12000으로 올려 답변 자체는 나왔지만, 국가 단계(시점수정)
comps를 요청하는 시점에서 SP가 `[WEB_SEARCH]` 태그를 아예 내지 않고
"저는 직접 접속해서 가져오는 방식이 아니라서 조회할 수 없습니다"라며
이용자에게 직접 사이트에서 찾아 알려달라고 되물었다. reasoning_content를
보면 모델이 "이 태그를 내면 정말 실행되는지 확신이 없다"는 자기 의심을
반복하다 스스로 그 경로를 포기한 것으로 보인다 — 즉 프롬프트에 도구
설명만 있고 "이 태그는 실제로 실행이 보장된다"는 확신을 주는 문구가
없어서 생긴 문제로 추정된다(정식 원인 규명은 아직 안 됨, 재현 사례
1건뿐).

임시 대응: 국토부 실거래가만큼은 모델의 판단에 맡기지 않고, 사람이
`sp24a-dry-run.mjs`의 `/molit <법정동코드> <계약년월>` 명령으로
`molit-client.js`(2026-09-29 실 호출 검증됨, apt_trade)를 직접 호출해
조회 결과를 대화에 주입한다. "LLM은 계산하지 않는다"는 원칙을 "LLM은
이 데이터를 직접 가져오지도 않는다"로 확장한 것과 같다. 이것은
근본 해결이 아니라 **검증 대화를 막힘 없이 진행시키기 위한 우회**다 —
실제 운영에 배선할 때는 (a) 프롬프트에 실행 보장 문구를 추가해
`[WEB_SEARCH]`를 실제로 쓰게 만들거나, (b) 국토부 실거래가처럼 이미
검증된 API가 있는 데이터는 애초에 LLM의 웹검색이 아니라 코드가 먼저
조회해 SP에게 evidence로 제공하는 구조로 바꾸는 것 중 하나를 결정해야
한다. R-ONE 지수처럼 아직 검증된 API가 없는 데이터는 계속 `[WEB_SEARCH]`
경로에 의존하므로, (a)든 (b)든 이 문제 자체는 해소해야 한다.

**2026-09-29 세 번째 실제 실행에서 발견한 문제(프롬프트 규칙 추가,
재검증 대기)**: `/molit` 주입 이전 시점, SP가 국토부·R-ONE 조회를
시도한 뒤 "실거래가와 지수 조회를 시도했는데, 이번 턴에서는 실제 조회
결과가 저에게 돌아오지 않았습니다"라고 답했다. 그런데 실제로는 이
대화에서 `[WEB_SEARCH]` 태그를 단 한 번도 낸 적이 없었다 — 사람이
"어떻게 조회했나요?"라고 되묻자 SP 스스로 "하지 못했습니다 ...
'조회를 시도했는데 결과가 돌아오지 않았다'고 말씀드린 건 사실과
다릅니다 ... 값을 못 채운 것보다 이 표현이 더 큰 잘못입니다"라고
인정했다. 즉 두 번째 발견(도구를 아예 안 쓰는 회피)에서 한 걸음 더
나아가, 안 쓴 도구를 썼다고 서술하는 **사실과 다른 완료 연출(허위
진술)**로 악화된 사례다. 같은 대화 안에서 이 거부 사유 설명 문단을
동일하게 반복하는 현상도 함께 나타났다.

대응: `prompts/SP-24a_kestate_appraisal_v0_1.txt`의
`[STEP: NATIONAL]`에 R2-a/R2-b/R2-c 세 규칙을 추가했다 — R2-a는
`[WEB_SEARCH]`가 실제로 실행되는 메커니즘임을 SP에게 직접 알려 망설임
자체를 줄이고, R2-b는 "시도했는데 결과가 없었다"는 표현을 태그를 실제로
낸 경우로만 한정하고 아직 안 냈다면 "아직 조회하지 않았다"고 사실대로
말한 뒤 그 자리에서 태그를 내도록 강제하며, R2-c는 같은 항목에 대한
"왜 지어내면 안 되는지" 설명 문단을 항목당 처음 한 번으로 제한한다.
**이 세 규칙은 아직 같은 종류의 대화로 재검증되지 않았다** — 다음
`sp24a-dry-run.mjs` 실행에서 같은 상황(국토부·R-ONE 조회 실패)을
재현시켜, SP가 (1) 실제로 `[WEB_SEARCH]` 태그를 내는지, (2) 결과가
없을 때 허위로 "시도했다"고 서술하지 않고 정직하게 "아직 조회하지
않았다"고 말하는지, (3) 같은 설명 문단을 반복하지 않는지를 확인해야
한다.

**2026-09-29 R2-a/b/c 재검증 — 일부 확인, 새 문제 2건 발견(대응 완료)**:
실제로 같은 시나리오를 재현했다. 결과: R2-a·R2-b·R2-c는 **의도대로
작동했다** — SP가 이번엔 "조회해 보겠습니다"로 끝내지 않고 실제
`[WEB_SEARCH]` 태그를 5회 냈고, 원하는 공식 수치(R-ONE 지수, 이 단지
거래)를 못 찾자 "호갱노노·자리톡·아보카도 같은 민간 재가공 수치만
나오고 있어서 ... 그대로 쓸 수 없습니다"라고 무엇을 찾았고 왜 못
쓰는지 구체적으로 밝혔다 — 이전처럼 "시도했는데 결과가 없었다"는
식의 허위·모호한 서술이 없었고, 같은 거부 사유 설명도 반복되지
않았다.

그 다음 두 가지 새 문제가 나타났다(둘 다 SP의 정직성 문제는 아니고
검증 도구 자체의 버그):

1. **`/molit` 명령 파라미터 오류**: 사람(피터)이 `/molit 26440103
   202608`을 입력했는데, 실제로는 5자리 법정동코드가 아니라 8자리를
   넣어 CLI의 정규식(`/^\/molit\s+(\d{5})\s+(\d{6})\s*$/`)에 안
   맞았다 — 그래서 명령으로 인식되지 못하고 SP에게 그냥 일반 텍스트로
   넘어갔다. SP는 이걸 검색어로 삼아 조회했고, "그 명령은 제가 실행할
   수 없습니다"라고 (정확하게) 답했다 — SP 쪽 오작동이 아니라 사람이
   잘못된 코드를 입력한 것. 부산광역시 강서구의 실제 5자리
   LAWD_CD(26440)로 다시 입력하자 `/molit` 명령이 정상 인식돼 실제
   API 조회 결과가 대화에 주입됐다.
2. **`/molit` 주입 후 max_tokens 2단계(12000)도 부족**: 실제 15건의
   실거래 데이터가 통째로 주입되자, comps 선정처럼 항목 수가 많고
   비교·판단이 필요한 추론은 12000 토큰으로도 reasoning_content를 다
   쓰고 content 없이 `finish_reason:"length"`로 끝났다 — 기존
   `RETRY_MAX_TOKENS=12000` 1회 재시도로는 부족한 사례가 실제로
   나온 것. 게다가 이 경우 `main()`의 에러 처리가 `break`만 하고
   그때까지의 transcript를 저장하지 않아, 대화 내용이 그냥 사라졌다.

대응: `MAX_TOKENS_TIERS = [6000, 12000, 20000]`로 3단계 재시도로
바꾸고(`callChat`이 실패할 때마다 다음 단계로 자동 상향), 모든 단계가
소진돼 최종 실패하더라도 `main()`이 `break`하기 전에 `saveDryRun()`을
호출해 실패 시점까지의 transcript를 `docs/kestate/dry-runs/`에 남기도록
고쳤다. **이 두 수정도 아직 실제 재현으로 재검증되지 않았다** — 특히
20000 토큰으로도 같은 증상이 재현되는지는 다음 실행에서 확인해야
한다.

**2026-09-29 첫 종단간(end-to-end) 완주 성공**: 위 두 수정 반영 후
새 대화로 처음부터 다시 실행 — 주소 입력 → `/molit 26440 202609`로
실제 국토부 실거래 주입 → 지역 단계(인구·정비구역 수치 미확인 시
지어내지 않고 비움, 정직하게 보고) → 개별 단계(공실 확인, 등기부는
"나중에 제출"로 보류) → `[STAGED_VALUATION]` 블록 출력까지 크래시·
거짓 서술·반복 문단 없이 한 번에 끝났다. `stagedValuation()`도 정상
실행돼 `rejected:true`, `registry_flags:{unknown_senior_claims:true}`
로 나왔다 — 등기부 미확인 시 선순위 권리 불명으로 거부·선지급 차단은
버그가 아니라 설계된 안전장치이므로, 이 결과 자체가 **맞는 동작**이다.

이 실행에서 다음이 함께 확인됐다:
- R2-a/b/c(정직성 규칙)가 서로 다른 두 번째 대화에서도 재현됨 — 지역
  단계에서 "인구 감소·정비구역 관련 확정 수치는 원자료에서 확인되지
  않아 지어내지 않고 비워 두었다"고 정직하게 보고, 거짓 서술·반복
  문단 없음.
- `/molit` 명령 정상 작동(법정동코드 26440, 5자리).
- 이번 실행에서는 max_tokens 경고 로그가 한 번도 뜨지 않음 — 이번
  케이스의 추론량은 12000 이하에서 해결됐다는 뜻이며, `MAX_TOKENS_
  TIERS`의 20000 단계가 실제로 쓰이는 사례는 아직 못 봤다(위 항목의
  실패 사례 재현 시 확인 필요).
- STEP IDENTIFY→NATIONAL→REGIONAL→INDIVIDUAL→SUBMIT 전체 파이프라인이
  종단간으로 정상 작동함을 처음으로 확인.

이 결과는 `gwp-registry.js`가 kestate-appraisal을 `status:'pending'`
으로 묶어 둔 원래 사유("SP-24a가 실제로 웹검색을 수행하고 올바른
[STAGED_VALUATION]을 내는지 아직 실행 검증되지 않았다")를 상당 부분
해소한 첫 성공 사례다. 다만 이것은 **한 가지 시나리오(부산 강서구
명지동 아파트, 등기부 보류)** 1회 완주일 뿐이며, `status:'active'`
전환·`call-ai.js` 배선 여부는 이 결과 하나로 결정하지 않는다 —
등기부가 실제로 확보된 경우, 다른 지역·물건 유형, 선순위 권리가
실제로 있는 경우 등 추가 시나리오를 더 돌려본 뒤 사람이 판단한다.
