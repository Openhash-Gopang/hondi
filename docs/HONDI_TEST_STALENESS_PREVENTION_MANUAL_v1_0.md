# 나비 테스트 매뉴얼 — 설계 변경과 테스트 노후화 방지 (v1.0)

**작성 배경**: 2026-08-30, 기존 오프라인 유닛테스트 77개 전체를 처음으로
한 번에 실행해 현황을 파악하는 세션을 진행했다. 시작 시점엔 상당수가
"신호 없음"(실행조차 안 됨) 상태였고, 실행되는 것 중에서도 다수가
실패하고 있었다. 원인을 하나씩 추적한 결과 크게 두 갈래로 갈렸다:

1. **실제 프로덕션 버그** (7건 — 아래 §1에 정리)
2. **테스트가 이후의 의도적인 설계 변경을 못 따라간 것** (다수 — 아래
   §2~§3에 정리, 이 문서의 핵심)

이 문서는 (2)의 패턴이 왜 반복됐는지 분석하고, 앞으로 같은 일이 또
생기지 않도록 **설계를 바꾸는 시점에 지켜야 할 절차**를 정리한다.
이번 세션에서 고친 버그 자체의 기술적 세부사항은 각 PR 설명(#692~#717)에
있으므로 여기서는 반복하지 않고, **재발 방지에 필요한 일반 원칙**에
집중한다.

실행해봐서 잡혔다.** 코드 리뷰만으로는 못 잡았을 가능성이 높다.

## §2. 테스트가 못 따라간 설계 변경 — 실제 사례 전부 (패턴별 분류)

같은 근본 원인("설계는 바뀌었는데 테스트는 안 바뀜")이 최소 7가지
서로 다른 **변경 유형**으로 나타났다. 유형별로 재발 방지 규칙을 뒤에
붙인다.

### 2-1. 식별자 개명(rename) — 옛 이름이 코드베이스 곳곳에 잔존

- `jeju_do`/`jeju_national` → `gov_do`/`gov_national` (2026-07-21).
  개명 이유 자체는 훌륭했다("제주 전용이 아니라 전국 공통 지방행정
  트리"). 그런데 `sp-intercall.test.mjs`는 옛 이름을 **agency 필드와
  sp_call.target 필드 양쪽에 7군데** 그대로 쓰고 있었고, `GOV_AGENCIES`
  Set과 `SP_DELEGATION_REGISTRY`에서 그 이름이 사라진 걸 몰라 매 호출이
  즉시 거부되거나 위임이 조용히 실패하고 있었다.

### 2-2. 평면 구조 → 계층 구조로 재편

- `professor-math`가 2026-08-10 개편으로 `professor` → `professor-mathphys`
  → `professor-math-series` → `professor-math`, 3단계 깊이로 재소속.
  `subject-gate.test.mjs`는 "한 번의 LLM 호출로 바로 리프까지 간다"는
  개편 전 가정을 그대로 쓴 고정 mock 응답 하나만 재사용하고 있었다.

### 2-3. 데이터 저장 인터페이스 변경 (평문 → 해시)

- `_writeOwnerPdvRecord`가 2026-08-20에 what/why/detail을 프로즈
  원문에서 SHA-256 해시로만 받도록 바뀜(원문 미저장 원칙). 호출부 하나
  (`handleOwnerPdvReport`)는 같이 갱신됐지만 다른 호출부
  (`_interceptAgyVaultStore`)는 빠졌고, 테스트도 옛 평문 비교 assertion
  그대로였다.

### 2-4. 정책/설정 값 변경 (요금제·환율·안전망 스위치)

- `EXCHANGE_RATE_KRW_PER_GDC`가 "베타 테스트 기간 한정"으로 100→1로
  변경(2026-07-27). 테스트는 옛 1:1000 비율을 그대로 기대.
- K-Law "전문직 티어(all_services_free)"가 2026-08-14 요금제 재설계로
  완전히 삭제(시민 990원 단일 요금제로 통합). 테스트는 그 티어가 여전히
  존재한다고 가정.
- `FREE_QUOTA_ENFORCEMENT_ENABLED`가 2026-07-29에 인프라 불안정으로
  임시 `false`로 전환된 뒤, "안정화되면 되돌릴 것"이라는 주석만 남긴
  채 방치(§1의 실제 버그 사례와 겹침 — 이 경우는 코드 자체가 잘못된
  임시상태로 남아있던 것).

### 2-5. 안전장치 추가가 특정 경로에서만 적용되고 다른 경로는 누락

- 2026-08-08 "정적 데이터 없는 도는 위험한 실시간 검색(LAZY) 대신
  정직한 '정보없음' 안내로 폴백"이라는 안전조치가 국가기관 라우팅에
  추가됐는데, 이 조치는 **LLM 분류 경로(classifyFn 있음)에만** 적용되고
  **키워드 전용 경로(classifyFn 없음)에는** 안 들어가 있었다. 오프라인
  테스트는 항상 classifyFn 없이 실행되므로, 이미 고쳤다고 생각한 버그가
  테스트에서는 계속 실패로 남아있었다.
  - 같은 유형이 하나 더 있었다: "국가기관↔지방행정 계층충돌 통합판단"
    안전망도 classifyFn 있을 때만 동작하고, 없으면 옛 버그(잘못된
    기관으로 즉시 확정)가 그대로 재현되고 있었다.

### 2-6. "죽은 코드"로 판단해 통째로 제거

- same-thread 전문가 세션 서브시스템(`startExpertSession` 등)이
  2026-07-03부터 아무도 안 쓰는 죽은 코드임이 2026-08-06 감사로 확인돼
  `_archive/`로 이관됐다. 이건 정리 자체는 잘한 일이지만, 그 기능만
  전담으로 검증하던 테스트 블록(`describe('B3-2 ...')`)이 통째로 안
  지워지고 남아, 존재하지도 않는 함수를 계속 호출하며 실패하고 있었다.

### 2-7. 테스트 자신의 정적 분석 방식이 소스 코드 형식 변화에 못 버팀

- `national-s7-keyword-consistency.test.mjs`가 `gov-router.js` 소스를
  정규식으로 파싱해 키워드 사전을 재구성하는데, 그 정규식이 줄 끝
  인라인 주석(`],  // ...`)을 못 견뎌 조용히 빈 배열로 오인.
- `phase12_gov_importance_scoring.test.mjs`의 "조립 순서" 검증도
  `ctxBlock` 조립 코드 한 줄을 정규식으로 통째로 매칭하는데, 새 블록
  (`paHandoffBlock`)이 하나 추가될 때마다 이 정규식이 뒤처졌다(같은
  파일 안에 이미 "예전에도 이런 일이 있었다"는 주석이 남아있었다 —
  즉 반복된 패턴이었다).

## §3. 왜 반복되는가 — 근본 원인

위 7가지 사례 전부에 공통된 구조가 하나 있다:

> **"코드를 바꾼 사람은 그 순간엔 관련 테스트를 알고 있었을 가능성이
> 높지만(주석에 배경 설명이 상세히 남아있는 걸 보면), 정작 그 테스트를
> 실행해서 확인하지는 않았다."**

증거: 이번에 고친 항목 거의 전부가 **친절하고 상세한 배경 설명 주석**을
이미 갖고 있었다("2026-08-08 안전조치", "2026-07-21 개명", "2026-08-14
요금제 재설계" 등). 즉 **기록은 잘 돼 있었는데 검증까지 이어지지
않았다.** 이건 개인의 실수라기보다, "코드를 고치면서 관련 테스트
전부를 실행해보는 게 습관/자동화로 강제되지 않았다"는 프로세스 공백이다.

또 하나의 구조적 원인: **77개 테스트 파일 중 다수가 오랫동안 한 번도
전체 실행되지 않았다.** `package.json`의 `"type": "commonjs"` 오설정
하나 때문에 25개 파일이 아예 실행이 안 되는 상태로 방치돼 있었고,
`node --experimental-test-module-mocks` 플래그가 필요한 파일 8개도
플래그 없이 실행하면 크래시로 보여 마치 깨진 것처럼 보였다(실제론
멀쩡). **깨진 걸로 착각한 테스트는 아무도 안 돌려보고, 안 돌려본
테스트는 계속 노후화된다** — 이 악순환이 상당수 실패를 누적시켰다.

## §4. 재발 방지 체크리스트 — 다음에 이런 변경을 할 때

### 체크리스트 A — 식별자를 개명(rename)할 때
1. `grep -rn '<옛이름>'` 을 저장소 전체(`src/`, `worker.js`, `tests/`,
   `docs/`)에 돌려 **테스트 파일에 남은 옛 이름까지 전부** 찾는다.
   코드만 grep하고 테스트를 빼먹는 실수가 이번 세션의 가장 큰
   재작업 원인이었다.
2. 개명한 이름이 여러 레지스트리/화이트리스트(`GOV_AGENCIES`,
   `SP_DELEGATION_REGISTRY` 같은)에 동시에 등록돼야 하는 구조라면,
   **모든 레지스트리에서 옛 이름이 지워지고 새 이름이 추가됐는지**
   각각 확인한다. 하나만 바꾸고 다른 하나를 빠뜨리면 "미등록"으로
   오인되는 조용한 실패가 난다.

### 체크리스트 B — 평면 구조를 계층 구조로 바꿀 때
1. 그 구조를 가정하고 "한 번에 최종 리프까지 도달"하는 식으로 짜인
   테스트 mock이 있는지 찾는다(고정된 단일 응답을 반환하는 mock은
   특히 의심).
2. 계층이 깊어지면 mock도 **단계별 순차 응답**으로 바꿔야 한다 —
   실제 로직이 한 단계씩 내려가며 매번 새로 판단을 요청하는 구조라면,
   테스트의 mock도 그 반복 횟수만큼 다른 값을 순서대로 내놓아야 한다.

### 체크리스트 C — 데이터 인터페이스를 바꿀 때 (예: 평문 → 해시)
1. 그 함수를 호출하는 **모든 지점**을 grep으로 찾는다. "이 함수를
   호출하는 곳은 A뿐이다"라는 가정은 검증 없이 믿지 않는다 — 이번
   세션에서 실제로 호출부 하나를 빠뜨린 게 65개+ 서비스의 기록 기능을
   통째로 죽였다.
2. 인터페이스 변경 후 실패해야 정상인 옛 방식의 테스트(평문 비교 등)를
   찾아 **의도적으로 새 인터페이스에 맞게 갱신**한다. 이때 "실패를
   숨기려고 assertion을 느슨하게 만드는 것"과 "새 설계에 맞게 정확히
   갱신하는 것"을 구분한다 — 후자만 허용된다.

### 체크리스트 D — 정책/설정 값을 바꿀 때 (요금제·환율·한도 등)
1. 그 상수/정책을 하드코딩해 검증하는 테스트를 grep으로 찾는다
   (`* 1000`, `all_services_free`, `990` 같은 매직넘버 검색).
2. 값이 "임시" 성격이면(예: "베타 테스트 기간 한정") **주석에 되돌릴
   조건을 명시**하고, 그 조건이 충족되면 **누가 다시 확인할지**까지
   정해둔다. 이번 세션의 `FREE_QUOTA_ENFORCEMENT_ENABLED`처럼 "안정화되면
   되돌릴 것"이라고만 적어두고 아무도 다시 안 보는 상태가 실제 사고
   위험으로 남아있었다(베타 시작 이틀 전에야 발견).

### 체크리스트 E — 안전장치/폴백 로직을 추가할 때
1. 이 안전장치가 **모든 진입 경로**(LLM 분류 경로, 키워드 전용 경로,
   API 직접 호출 경로 등)에 다 적용되는지 명시적으로 확인한다.
   "classifyFn이 있을 때만"처럼 조건부로 게이트를 거는 안전장치는
   특히 위험하다 — 오프라인 테스트가 항상 classifyFn 없이 도는 구조라면,
   그 게이트 뒤의 안전장치는 **테스트로 영원히 검증이 안 된다.**
2. 가능하면 안전장치 로직 자체가 LLM에 의존하지 않는(순수 결정론적)
   부분과, LLM 통합판단이 필요한 부분을 분리해서, 최소한 결정론적
   부분만이라도 모든 경로에서 항상 동작하게 만든다.

### 체크리스트 F — 기능을 "죽은 코드"로 판단해 제거할 때
1. 그 기능만 전담으로 검증하던 테스트 파일/블록을 찾아 **함께 삭제**
   하거나, 향후 재도입 시 참고할 수 있도록 명확히 표시해서 archive와
   같이 이동한다. 코드만 지우고 테스트를 남기면, 그 테스트는 영원히
   실패 상태로 남아 "진짜 버그가 있나?"를 확인하는 시간을 계속
   낭비시킨다.
2. 반대로 죽은 코드로 보였지만 실은 특정 조건에서만 호출되는 경우일
   수도 있으니, 삭제 전 grep으로 호출부가 정말 0개인지 재차 확인한다
   (이번 세션의 `startExpertSession`은 실제로 0개였음이 2026-08-06
   감사로 재확인된 사례).

### 체크리스트 G — 테스트 자신이 소스 코드를 정규식으로 파싱할 때
1. 이런 테스트는 **소스 코드 형식이 조금만 바뀌어도(주석 추가, 줄바꿈
   변경 등) 깨지기 쉽다.** 가능하면 정규식 매칭 대신 실제 함수를
   import해서 호출한 결과를 검증하는 방식으로 바꾸는 걸 고려한다.
2. 정규식 방식을 유지해야 한다면, 정규식 자체에 "이 패턴은 소스 형식
   변화에 취약함 — 실패 시 코드가 아니라 이 정규식부터 의심할 것"이라는
   주석을 남긴다.

## §5. 테스트 실행 인프라 — 반드시 알아야 할 것

이번 세션에서 "코드는 멀쩡한데 테스트가 깨진 것처럼 보였던" 원인의
상당수가 여기 있었다.

1. **`package.json`의 `"type"` 필드는 반드시 `"module"`이어야 한다.**
   `src/` 전체가 ESM(`import`/`export`)만 쓰는데 이 값이 `"commonjs"`로
   잘못 설정돼 있으면, `node file.js`로 실행 시 `Cannot use import
   statement outside a module` 크래시가 나며 **25개 파일이 통째로
   실행 자체가 안 됐다.** 이미 고쳤지만(#690대), 앞으로 이 값을 다시
   바꿀 일은 없어야 한다.

2. **`mock.module()`을 쓰는 테스트는 `--experimental-test-module-mocks`
   플래그가 반드시 필요하다.** 플래그 없이 돌리면
   `TypeError: mock.module is not a function`으로 크래시하는데, 이건
   테스트가 깨진 게 아니라 **잘못된 방법으로 실행한 것뿐**이다. 해당
   파일들은 이미 자기 헤더에 정확한 실행 명령어를 적어뒀다:
   ```
   // 실행: node --experimental-test-module-mocks --test src/tests/...
   ```
   **테스트 파일을 실행하기 전에 반드시 그 파일 맨 위 주석에 적힌
   실행 명령어를 확인한다.** 임의로 `node --test`나 `node file.js`로
   돌리고 결과를 신뢰하지 않는다.

3. **테스트 파일마다 결과 출력 형식이 다르다.** Node 내장
   `node:test`(TAP 형식, `# pass`/`# fail`)를 쓰는 파일이 있고, 자체
   `✅`/`❌` 마커 + `총 N건 중 M건 통과` 같은 커스텀 출력을 쓰는 파일도
   있다. 전체 스캔 스크립트를 짤 때 **두 형식을 다 인식하도록** 만들지
   않으면, 멀쩡히 실행되고 있는 테스트가 "신호 없음"으로 잘못 집계된다
   (이번 세션에서 `gov-router.test.mjs`가 실제로 이렇게 놓친 적이
   있었다 — 자체 포맷이라 처음 스캔에서 카운트가 전혀 안 잡혔다).

4. **전체 테스트를 스캔할 때 이 세 가지를 매번 병행 확인한다:**
   - TAP 요약 (`# pass N` / `# fail N`)
   - 커스텀 마커 카운트 (`✅`/`❌` grep, 또는 파일 고유 요약 문구)
   - 종료 코드/크래시 여부 (`SyntaxError`, `TypeError` 등 — 이건 코드
     문제가 아니라 실행 방법 문제일 수 있으니 바로 "버그"로 결론 내지
     말고 원인부터 확인)

## §6. PR 작성 시 권장 체크리스트 (설계를 바꾸는 모든 PR에 적용)

설계·정책·구조를 바꾸는 PR을 낼 때, 아래 항목을 PR 설명에 짧게라도
포함하는 걸 권장한다. 이번 세션에서 되짚어본 결과, 이 체크리스트를
당시에 거쳤다면 §2의 사례 대부분이 애초에 안 생겼을 것으로 보인다.

```
- [ ] 이 변경으로 이름/구조/인터페이스가 바뀐 대상을 grep으로 저장소
      전체(테스트 포함)에서 재검색해 남은 옛 참조가 없는지 확인했다.
- [ ] 이 변경과 직접 관련된 테스트 파일을 실제로 실행해 통과를
      확인했다(파일 헤더의 정확한 실행 명령어 사용).
- [ ] 이 변경이 여러 진입 경로(LLM 경로/키워드 경로, 클라이언트/서버
      등) 중 일부에만 적용됐다면, 그 사실을 주석과 PR 설명에 명시했다.
- [ ] "임시" 조치라면 되돌릴 조건과 담당을 주석에 명시했다.
- [ ] 기능을 죽은 코드로 판단해 제거했다면, 그 기능 전담 테스트도
      함께 제거하거나 archive와 같이 옮겼다.
```
