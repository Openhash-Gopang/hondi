SESSION LESSONS — 2026-09-08 세션 발견 정리

거래명세서는 구매자 몫만 있었다 — 검증 도구 자체도 세 번 틀렸다

"두 사람이 거래하면 양쪽 다 6하원칙 거래명세서를 남기고, 재무제표에도 양쪽 다 반영돼야 한다"는 지시에서 시작했다. 코드를 보니 _recordOrderPdv가 seller_guid를 인자로 받고도 실제로는 구매자 쪽 pdv_records만 기록하고 있었다 — 재무제표 쪽(pending_claims)은 이미 2026-09-07에 양방향화됐는데 PDV만 편측으로 남아있던 비대칭이었다. 고쳐서 라이브 스모크테스트로 검증하는 과정에서, 코드는 멀쩡한데 검증 스크립트 자체가 세 번 잘못된 결론(가짜 실패 2건, 진짜 원인 오인 1건)을 낼 뻔했다 — 그 세 가지를 구분해내는 과정 자체가 이 문서의 핵심이다.

Overview
이 문서가 왜 있는가

이 문서는 PDV나 재무제표 API 사용법을 다루지 않는다. 오늘 세션에서 반복적으로 확인된 패턴 — "두 당사자 거래를 한쪽 관점에서만 기록하는 코드는 절반의 진실만 말한다"와 "라이브 테스트가 실패했을 때, 대상 코드가 틀렸다고 단정하기 전에 검증 스크립트 자신의 가정부터 의심하라"는 두 교훈을 기록해두기 위한 것이다.

이 문서를 읽어야 하는 상황
두 당사자(구매자/판매자, 발신자/수신자 등)가 관여하는 기록을 한쪽 관점에서만 남기는 코드를 리뷰할 때 / PocketBase의 json 타입 필드를 다루는 클라이언트·테스트 코드를 새로 짤 때 / 라이브 스모크테스트가 실패했는데 원인이 대상 코드인지 테스트 코드인지 확신이 안 설 때 / 간헐적으로만 실패하는 API 호출을 마주쳤을 때.
Goal
오늘 세션의 목표와 흐름

출발점은 "PDV는 사용자의 일상과 업무를 6하원칙으로 기록하고, 금전 거래는 재무제표에도 반영돼야 한다"는 요구였다. 조사 결과 거래명세서를 작성하는 코드(_recordOrderPdv)가 실제로 존재했지만, seller_guid를 인자로 받고도 본문 어디서도 쓰지 않는다는 게 드러났다 — 구매자 쪽만 pdv_records에 기록되고 판매자는 자기 거래 내역을 PDV에서 볼 수 없는 구조였다. 재무제표 쪽(pending_claims → buyer_claim/ seller_claim)은 2026-09-07에 이미 양방향화가 끝나 있었으니, PDV만 뒤늦게 비대칭이 남아있던 셈이다.

흐름은: ① _recordOrderPdv 양방향화 → ② 이를 검증하는 라이브 스모크테스트(pdv_bidirectional_order_live_smoketest.cjs) 신규 작성 → ③ 실행·디버깅 반복(5회) → ④ 전 구간 PASS 확인, 순서로 진행됐다. ③ 단계에서 나온 실패 세 가지가 전부 검증 스크립트 자체의 버그였다는 게 오늘의 핵심 교훈이다.

Lesson ①
판매자만 기록되던 거래명세서 — _recordOrderPdv 편측 기록

worker.js의 _recordOrderPdv(env, { from_guid, seller_guid, ... })는 함수 시그니처에 seller_guid를 받으면서도, 본문에서는 guid: from_guid 한 줄만 써서 구매자 쪽 pdv_records에만 6하원칙 명세서를 남겼다. seller_guid는 인자로 넘어오고도 함수 어디에서도 참조되지 않았다 — 죽은 매개변수가 곧 죽은 기능이었던 사례다.

증상
판매자가 혼디마켓에서 아무리 많이 팔아도, 자신의 PDV(대시보드 "나의 기록 금고" 등)에서는 그 거래 기록을 전혀 볼 수 없었다. 재무제표 쪽은 이미 정상이었으므로("돈은 들어오는데 기록은 없다"), 두 시스템이 서로 다른 사실을 말하는 상태였다.

수정

  • 동일 거래의 6하원칙 명세서를 구매자용/판매자용 두 벌로 만들어 각자의 pdv_records에 기록. when· where·how·raw_hash 등 원장 메타데이터는 공유하고, who/what/ why만 구매/판매 관점에 따라 분기.
  • report_id는 pdv_records.report_id의 UNIQUE 인덱스 때문에 그대로 재사용할 수 없어(기존 handlePdvReport의 sessionId:reporterSvc 관례와 동일하게) :buyer/:seller 접미사로 분리했다.
  • 두 기록은 Promise.all + 개별 catch로 서로 독립시켜, 한쪽 기록 실패가 다른 쪽을 막지 않게 했다.

검증

라이브 스모크테스트에서 실제 P2P 매매 1건 후 guid+block_hash로 pdv_records를 조회해, 구매자·판매자 양쪽에 정확히 1건씩, type='tx_2party'로 존재하며 who/ what/why가 구매/판매 관점으로 정확히 갈리는지 확인했다 — 전부 통과.

Lesson ②
PocketBase json 필드를 문자열로 오인 — 이미 파싱된 값 재파싱

스모크테스트 첫 실행에서 구매자 who 필드 불일치: undefined로 실패했다. 진단 로그를 찍어 원본 레코드를 그대로 출력해보니 summary_6w 필드는 이미 {"who": "buyer(...)", "what": "...", ...} 형태의 파싱된 객체로 들어 있었다 — pdv_records 컬렉션의 summary_6w가 PocketBase json 타입 필드라, API 응답에서 자동으로 객체/배열로 역직렬화되기 때문이다.

증상
테스트 코드가 JSON.parse(rec.summary_6w)를 그대로 걸었다 — 인자가 이미 객체이므로 String(value)로 "[object Object]"가 되고, 그 문자열을 다시 JSON으로 파싱하려다 SyntaxError가 나서 catch에 조용히 삼켜져 빈 객체 {}로 남았다. 그 결과 who/what/why가 전부 undefined로 보여, 마치 실제 기록이 비어있는 것처럼 오인하기 쉬운 상태였다 — 실제로는 데이터가 완벽하게 정상이었다.

수정

function parse6w(raw) {
  if (raw && typeof raw === 'object') return raw;
  try { return JSON.parse(raw || '{}'); } catch { return {}; }
}

문자열이면 그대로 파싱하고, 이미 객체면 그대로 반환하도록 바꿔 문자열/객체 양쪽을 다 안전하게 처리하게 했다.

Lesson ③
API 응답 구조를 추측하지 말 것 — pl 하위 객체를 최상위로 오독

두 번째 실패는 구매자 재무제표 pl-purchase 미반영 — 기대 >= 30, 실제 undefined였다. 이번에도 재무제표 자체는 정상 반영돼 있었다 — 테스트 코드가 handleSettleLedger의 실제 응답 구조를 확인하지 않고 buyerFs.purchases로 바로 읽었는데, 실제 응답은 { pl: { revenue, purchases, ... }, bs: { inventory } }처럼 pl 객체 아래 중첩돼 있었다.

근본 원인
응답 구조를 실제 서버 코드(worker.js의 handleSettleLedger 반환문)를 다시 확인하지 않고 "아마 이렇게 생겼을 것"이라는 가정으로 짰다. Lesson ②와 근본 원인이 같다 — 서버가 실제로 돌려주는 형태를 직접 확인하지 않고 추측한 대가였다.

수정

buyerFs.pl?.purchases, sellerFs.pl?.revenue로 경로를 정정했다. 이번에도 재무제표 반영 자체는 처음부터 정상이었다 — purchases=30, revenue=30이 ORDER_AMOUNT와 정확히 일치함을 확인했다.

Lesson ④
간헐적 실패를 코드 결함으로 오인하기 전에 — TX_HASH_MISMATCH 재확인

위 두 버그를 고친 뒤에도 실행이 TX_HASH_MISMATCH로 두 번 실패했다. 처음엔 이번 패치가 원인인가 의심했지만, 클라이언트 (gopang-wallet.js)·서버 두 곳(pb_hooks/main.pb.js)의 sortedStringify 구현 세 곳을 전부 직접 대조한 결과 코드상 완전히 동일했다 — 이번 세션에서 건드린 부분과 무관한, 이미 2026-09-07 문서의 후속 과제에 "약 15~28% 빈도, 재시도 시 항상 성공"으로 기록돼 있던 알려진 L1 인프라 산발적 문제였다.

판단 기준
결정론적 버그라면 매번 재현돼야 한다. 같은 코드로 5번 실행해서 3번 성공·2번 실패했다면, 그건 "이번에 건드린 로직의 버그"가 아니라 외부 의존성의 산발적 문제일 가능성이 훨씬 높다 — 코드를 더 파기 전에 먼저 재현율부터 확인해야 한다.

대응

이 문제의 근본 원인 규명은 이번 세션 범위 밖으로 남겨두고, 테스트 하네스에는 매 시도마다 새 nonce/timestamp로 최대 3회까지 재시도하는 로직만 추가했다. 재시도는 거래 성사 여부에만 영향을 주고, 그 뒤에 실행되는 실제 검증(PDV 양방향 기록·재무제표 반영)의 판정 기준은 전혀 느슨하게 하지 않았다.

결과 — 검증된 사실
  • 검증됨 _recordOrderPdv 양방향화 — 실거래 1건 후 구매자·판매자 양쪽 pdv_records에 정확한 관점(who/what/why)의 6하원칙 명세서가 남는 것을 확인.
  • 검증됨 pending_claims 양방향 적재 — 구매자 pl-purchase, 판매자 pl-revenue 둘 다 적재 확인.
  • 검증됨 재무제표 실반영 — /biz/settle-ledger 호출 결과 purchases=30, revenue=30이 거래액과 정확히 일치.
  • 수정됨 스모크테스트 자체의 버그 3건(json 필드 재파싱, 응답 구조 오독, TX_HASH_MISMATCH 재시도 부재) — 전부 대상 코드가 아니라 검증 스크립트 쪽 결함이었음.
