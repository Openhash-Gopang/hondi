Overview
이 문서가 왜 있는가

이 문서는 GDC 이체 자체의 사용법을 다루지 않는다. "실사용 조건으로 한 번도 실행돼 본 적 없는 코드 경로는, 겉보기에 아무리 안전해 보여도(try/catch로 감싸져 있어도, 이미 검증됐다는 주석이 달려 있어도) 실제로 검증된 게 아니다"라는, 오늘 세션에서 반복적으로 확인된 하나의 패턴을 기록해두기 위한 것이다.

이 문서를 읽어야 하는 상황
PocketBase(Goja) 훅에서 원인 불명의 "Something went wrong" 400/500을 마주쳤을 때 / 서명 검증·해시 재계산이 클라이언트-서버 간에 어긋나는 버그를 디버깅할 때 / 최상위 모듈 스코프에 유틸리티 함수나 객체를 선언해 여러 훅에서 공유하려 할 때 / 오래돼 보이는 라우트나 코드를 지워도 되는지 판단해야 할 때.
Goal
오늘 세션의 목표와 흐름
  1. 출발점 — 이전 세션에서 GDC P2P 이체 라이브 테스트(gdc_transfer_live_test.cjs)가 구매자/판매자 계정 생성·가입 축하금 mint까지는 성공하지만, 실제 서명 이체(sendGdc)에서 "Something went wrong while processing your request."(정본 400)로 막힌 채 크레딧이 소진돼 중단된 상태로 이어받음.
  2. 1단계 — 원인 노출 — nginx 로그·journalctl로 먼저 확인했으나 실패(hanlim 노드 로그는 journald가 아니라 /opt/gopang/logs/hanlim.log 파일에 쓰인다는 걸 놓쳤던 게 원인). /api/mint가 2026-07-07에 같은 문제를 겪었을 때 썼던 패턴(핸들러 전체를 try/catch로 감싸 e.message를 응답에 노출)을 /api/tx에도 적용(#72) → 진짜 예외가 드러남.
  3. 2단계 — 근본 원인 ① — "_sigVerify is not defined" ReferenceError. 2026-07-19에 "여러 훅에서 재사용하기 위해" 파일 최상단 모듈 스코프로 승격했다고 기록된 서명 검증 유틸이, 실제 운영 환경(PocketBase Goja)에서는 콜백 안에서 참조가 안 됐다(#73으로 콜백 내부 지역 재선언으로 수정).
  4. 3단계 — 근본 원인 ② — 재시도했더니 이번엔 TX_HASH_MISMATCH. Worker(worker.js의 handleBizOrder)가 L1에 보낼 tx 객체를 "순수 UTXO만 전달"한다는 의도로 {version, input, outputs} 3개 필드만 재구성해서 보내고 있었는데, 클라이언트 지갑은 {..., items, nonce, timestamp} 6개 필드 전체로 서명했었다 — 필드가 하나라도 다르면 L1의 해시 재계산이 100% 어긋난다(#74로 재구성 없이 클라 서명 원본을 그대로 전달하도록 수정).
  5. 4단계 — 최초 성공 — 두 수정을 모두 배포한 뒤 재테스트, [PASS] GDC 이체가 실제 서명으로 정상 처리됨 확인(구매자 100→90, 판매자 100→110).
  6. 5단계 — 선제 감사 — ①과 같은 부류의 Goja 스코프 버그가 더 있는지 acorn(AST 파서)으로 파일 전체를 구조적으로 감사. _balanceUtils(삭제/PATCH 방어 훅 2곳)와 죽은 레거시 라우트 routerAdd("POST","/tx",...)의 NODE_ID까지 같은 패턴을 발견 → _balanceUtils는 예방적으로 지역 선언 전환, 레거시 /tx는 nginx 로그·저장소 전체 검색으로 호출자 0건 확인 후 삭제(#75).
① · Diagnostics
PocketBase 제네릭 오류는 원인을 숨긴다 — 통째로 감싸서 노출시켜라
국소적 try/catch만으로는 그 사이(gap)에서 나는 예외를 못 잡는다

PocketBase의 jsvm(Goja) 바인딩은, 훅 콜백 안에서 어디서도 잡히지 않은 예외가 발생하면 그걸 뭉개서 "Something went wrong while processing your request."라는 정본 메시지의 400으로 바꿔버린다. 실제 e.message/e.stack은 HTTP 응답에도, 서버 로그 파일에도 전혀 남지 않는다.

/api/tx 핸들러 안에는 이미 여러 개의 국소적 try/catch가 있었지만(2단계 공개키 확인, 3단계 블록 조회, 블록 저장, 원장 기록 등), 그 사이 구간(서명 검증, computeBalance() 호출, buyerClaim/ sellerClaim 생성 등)은 감싸져 있지 않았다 — 바로 이 사이 구간에서 오늘 발견된 두 버그가 둘 다 터졌다.

핵심 교훈
국소적 try/catch를 촘촘히 박아뒀다는 사실 자체가 안전하다는 증거가 아니다. 핸들러 전체를 감싸는 바깥 try/catch 하나가 "사이 구간"의 예외까지 모두 잡아 실제 원인을 즉시 응답에 노출시켜준다 — /api/mint가 2026-07-07에 같은 문제로 이미 이 패턴을 쓰고 있었고, 오늘 /api/tx에도 적용해 두 근본 원인을 순서대로 잡아냈다. 단, 클라이언트 응답에 e.stack을 그대로 넣는 건 운영 단계 정보 노출 리스크이므로, 스택은 서버 로그에만 남기고 응답에는 e.message만 담는다. 
} catch (e) {
  // 클라이언트 응답에는 stack을 넣지 않는다(운영 단계 노출 방지) —
  // 서버 로그(/opt/gopang/logs/hanlim.log)에는 그대로 남긴다.
  console.log("[TX] UNCAUGHT_EXCEPTION:", e.message, "| stack:", e.stack);
  return c.json(500, { ok: false, error: "UNCAUGHT_EXCEPTION", detail: e.message });
}

디버깅 도중 흔한 함정도 하나 있었다: hanlim 노드는 journald가 아니라 /opt/gopang/logs/hanlim.log 파일에 로그를 쓴다(EnvironmentFile/로그 경로 설정이 다른 systemd 유닛들과 다름). journalctl -u gopang-pb-hanlim -f로 기다렸다가 아무것도 안 찍혀서 "핸들러 진입 자체가 실패했다"고 잘못 판단할 뻔했다 — 실제로는 핸들러가 정상 실행되고 있었고, 단지 로그가 다른 파일에 쌓이고 있었을 뿐이다.

② · Goja Scoping
Goja는 콜백 바깥 최상위 선언을 콜백 안에서 못 본다 — 이 프로젝트에서 이미 여섯 번째 재발
"top-level var + IIFE 패턴은 안전하다"는 이전 기록 자체가 검증되지 않은 가정이었다

main.pb.js의 routerAdd/ onRecordBefore* 콜백 바깥(모듈 최상위 스코프)에 선언한 것을 콜백 안에서 참조하면, 이 프로젝트가 배포하는 PocketBase(Goja) 환경에서는 "X is not defined" ReferenceError가 난다. 이건 오늘 처음 발견된 게 아니라, 이 파일에서 이미 여러 번 재발한 패턴이다:

발견 시점대상결과
2026-07-07 이전computeBalance(bare function 선언), MINT_SECRET, NODE_CONFIG콜백 내부 지역 선언으로 이미 수정된 상태로 발견
2026-07-18sha256hex콜백마다 복붙(주석에 "5곳에 복붙됐다가 UTF-8 버그가 5중으로 재발" 기록)
2026-09-06(오늘, #73)_sigVerify(2026-07-19 "모듈 최상단 승격" 기록) — /api/tx실사용 이체가 처음 이 경로를 탄 순간 ReferenceError로 발각
2026-09-06(오늘, 예방수정)_balanceUtils — 삭제 방어·PATCH 방어 훅 2곳try/catch로 감싸져 있어 크래시는 아니었으나 같은 버그를 안고 있었음(미확인 상태였음)
2026-09-06(오늘, #75)NODE_ID — 죽은 레거시 /tx 라우트호출자 없어 실제 영향 없음, AST 감사로 발견 후 라우트째 삭제

흥미로운 부분은 _balanceUtils를 도입할 때 남긴 주석이다: "top-level var에 IIFE의 반환값(객체)을 담는 패턴은 실제로 동작한다(_sigVerify 자체가 그 증거)"라고 적혀 있었다 — 그런데 그 _sigVerify가 바로 오늘 실사용 조건에서 처음 크래시를 낸 대상이었다. 즉 "동작 확인된 선례"로 인용됐던 코드 자체가, 사실은 실사용 조건으로 한 번도 실행돼 본 적이 없어서 검증된 적이 없었을 뿐이었다.

왜 이제껏 안 걸렸나
register-key→mint→transfer 전체 플로우 중 서명 검증(_sigVerify 사용)까지 실제로 도달한 게 오늘이 처음이었다. 그 전까지의 모든 테스트 시도는 매번 더 앞 단계(잘못된 CFG 참조, mint 시크릿 불일치, 잔액 부족 등)에서 먼저 막혔다 — "여러 번 테스트했는데 안 터졌다"는 "이 코드가 안전하다"의 증거가 아니라 "이 코드에 아직 도달한 적이 없다"의 증거일 수 있다.

수정 방법 — 이미 검증된 워크어라운드

전역/모듈 스코프에 선언하지 말고, 그 값을 쓰는 각 콜백 내부에 지역 변수로 다시 선언한다(필요하면 코드 복붙이 되더라도). /api/tx, 삭제 방어 훅, PATCH 방어 훅 세 곳 모두 이 방식으로 고쳤다. 참고로 정확한 내부 메커니즘(왜 Goja가 이렇게 동작하는지)은 이번에도 확인하지 못했다 — 재현되는 증상과, 이미 여러 번 통한 워크어라운드만 확정했다.

오늘 세션 종료 시점 기준, main.pb.js 전체를 acorn으로 AST 파싱해 "콜백 밖 최상위 선언을 콜백 안에서 참조"하는 패턴이 더 남아있지 않은지 확인했다 — 남은 사례는 없다(레거시 /tx 라우트 삭제로 마지막 하나까지 제거됨).

③ · Signing Pipeline
서명 대상 객체는 다단계를 거치며 재구성하면 안 된다
"필요한 필드만 골라 새 객체를 만들기" ≠ "원본 그대로 전달하기"

클라이언트 지갑(gopang-wallet.js의 buildTxWithPrevHash)은 {version, input, outputs, items, nonce, timestamp} 6개 필드 전체를 sortedStringify()로 정규화한 뒤 그 결과를 해시(tx_hash)해서 서명한다. Worker의 handleBizOrder는 이 tx_hash를 L1에 그대로 전달하면서도, L1로 보낼 tx 본체는 "L1에는 순수 UTXO만 전달"한다는 의도로 {version, input, outputs} 3개 필드만 골라 새 객체를 만들어서 보내고 있었다.

L1의 /api/tx는 받은 tx로 sha256(sortedStringify(tx))를 다시 계산해 클라이언트가 보낸 tx_hash와 대조한다 — 필드 구성이 다르면 sortedStringify 결과 문자열 자체가 달라지므로, 해시는 절대 같아질 수 없다. 즉 이 경로로는 실제 지갑 서명 거래가 구조적으로 단 한 번도 통과할 수 없었다.

핵심 교훈
"이 필드는 수신 측에서 안 쓰니까 빼도 된다"는 판단은 함수 호출 인자를 줄이는 것과 서명 검증 대상 객체를 줄이는 것 사이에서 완전히 다르게 작동한다. 후자는 수신 측이 그 필드를 쓰든 안 쓰든, 서명 시점의 바이트 구성과 정확히 일치해야 검증이 통과한다. 수신 측(L1)이 특정 필드(tx.items, tx.score, tx.lcat 등)를 실제로 참조하는지 여부는 완전히 별개의 질문이다 — "L1이 unknown field를 무시한다"는 사실은 const {input, outputs} = tx 같은 구조 분해에는 맞는 말이지만, tx_hash 재계산에는 전혀 적용되지 않는다.

수정 방법

L1에 보낼 tx는 재구성하지 않고 클라이언트가 서명한 원본을 그대로 전달한다(tx || 최소 폴백). Worker가 L1 라우팅을 위해 추가로 계산한 값(score, lcat — PLSM 중요도 점수·LCAT)은 tx 객체 안이 아니라 바깥 요청 바디의 형제 필드로 보낸다 — L1이 나중에 이 값을 실제로 쓰게 되더라도 서명 검증 대상과는 분리된 채로 유지된다. 

// 틀렸던 방식 — 재구성하며 필드 누락 + score/lcat을 tx 안에 주입
const txPayload = {
  version: tx?.version || 1,
  input: tx?.input || {...},
  outputs: tx?.outputs || outputs || [...],
  score: importance_score,   // tx_hash 서명 대상 오염
  lcat,                      // tx_hash 서명 대상 오염
};

// 고친 방식 — 원본 그대로 전달, PLSM 입력값은 밖으로
const txPayload = tx || {...최소 폴백...};
const plsmFields = { score: importance_score, lcat };
body: JSON.stringify({ tx: txPayload, tx_hash, buyer_sig, buyer_public_key,
                        purpose, ...plsmFields, ...bridgeBody })
④ · Dead Code
죽은 코드는 고치지 말고, 로그로 확인한 뒤 지워라
호출자 없는 코드에 예방적 패치를 넣는 건 안전망이 아니라 함정을 다시 묻어두는 것

AST 감사에서 발견한 마지막 사례(레거시 routerAdd("POST", "/tx", ...)의 NODE_ID)는 처음엔 ②와 같은 방식으로 그냥 지역 선언으로 고치는 게 후보안이었다. 하지만 확인해보니 이 라우트를 부르는 곳이 저장소 어디에도 없었다(worker.js, gopang-wallet.js 포함 전체 검색 0건) — 그리고 nginx 접속 로그(hanlim·seogwipo 양쪽) 전수 확인 결과도 "POST /tx "(정확히 이 경로) 요청 0건이었다.

핵심 교훈
호출자가 없는 죽은 코드를 "혹시 모르니" 패치해두면, 겉보기엔 더 안전해 보이지만 실제로는 아무것도 더 안전해지지 않는다 — 아무도 안 부르니까. 오히려 "고쳐서 멀쩡해 보이게" 만들어두면 나중에 누군가 이걸 되살려 쓸 때 오늘과 똑같은 버그를 처음부터 다시 만나게 된다(이 경우 Goja 스코프 버그뿐 아니라, 43개 L1 노드 중 hanlim에만 맞는 NODE_ID 하드코딩까지 두 번째 버그가 숨어 있었다). 대체된 코드는 지우는 게 낫다 — git 히스토리에 그대로 남으므로 필요하면 언제든 복원 가능하다. 삭제 전에는 반드시 (1) 저장소 전체 텍스트 검색, (2) 실제 프로덕션 접속 로그, 두 가지로 호출자 부재를 확인한다.
