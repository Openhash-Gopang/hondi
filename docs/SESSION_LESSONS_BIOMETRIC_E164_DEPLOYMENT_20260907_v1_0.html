SESSION LESSONS — 2026-09-07 인증 강화 세션

코드는 하루 만에 끝났는데, 배포가 이틀치였다

SIM 스와핑·중고폰을 이용한 계정 재클레임 공격을 막기 위해 지문 (WebAuthn) 인증을 device-link 승인과 전화번호 재클레임 양쪽에 필수화하고, 그 과정에서 "혼디는 서버에 개인정보를 저장하지 않는다"는 원칙과 profiles.e164 평문 저장이 충돌한다는 지적을 받아 e164를 해시·암호화·뒷8자리 3필드로 재설계했다. 코드 자체(worker.js·pb_hooks/main.pb.js)는 하루 만에 짜고 로컬 PocketBase로 라이브 검증까지 마쳤지만, 실제 운영 배포 과정에서 이미 2026-08-10에 만들어져 있었던 자동배포 파이프라인의 존재를 모른 채 SSH로 수동 배포를 반복했고, 그 과정에서 필요한 환경변수(PHONE_ENC_KEY) 없이 새 코드가 먼저 배포되는 순서 사고까지 겪었다. 다행히 실사용자 피해는 없었던 것으로 확인됐지만, 이 문서는 그 경위를 다음에 비슷한 작업을 할 사람이 반복하지 않도록 정리한 것이다.

Overview
이 문서가 왜 있는가

"불법적으로 획득한 남의 폰으로는 본인 인증을 할 수 없게 하라"는 요구에서 시작해, 사고실험 도중 이미 배포돼 있던 handleWebAuthnRegisterKey·handlePushSubscribe 엔드포인트에 인증 자체가 아예 없었다는 훨씬 더 심각한 기존 결함을 발견했다. 이걸 고치는 김에 phone 번호 평문 저장 문제까지 같이 정리했는데, 정작 하루 종일 가장 많은 시간을 쓴 건 코드가 아니라 "이미 배포된 걸 어떻게 안전하게 되돌리고, 무엇을 어느 순서로 다시 배포하는가"였다.

이 문서를 읽어야 하는 상황
pb_hooks/main.pb.js나 pb_migrations/*.js를 운영에 배포하기 전 / profiles 스키마에 새 필드를 추가하거나 기존 필드 의미를 바꿀 때 / "SSH로 hanlim에 직접 파일을 올려야 하나?" 고민이 들 때(→ 답은 대부분 "아니오", §배포 파이프라인 참고) / WebAuthn·step-up 토큰 관련 코드를 만질 때.
What Changed
지문(WebAuthn) 인증 강화

기존에도 고액 거래 재인증용 step-up WebAuthn credential이 있었지만, device-link 승인(다른 기기 로그인 확인)과 전화번호 재클레임(SMS 인증) 두 경로는 지문 없이도 통과할 수 있었다 — 즉 도난·중고 획득한 폰이 이미 로그인/잠금해제된 상태라면, 코드 확인이나 SMS 인증번호 입력만으로 계정 승인·재가입이 끝났다. 이번에 두 경로 모두 지문 인증을 필수로 바꿨다.

device-link 승인 (auth/device-link-approve.html)

"본인이 맞습니다" 버튼을 눌러도, handleDeviceLinkVerify가 step_up_token 없이는 승인을 거부한다(403 BIOMETRIC_REQUIRED). 클라이언트는 승인 직전 GopangWallet.requireStepUpBiometric()을 호출하고, 이 세션(device-link:{sessionId})에만 유효한 챌린지에 서명해야 한다 — 다른 세션의 토큰을 재사용할 수 없다(WYSIWYS). 아직 생체 등록이 안 된 기기는 그 자리에서 enrollStepUpBiometric()으로 즉시 등록을 유도한다.

전화번호 재클레임 (biz/phone-otp-request → pb_hooks)

같은 번호로 이미 지문을 등록한 계정이 있으면, handlePhoneOtpRequest가 SMS 발송과 함께 그 계정 guid 앞으로 생체 인증 챌린지를 동봉해 내려준다. 이 챌린지로 유효한 assertion을 만들 수 있는 사람은 그 계정을 등록한 "물리적 인증기"를 실제로 쥔 사람뿐이다 — 불법 취득한 폰으로도 SMS는 받을 수 있지만 원래 소유자의 지문은 재현할 수 없다는 사실을 이용한다. pb_hooks/main.pb.js의 onRecordBeforeCreateRequest가 step_up_token을 독립 검증하며, 실패하면 BadRequestError로 가입 자체를 막는다(best-effort가 아니라 hard fail — §발견한 취약점 참고, 이 경로는 원래 느슨했다).

기존 사용자 유도

gopang-app.js의 앱 로드 시 배너(24시간 쿨다운) 문구를 "고액 거래 보호용" 에서 "등록 안 하면 새 기기 승인·번호 재등록이 막힌다"로 개정했다. 설정 화면의 "해제" 버튼에는 그 영향(로컬 해제일 뿐 서버 등록은 안 지워지지만, 재등록 전까진 이 두 경로를 못 씀)을 명시하는 확인창을 추가했다.

Findings
사고실험 도중 발견한 인증 부재 취약점 4건

지문 강화 작업을 시작하기 전 사고실험 단계에서, 관련 엔드포인트들에 원래 있던 훨씬 심각한 결함들이 먼저 드러났다. 전부 이번에 서명 검증(_verifyClaimsRequester 패턴)을 추가해 막았다.

엔드포인트문제파급력
handleWebAuthnRegisterKeyguid만 알면 누구나 그 계정에 자기 지문 credential을 등록 가능guid는 공개 정보 — 누구든 남의 계정 고액거래 생체인증을 자기 지문으로 통과시킬 수 있었음
handlePushSubscribeguid만 알면 누구나 임의 기기를 "신뢰 기기" 목록에 등록 가능재가입·device-link 판별의 "이 기기가 계정 소유자 것"이라는 전제 자체가 위조 가능했음
_verifyStepUpToken토큰 payload를 콜론으로 join/split했는데, guid가 IPv6 형식이라 콜론을 7개 포함 — 경계 복원이 원천적으로 불가능고액거래 재인증(step-up) 기능 자체가 애초에 정상 동작 안 했을 가능성 — JSON 배열 인코딩으로 근본 수정
최초 키 바인딩 방어e164_hash 전환 후에도 문제 없었으나, e164 → e164_hash 전환 과정에서 이 방어 로직이 참조하는 필드를 같이 안 바꿨다면 조용히 항상 실패했을 것실제로 걸릴 뻔했던 회귀 — 코드 리뷰 중 발견해 같이 수정
패턴
handleStepUpThresholdSet은 2026-09-06에 이미 같은 결함(guid만으로 값 변경 가능)이 발견돼 패치됐는데, 바로 옆의 형제 엔드포인트들은 그 패치에서 빠져 있었다. 같은 병의 다른 부위가 안 고쳐진 채 방치되는 패턴 — 인증 방식을 하나 고칠 때는 그 패턴을 쓰는 다른 엔드포인트도 전수 점검할 것.
Privacy
profiles.e164 평문 저장 제거

"혼디는 서버에 개인정보를 저장하지 않는다"는 원칙과 실제로 profiles.e164가 평문으로 저장되던 현실이 충돌한다는 지적에서 시작했다. e164는 세 가지 서로 다른 용도로 쓰이는데(①재가입 시 동일 번호 정확일치 중복탐지, ②SMS 재발송용 실제 번호, ③"숫자코드" 기능의 뒷자리 부분일치 검색) 하나의 단방향 해시로는 셋 다 대체가 안 된다 — 그래서 세 필드로 쪼갰다.

필드계산용도
e164_hash$security.hs256("e164-lookup:"+e164, PHONE_VERIFY_SECRET)정확일치 조회(중복탐지) 전용. 원문 복원 불가
e164_enc$security.encrypt(e164, PHONE_ENC_KEY)(AES-256-GCM)원문이 꼭 필요한 경로용으로 설계했으나, 실제로 이걸 읽는 코드는 현재 없음(아래 참고)
e164_last8뒷 8자리 평문"숫자코드" 입금 매칭 기능 — 원래도 사용자 화면에 일부 공개되는 정보라 예외로 둠

pb_hooks/main.pb.js의 onRecordBeforeCreateRequest가 신규 프로필 생성 시 위 세 필드를 계산해 저장하고, e164는 빈 문자열로 덮어쓴다. worker.js의 정확일치 조회 지점(_l1FindProfileByE164 등)은 전부 e164_hash 기준으로 바뀌었다.

뜻밖의 개선 — 숫자코드 기능이 오히려 단순해짐

기존엔 e164 저장 형식이 국가마다 자릿수가 달라 ~(LIKE, 부분포함) 필터로 넓게 뽑은 뒤 애플리케이션에서 뒷자리를 재확인하는 2단계였다. e164_last8은 애초에 정확히 8자리만 담기므로, 이제 e164_last8='코드' 정확일치 1단계로 끝난다.

e164_enc는 지금 아무도 안 씀

"SMS 재발송엔 원문이 필요하다"고 가정하고 암호화 필드를 만들었는데, 실제 코드(handleDeviceLinkResendSms)를 다시 보니 그 경로는 PocketBase에 저장된 값이 아니라 매 요청마다 클라이언트가 새로 보내는 임시 세션 값을 쓴다 — 애초에 영구 저장된 번호를 읽어온 적이 없었다. 그래서 복호화용 내부 라우트는 만들지 않았다(안 쓰이는 인증 경로를 미리 만드는 건 그 자체로 공격 표면). 스키마에 자리만 마련해뒀고, 실제 필요한 기능이 생기면 그때 추가한다.

아직 안 끝난 부분
이 마이그레이션은 앞으로 생성되는 레코드부터만 평문 저장을 막는다. 이미 쌓인 기존 레코드는 별도 백필 마이그레이션(1793900200_backfill_..., PR #108)으로 e164_hash/e164_enc/e164_last8을 소급 계산했지만, 평문 e164 자체는 아직 지우지 않았다(계산 오류 시 원본에서 재계산할 수 있게 하려고 의도적으로 남겨둠). 완전히 지우는 건 별도 후속 정리 마이그레이션으로 분리했다 — §아직 안 끝난 것 참고.
Verification
라이브 검증 — 로컬 PocketBase 버전을 반드시 맞춰야 하는 이유

pb_hooks/main.pb.js는 실제 재가입 로직의 집행 지점인데, PocketBase(Goja)에서 "문법 에러 없이 뜬다"와 "그 안의 로직이 실제로 맞게 실행된다"는 완전히 다른 얘기다 — _verifyStepUpTokenPB 같은 콜백 지역 함수는 (파일 상단에 이미 문서화된 제약대로) 최상위 선언이었으면 조용히 무시됐을 수 있다. 그래서 코드 반영 전에 격리된 로컬 PocketBase로 실제 HTTP 요청을 쏴서 재현했다.

처음에 겪은 실수 — PocketBase 최신 버전을 받음

releases/latest로 받은 v0.40.3은 v0.23에서 JS 훅 API가 완전히 갈아엎어진 이후 버전이라 onRecordBeforeCreateRequest 같은 옛날 훅 이름 자체가 없다 — ReferenceError: onRecordBeforeCreateRequest is not defined가 났다. 운영은 docs/POCKETBASE-STRUCTURE-GUIDE_v1_0.md에 명시된 대로 v0.22.14로 고정돼 있다 — 검증 환경도 반드시 이 버전을 명시적으로 지정해서 받아야 한다 (releases/download/v0.22.14/..., latest 금지).

검증 방법

운영과 무관한 격리 디렉토리·격리 포트(운영이 8091~8096을 쓰므로 8199 사용)에 v0.22.14를 새로 받아, 저장소의 전체 pb_migrations를 복사해 처음부터 재생시켜 스키마를 실제 운영과 동일하게 재현했다(수동으로 최소 필드만 만드는 것보다 이 방식이 select 필드 제약(claim_status가 자유 텍스트가 아니라 claimed/unclaimed select였던 것) 같은 실제 스키마 제약을 놓치지 않는다). curl로 가짜 지문 계정을 심고, ①지문 없이 재클레임 시도 → 차단, ②유효한 step_up_token으로 재클레임 → 통과 + 옛 계정 완전 supersede, ③worker.js↔pb_hooks 해시 알고리즘 크로스 검증까지 전부 확인한 뒤에야 실제 배포로 넘어갔다.

Incidents
배포하면서 실제로 겪은 사고 5건

① git add -A로 무관한 파일 149개가 커밋될 뻔함

작업 폴더에 다른 세션의 산출물(node_modules, *.bundle, *.zip, 테스트 스크립트 등)이 섞여 있었는데, git add -A를 그대로 실행해 전부 커밋에 딸려갈 뻔했다. git reset(mixed, soft 아님 — soft는 스테이징이 그대로 남는다) 후 필요한 파일만 명시적으로 add해 복구. 여러 세션이 같은 작업 폴더를 공유할 때는 -A를 쓰지 않는다.

② git apply 후 커밋 없이 push — "빈 브랜치" 사고

git apply로 패치를 작업 디렉토리에만 적용하고 커밋을 빼먹은 채 git push했다 — push는 커밋을 올리는 것이지 작업 디렉토리 변경사항을 올리는 게 아니므로, 그 시점 main과 똑같은 빈 브랜치가 올라갔다. 라이브 검증 중 새 코드 마커가 하나도 안 잡혀서 발견 — 테스트 코드에 로그 마커를 심어둔 덕분에 "패치가 잘 동작한다"는 잘못된 결론을 피할 수 있었다.

③ PHONE_ENC_KEY 없이 pb_hooks가 먼저 배포됨

PR #107 머지 → §배포 파이프라인의 마이그레이션 자동배포가 발동 → migrate up 성공 후 자동으로 systemctl restart → 그런데 이때 hanlim의 pb_hooks/main.pb.js가 (별도 경로로) 이미 새 버전으로 올라가 있어서, 재시작과 함께 e164_hash 로직이 활성화됐다. 이 로직은 PHONE_ENC_KEY 환경변수를 요구하는데, 그때까진 Cloudflare Worker에만 설정했고 PocketBase의 /opt/gopang/gopang.env에는 없었다 — 전화번호 인증이 필요한 모든 신규가입이 07:14~07:51 약 37분간 400 BadRequestError로 실패했을 수 있는 상태였다. journalctl·에러 로그로 실제 PHONE_ENC_KEY 관련 에러가 0건임을 확인해 실제 피해는 없었던 것으로 결론냈지만, 운이 좋았을 뿐이다.

배포 순서 원칙
새 필드/새 환경변수를 요구하는 로직은, ①스키마 마이그레이션 → ②환경변수 설정 → ③기존 데이터 백필 → ④그 로직 자체를 배포 순서를 반드시 지킬 것. 순서를 바꾸면 "새 로직이 옛날 데이터·옛날 환경을 만나는" 창이 생긴다. 오늘은 이 순서를 계획은 했지만, git 머지 시점과 실제 파일 배포 시점을 착각해 ③보다 ④가 먼저 나가버렸다.

④ 7월 16일 과거 크래시 로그와 오늘 사고를 혼동할 뻔함

pb_hooks 재배포 후 헬스체크가 HTTP 000이 나와 당황했다가(재시도하니 200 — 단순 기동 타이밍 문제), 에러 로그에서 panic: registerMigrations: ... 1784200001_created_public_data_usage.js 반복 크래시를 발견하고 오늘 배포 때문인가 의심했다. stat으로 로그 파일의 실제 mtime을 확인하니 2026-07-16 — 두 달 전 흔적이었다(append 전용 로그라 안 지워지고 남아있던 것). append 로그는 항상 타임스탬프로 "지금" 발생한 건지 확인하고, 절대 마지막 줄만 보고 판단하지 않는다.

⑤ 실사용자 데이터로 파괴적 테스트를 할 뻔함

운영에 지문 등록된 활성 계정이 실제로 1건 있는 걸 확인한 시점에, 그 계정으로 "진짜 재클레임 스모크 테스트"를 하려다 멈췄다 — 성공하면 그 실사용자 계정이 실제로 superseded 처리된다. 로직 정확성은 이미 격리된 로컬 환경에서 충분히 검증했으므로, 운영에서는 "배포가 무사히 됐고 서비스가 안정적인지"만 확인하고, 실사용자 데이터를 이용한 파괴적 검증은 하지 않는다.

기존 자동배포 파이프라인 — 이미 있었는데 몰랐다

위 사고 ③을 겪고 원인을 추적하다가, 이미 2026-08-10 문서에 같은 유형의 사고("2026-07-16 사고 — 마이그레이션 파일이 GitHub에만 있고 서버엔 한 번도 안 들어간 문제")를 막기 위해 만든 자동배포 파이프라인이 문서화돼 있었다는 걸 뒤늦게 발견했다. 그동안 SSH로 직접 파일을 복사하고 있었던 게, 바로 이 문서가 명시적으로 경고한 방식이었다.

워크플로트리거동작
.github/workflows/deploy-pb-migrations.ymlpb_migrations/**가 main에 push될 때강제 커맨드로 제한된 SSH 키로 hanlim의 /opt/gopang/ops/apply-pb-migrations.sh 실행 — 변경된 파일만 개별 검증 후 반영, migrate up 성공 후에만 systemctl restart, 재시작 후 헬스체크(최대 5회 재시도)까지 자동
.github/workflows/deploy-worker.ymlworker.js 또는 wrangler.toml이 main에 push될 때cloudflare/wrangler-action으로 hondi-proxy Worker에 자동 배포

pb_hooks/main.pb.js에 대한 자동배포는 없다 — 위 두 워크플로 중 어느 것도 pb_hooks/** 변경을 트리거로 잡지 않는다. 그래서 오늘 겪은 것처럼, pb_hooks 자체는 여전히 SSH 수동 배포 대상이고, 그 배포 타이밍을 "마이그레이션 자동배포"와 맞춰 신경 써서 조율해야 한다.

실제 마이그레이션 폴더 경로
/opt/gopang/pb_migrations가 아니라 /opt/gopang/pb/pb_migrations다(예전엔 전자가 후자를 가리키는 심볼릭 링크였던 것으로 추정 — 2026-08-10 문서 참고). ls /opt/gopang/pb_migrations가 "No such file"이면 이 진짜 경로부터 확인할 것.
