## 0. 이 문서가 존재하는 이유

2026-09-02 문서(KPLAN_KMAIL_INTEGRATION_ARCHITECTURE)는 "캠페인이 끝나면 K-Mail이 다이제스트를 만들어 K-Plan에 알린다"는 **상향 보고 한 줄기**만 구현했다. 그런데 실제로 K-Mail이 인바운드 메일을 받을 때마다 "이걸 내가 처리해도 되나, K-Plan에 물어봐야 하나, 사람까지 올려야 하나"를 판단해야 하는 상황이 반복적으로 생긴다 — 이걸 처리할 **하향 지시·실시간 질의응답 경로**가 없었다. 본 문서는 그 공백을 메운다.

## 1. 근본 전제 — 메일이라는 매체의 재정의

기존 이메일은 "사람이 사람에게 쓰고, AI가 대신 써준다"는 틀이다. K-Mail의 설계 의도는 이걸 **"K-Mail이 상대측 K-Mail과 직접 주고받고, 그 결과를 사람에게 보고한다"**는 틀로 바꾸는 것이다. 두 조직(또는 개인) 사이의 조율이 "사람이 메일 확인 → 며칠 뒤 답장" 대신 양쪽 K-Mail이 그 자리에서 여러 차례 주고받는 방식으로 이뤄지면, 의사결정 속도·정확성·합리성이 사람이 매 왕복에 끼어들 때보다 현저히 높아진다는 것이 이 재설계의 목적이다.

이게 성립하려면 K-Mail이 **사람 확인 없이 여러 차례 자율적으로 응답할 수 있어야** 한다. 무제한 자율은 위험하므로, 그 자율성의 범위를 정하는 것이 조직 구조와 처리 등급 설계다(§2, §3).

## 2. 조직 구조 — 세 층위의 역할 분담

```
사람(사장)
  ↑ 최종 보고(중요한 것만)         ↓ 정책·승인
K-Plan (기획팀)
  ↑ 처리결과 보고                  ↓ 지시·위임(사전에) / 즉답(실시간)
K-Mail (front line, 실무 담당)
  ↔ 상대측 K-Mail (실제 협상·조율 — 메일 프로토콜)
```

| | 사람 | K-Plan (기획팀) | K-Mail (front line) |
|---|---|---|---|
| 결정하는 것 | 새로운 정책, 큰 그림 승인 | 이 캠페인을 왜/누구에게/몇 단계로, 각 체크포인트에서 뭘 확인할지, 결과를 보고 계획을 바꿀지 | 지금 이 사람에게 뭐라 쓸지, 언제 리마인드할지, 이 회신이 스팸인지 진짜 문의인지 |
| 시간 축 | 필요할 때만 개입 | 여러 주에 걸친 계획 전체 | 지금 이 순간의 대화 하나하나 |
| 실패 시 | 방향 재승인 | 계획 재수립(K-Recompose) | 스레드를 어떻게 이어갈지 재시도·에스컬레이션 |

**K-Mail은 사람에게 직접 보고하지 않는다** (개인이 K-Mail에 직접 부탁한 사적 용무 — 예: 지인에게 메일 한 통 — 는 예외. 이 경우는 지금처럼 K-Mail이 사용자에게 바로 답한다). K-Plan이 관리하는 캠페인/스레드는 전부 K-Plan을 거쳐 사람에게 올라간다. 이렇게 갈라야 K-Plan이 "이 정도면 사람한테 알릴 만하다/아니다"를 판단할 여지가 생긴다.

## 3. 3단계 처리 원칙

메일 한 통이 도착했을 때 K-Mail이 어느 등급으로 처리할지는 **[메일의 성격 × 지금의 실제 상태]**로 정해진다 — 메일 종류만으로는 등급이 정해지지 않는다.

> 예: "짜장면 2그릇 주문"은 영업시간·주방 여유·재고가 충분하면 **2단계**(K-Plan 선에서 즉시 승인), 재고가 없으면 같은 메일이 **3단계**(사람 승인 필요, 또는 정중한 거절)가 된다.

| 단계 | 정의 | 예시 | 보고 대상 |
|---|---|---|---|
| **1. 즉결** | 되돌릴 필요조차 없는 일 | 스팸 삭제 | 없음(로그만) |
| **2. 위임 범위 내 실행** | K-Plan이 미리 정해둔 조건 안에 들어옴 — K-Mail이 판단해 실행, 사람은 안 거침 | 짜장면 주문(재고·시간 여유 충분) | K-Plan |
| **3. 신규 판단 필요** | 전례 없음·기존 위임 범위 밖 | 시청 위생 점검 통보 | K-Plan **+** 사람 |

"지금의 실제 상태"(재고·영업시간 등)를 K-Mail은 직접 갖고 있지 않는다 — **K-Mail은 상태를 조회하지 않고, 판단이 필요하면 즉시 K-Plan에 묻는다.** K-Plan이 필요시 다른 모듈(예: K-JIT)과 통신해 답을 구하고, K-Mail에 지시를 내린다.

## 4. K-Plan↔K-Mail 프로토콜 — 세 가지 통신 패턴

기존(2026-09-02 문서)에는 아래 A만 있었다. 본 문서에서 B·C를 신설한다.

### A. 상향 보고 — 다이제스트 (기존, 변경 없음)
캠페인 종료/`digest_at` 도달 시 K-Mail → K-Plan. 1회성, 요약 성격. `KMAIL_LOOKUP_CAMPAIGNS`/`KMAIL_CAMPAIGN_REPORT`(SP v1.8)로 사람이 직접 캠페인을 다시 조회하는 것과는 별개 경로 — 그건 "개인이 기록을 찾아보는 것"이고, 이건 "K-Mail이 능동적으로 알리는 것"이다.

### B. 사전 질의 (신설) — 행동하기 전에 K-Plan의 즉답을 구함
메일이 2단계인지 3단계인지 K-Mail 혼자 판단이 안 서면, **응답 전에** K-Plan에 묻고 답을 받아서 실행한다.

```
① 상대 K-Mail → 자사 K-Mail: 메일 도착 ("짜장면 2그릇 주문")
② 자사 K-Mail → K-Plan: "이 요청, 처리해도 됩니까?" (사전 질의)
③ K-Plan → K-JIT 등 타 모듈: 재고·여유 조회 (필요시)
④ K-Plan → 자사 K-Mail: 지시 ("수락해도 됨" / "보류, 대기 응답 보내고 기다려" / "사람 승인 필요")
⑤ 자사 K-Mail → 상대 K-Mail: 지시에 따라 실행
⑥ 자사 K-Mail → K-Plan: 처리 완료 보고 (A 경로 재사용)
```

**K-Plan이 즉답을 못 줄 때(사람 승인이 필요해 시간이 걸릴 때)의 대응은 K-Plan이 사안의 급함에 따라 그때그때 정한다** — 정해진 규칙이 아니라 매 건 K-Plan의 판단이다:
- 급한 사안이 아니면: K-Mail은 K-Plan/사람의 결정이 나올 때까지 상대에게 응답을 미룬다.
- 상대측이 응답 지연을 이상하게 여길 수 있는 사안이면: K-Plan이 "확인 후 회신드리겠습니다" 같은 **대기 응답 문구까지 지정해서** K-Mail에 내려주고, K-Mail은 그 문구로 즉시 응답한 뒤 실제 결정을 후속 메일로 보낸다.

즉 대기 응답 여부·문구는 K-Mail의 재량이 아니라 **매번 K-Plan이 함께 내려주는 지시의 일부**다.

### C. 위임 정책 — 반복 상황을 매번 사전 질의하지 않도록
같은 유형의 요청이 반복될 걸 대비해, K-Plan이 체크포인트 단위로 **자연어 위임 문구**를 K-Mail에 미리 내려줄 수 있다(기존 K-Mail 자동삭제 규칙 — "불필요한 메일은 도착 즉시 삭제해" — 과 동일한 패턴: 문장을 그대로 저장해두고, 판정 시점에 다른 AI가 그 문장을 읽고 수행). 이 위임 범위 안에 들어오면 B의 ②~④(사전 질의 왕복)를 생략하고 바로 2단계로 실행한다.

**개발 초기에는 위임 문구를 단순한 자연어 한 줄로 시작하고, 점차 정련한다** — 처음부터 항목별 구조화 조건을 설계하지 않는다.

## 5. 데이터 모델에 미치는 영향 (다음 구현 단계에서 다룰 것 — 본 문서는 방향만 명시)

- **캠페인은 K-Plan 소유 개념으로 재해석된다.** 지금 `kmail_campaigns`는 K-Mail이 독자적으로 만드는 것처럼 돼 있는데(§2-2 `KMAIL_SEND_CAMPAIGN`), 실제로는 K-Plan 체크포인트가 "발송"으로 구체화된 결과물에 가깝다. `kplan_plan_id`/`kplan_checkpoint_label`는 지금처럼 선택적 태그가 아니라, K-Plan이 발주한 캠페인이면 필수로 채워지는 방향이 자연스럽다.
- **"스레드"(사람 1명과의 대화) 개념이 필요하다.** 지금은 캠페인이 최소 단위라 회신 처리가 `digest_at` 한 시점에 일괄 처리되는데, B 경로(사전 질의)가 들어오면 인바운드 도착 즉시(스레드 단위로) 판단이 필요해진다. `kmail_campaign_recipients`(SP v1.8 신설)가 이 스레드의 초기 형태이지만, 지금은 회신 1건 매칭·분류만 하지 신규 인바운드 도착 시 즉시 트리거되는 구조가 아니다 — 이 부분은 별도 설계가 필요하다.
- **위임 정책 저장소가 필요하다.** 지금 `kmail_rules`(자동삭제 규칙)와 유사하지만, 삭제 여부가 아니라 "K-Plan에 안 물어보고 실행해도 되는 조건"을 담는 새 컬렉션 또는 `kmail_rules`의 확장이 필요하다.
- **K-Plan 쪽에도 "K-Mail로부터의 사전 질의를 받는 창구"가 신설돼야 한다** — 지금 K-Plan은 K-Mail의 다이제스트(완료 보고)만 받는 수신자였지, 실시간 질의에 답하는 역할은 없었다.

## 7. K-Plan↔K-Mail 함수 수준 API (2026-09-04 구현)

두 모듈이 같은 Cloudflare Worker(`worker.js`) 안에 있으므로, 실제 HTTP 왕복이 필요 없다 — 함수 호출 자체가 API 경계다. 기존 상향 경로(`_kmailTriggerKPlanRecompose`)와 신설 사전 질의 경로(`_kplanDecideForKMail`) 둘 다 "K-Plan SP를 그 자리에서 로드해 즉시 LLM 호출" 패턴을 공유한다.

### 7-1. 기존 경로의 수정 — `_kmailTriggerKPlanRecompose` (상향, A)
캠페인 다이제스트 생성 시 트리거. **수정 사항**: 지금까지 K-Recompose 결과가 사용자 메시지함(`ai_messages`)에만 쓰이고, `kplan_plans` 레코드(대화 이력·`checkpoint_count`) 자체는 갱신되지 않던 공백을 메웠다 — `_kplanPersistCheckpoint`(HTTP 핸들러 `handleKPlanPlanCheckpoint`와 저장 로직 공유)로 실제 plan 레코드에 반영한다. plan.hondi.net에서 이 플랜을 다시 열면 이제 이 재평가가 대화 이력에 그대로 보인다.

### 7-2. 신설 — `_kplanDecideForKMail` (하향/사전 질의, B)
K-Mail 인바운드 메일이 로컬 위임 규칙(§4-C)만으로 판정이 안 서고(`none`/`escalate`), 그 캠페인이 K-Plan 플랜에 속해 있을 때(`kplan_plan_id` 존재) 호출된다.

```
입력: { ownerGuid, planId, checkpointLabel, subject, bodyText, threadHistoryText? }
출력: { decision: 'approve' | 'escalate', replyGuidance?, urgent?, holdMessage?,
        suggestedRuleText?, delegationPromoted? }
```

- K-Plan은 그 플랜의 `goal`·`refined_plan_md`(계획서 맥락)·**§8-2 실시간 상태**·**§8-3 스레드 이력**을 근거로 판단한다 — 로컬 위임 규칙(문장 하나)보다 풍부한 맥락으로 판단 가능.
- `approve`면 K-Mail이 `reply_guidance`를 근거로 사람 확인 없이 즉시 회신한다(§4-C의 위임승인 흐름과 동일 실행 경로 재사용).
- `escalate`면 K-Mail 인바운드가 `kmail_escalation`으로 사람에게 올라간다. `urgent:true`면 K-Plan이 함께 준 `hold_message`를 K-Mail이 즉시 발송한 뒤 에스컬레이션한다(예: 짜장면집이 새 식재료 공급업체의 첫 제안 메일을 받았을 때 — 즉답은 못 하지만 "검토 후 회신드리겠습니다"는 바로 보낼 수 있는 경우). `urgent:false`면 대기 응답 없이 그냥 에스컬레이션만 한다.
- 이 왕복도 체크포인트로 `kplan_plans`에 기록된다(§7-1과 동일 원칙) — 나중에 plan.hondi.net에서 "이런 문의가 왔고 K-Plan이 이렇게 판단했다"를 그대로 볼 수 있다.

## 8. 남은 공백 해소 (2026-09-04)

### 8-1. 위임 정책 자동 승격
`_kplanDecideForKMail`이 `APPROVE`를 낼 때, K-Plan 스스로 "이게 반복 가능한 안정적 패턴인가"까지 함께 판단한다(`suggest_delegation`/`rule_text`). `true`면 즉시 `kmail_rules`(`delegate_execute`, 이 `plan_id`/`checkpoint_label`로 범위 한정)를 생성한다 — 반복 횟수를 세지 않고 K-Plan의 판단 1회를 그대로 신뢰한다("초기엔 단순하게" 원칙과 일관). 과하게 일반화됐다고 드러나면 사람이 그 규칙을 나중에 지우거나 좁히면 된다("사람이 추후에 수정" 원칙과 일관). 승격이 일어나면 `kmail_delegated_reply` 메시지에 그 사실이 함께 보고된다 — 조용히 규칙이 늘어나지 않는다.

### 8-2. 실시간 상태 — `kplan_plan_state`
재고·영업시간처럼 계획서에 미리 적어둘 수 없는 값을 담는 범용 key-value 저장소(`plan_id`+`state_key` 단위). `POST /kplan/plan/state/set`으로 값을 넣으면 `_kplanDecideForKMail`이 자동으로 참조한다. 지금은 사람이 값을 넣는 것과 (미래의) K-JIT 같은 자동 연동을 구분하지 않는 설계라 — 후자가 생기면 이 컬렉션에 쓰는 것만으로 바로 연동된다. `source` 필드로 출처만 남겨둔다.

### 8-3. 스레드 단위 상태 — `kmail_campaign_recipients.thread_status`
완전히 새 컬렉션(`kmail_threads`) 대신, 이미 "사람 1명 × 캠페인 1건"을 가리키던 `kmail_campaign_recipients`를 스레드로 취급한다. `open`(진행 중)/`pending_kplan`(K-Plan 응답 대기)/`pending_human`(에스컬레이션 대기)/`resolved`(위임 처리 완료) 4단계로, 인바운드 처리마다 갱신된다. 동시에 신설된 `_kmailFetchThreadHistory`가 같은 상대와의 과거 왕복(최근 8건)을 불러와 `_kplanDecideForKMail`의 판단 근거에 포함시킨다 — 이번 메일 한 통만 보고 판단하지 않는다.

### 8-4. 여전히 남은 것
- `kplan_plan_state`는 사람이 수동으로 채워야 한다 — 실제 POS·재고 시스템과의 자동 연동(K-JIT 등)은 아직 존재하지 않는다. 이번 작업은 그 연동이 들어올 자리(인터페이스)만 마련했다.
- 위임 규칙 자동 승격(§8-1)은 K-Plan의 판단 1회를 그대로 신뢰하는 구조라, 오판이 그대로 규칙화될 위험이 있다 — 승격된 규칙에 대한 사후 검토·재확인 절차는 아직 없다.
- 스레드 이력(§8-3)은 최근 8건으로 고정 길이다 — 매우 긴 협상처럼 그 이상을 봐야 하는 경우는 아직 못 다룬다.

## 9. 전략과 전술 — 지휘 체계 명시 (2026-09-04, 주피터 지시)

§2의 역할 분담표를 한 단계 더 명확히 한다. **K-Plan은 전략(정치), K-Mail은 전술(전쟁)이다.** K-Plan은 "무엇을 왜 달성해야 하는가"를 정하고, 그 실현 방법(언제·누구에게·어떤 순서로·몇 차례에 걸쳐)을 설계하는 건 K-Mail의 몫이다. §2 표를 이 비유로 다시 쓰면:

| | K-Plan | K-Mail |
|---|---|---|
| 비유 1 (전쟁) | 전략 — 이 전쟁을 왜, 무엇을 위해 하는가 | 전술 — 그 전쟁을 실제로 어떻게 치르는가 |
| 비유 2 (정치) | 정치 — 목표와 정당성을 정한다 | 전쟁 — 정치가 정한 목표를 실제로 수행한다 |

이전 판(§7-1, §7-2, 그리고 2026-09-04 사고실험)에서는 K-Plan이 "1차/2차/3차 발송 시점, 각 차수 문구 차이" 같은 **전술적 세부사항까지 직접 설계**했다 — 이건 이번 지시로 정정된다. K-Plan은 이제 이 수준의 스케줄을 스스로 짜지 않는다. K-Plan이 하는 일은 §9-1의 정형 브리프를 만들어 K-Mail에 넘기는 것까지고, "몇 차례에 걸쳐 언제 누구에게 무엇을 보낼지"의 구체적 설계와 그 설계에 대한 보고는 K-Mail의 책임이다.

### 9-1. K-Plan → K-Mail 전략 브리프 — 반드시 육하원칙 정형 포맷

K-Plan이 사용자의 목표를 K-Mail에게 넘길 때는 자유서술이 아니라 **반드시 육하원칙(누가·언제·어디서·무엇을·어떻게·왜) 6개 항목이 모두 채워진 정형 포맷**으로 넘긴다. 항목이 비어 있으면(사용자 지시에 그 정보가 없으면) K-Plan이 K-Intent 단계에서 사용자에게 먼저 물어 채운 뒤에만 브리프를 발행한다 — 빈 칸을 짐작으로 채우거나 K-Mail에게 그대로 떠넘기지 않는다.

```json
{
  "brief_id": "kplan-brief-<uuid>",
  "plan_id": "<kplan_plans.id>",
  "누가(who)": "이 캠페인이 도달해야 하는 대상 — 인구통계·카테고리 수준(구체적 명단은 K-Mail이 조사)",
  "언제(when)": "전체 캠페인이 유효한 기간(시작~종료) — 회차 스케줄은 K-Mail 소관",
  "어디서(where)": "이 소통이 이뤄지는 채널·목적지",
  "무엇을(what)": "전달해야 하는 핵심 메시지·내용 요지(정확한 문구는 K-Mail 소관)",
  "어떻게(how)": "허용된 수단과 그 한계(예: 이메일만/여러 차례 가능/자동 접속측정 허용 여부)",
  "왜(why)": "이 캠페인의 목적·성공 기준 — K-Mail이 전술을 설계할 때 판단 근거로 삼는 기준"
}
```

이 브리프는 §7의 함수 수준 API와 같은 방식(같은 Worker 내 함수 호출)으로 K-Mail에 전달되며, 아래 §9-2의 보고를 받을 때까지 `kplan_plans`에 "브리프 발행됨" 상태로 기록된다.

### 9-2. K-Mail → K-Plan 전술 보고 — 같은 6개 항목, 구체화된 값으로

K-Mail은 브리프를 받으면 자체 판단(자체 SP, K-Plan의 SP가 아님)으로 전술을 설계하고, **같은 육하원칙 6개 항목을, 이번엔 실행 가능한 구체값으로 채워** K-Plan에 보고한다 — 항목 구조를 유지하는 이유는 K-Plan(그리고 궁극적으로 사람)이 "브리프에서 뭐가 구체화됐는지" 한눈에 대조할 수 있게 하기 위함이다.

```json
{
  "brief_id": "kplan-brief-<uuid>",
  "누가(who)": "실제 검색으로 확정된 수신자 목록(또는 그 규모·카테고리별 분포)",
  "언제(when)": "회차별 발송 일정 — 몇 차까지, 각 차수 날짜, 회신 취합 마감 시각",
  "어디서(where)": "실제 사용될 링크·도메인(예: {{TRACKING_LINK}} 사용 여부)",
  "무엇을(what)": "회차별 실제 제목·본문 초안(또는 그 차이점 요약)",
  "어떻게(how)": "발송·수신자별 맞춤·재시도·에스컬레이션 처리 방식",
  "왜(why)": "K-Mail이 이 스케줄·문구를 이렇게 짠 근거 — 브리프의 '왜'에 대한 K-Mail 나름의 해석"
}
```

그리고 **보고 주기 자체도 K-Mail이 이 보고 안에서 스스로 제안한다** — "몇 차 완료 시마다 보고할지"는 브리프에 없는 정보이므로(그건 전술이다) K-Mail이 정해서 K-Plan에 알리고, K-Plan이 이상하면 되돌려 조정을 요청할 수 있다.

### 9-3. 실행 승인 경계는 변하지 않는다

이 지휘 체계 명시는 **누가 무엇을 설계하느냐**를 바꾸는 것이지, §3(3단계 처리 원칙)·§8-1(위임 자동승격)이 정한 **누가 승인하느냐**의 경계를 바꾸지 않는다. K-Mail의 전술 보고가 K-Plan에 올라간 뒤에도, 실제 대량 발송처럼 위임 범위 밖의 실행은 여전히 사람의 최종 승인을 거친다.
