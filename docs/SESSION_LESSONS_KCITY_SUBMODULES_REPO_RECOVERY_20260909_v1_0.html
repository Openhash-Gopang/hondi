재개발 SP 하나 만들려다, 실제 서비스를 덮어쓸 뻔했다

"재개발·재건축 정비사업 실행 SP를 만들어달라"는 요청에서 시작했다. Openhash-Gopang/city 저장소를 클론했는데 .git 폴더만 보여서 "빈 저장소"라고 판단하고 K-City라는 이름으로 새 서비스를 설계·배포했다 — 그런데 그 클론은 빈 저장소가 아니라 실패한 클론이었고, 실제로는 이미 K-City("시민 복지 총합 최적 도시 설계")가 살아서 운영 중이었다. 실서비스의 index.html· webapp.html을 목업으로 덮어쓴 PR을 머지까지 해버린 뒤에야 발견해 되돌렸다. 이후 지시에 따라 재개발 기능을 K-City의 하위 모듈로 재설계하고, 감정평가는 새로 만들지 않고 기존 전문가 페르소나에 위임했으며, 배선 작업 중 gopang 저장소가 아카이브되고 실제 백엔드가 hondi로 옮겨간 사실도 뒤늦게 알게 됐다. 전부 "확인 없이 넘겨짚었다가 나중에 더 큰 비용으로 바로잡은" 패턴이라 한데 묶어 기록한다.

Overview
이 문서가 왜 있는가

이 문서는 K-City나 감정평가 SP의 사용법을 다루지 않는다. 오늘 세션에서 반복적으로 확인된 패턴 — "클론·조회 결과가 예상과 다르면 '없다'로 단정하기 전에 그 조회 자체가 성공했는지부터 의심하라"와 "이미 있는 걸 다시 만들기 전에, 있는지부터 제대로 찾아봐라" 는 두 교훈을 기록해두기 위한 것이다.

이 문서를 읽어야 하는 상황
git clone·조회 결과가 비어 있어서 "새로 만들어도 되겠다"고 판단하려 할 때 / 이미 있을 법한 기능(전문가 페르소나, 유틸리티 모듈)을 처음부터 다시 짜려고 할 때 / 여러 저장소에 걸쳐 백엔드가 나뉘어 있는 프로젝트에서 "진짜 소스가 어디 있는지" 헷갈릴 때 / Windows에서 한글이 섞인 스크립트·문서 파일이 자꾸 깨질 때.
Goal
오늘 세션의 목표와 흐름

출발점은 "재개발 관련 주민 의사 수렴, 절차 진행, 감정평가, 비용 추산, 분양 계획, 시공사 선정을 수행할 SP를 만들어달라"는 요청이었다. 흐름은: ① Openhash-Gopang/city 클론 → 빈 저장소로 오인 → 독립 서비스 "K-City"(재개발 실행 AI) 설계·배포(PR #4) → ② 사용자가 로그를 되짚어보라는 지시로 히스토리 재조사 → 실제 K-City가 이미 있었고 그걸 덮어썼다는 사실 확인 → git revert로 복구 (PR #5) → ③ "K-City 하위 모듈로 추가하라" 지시 → 도시정비(SP-27a)를 본체(SP-27)의 실행 계층으로 재설계, 본체 콘텐츠는 건드리지 않고 추가만 하는 패치 스크립트로 배포(PR #6) → ④ "감정평가는 자체 기능을 가질 필요 없다, 필요할 때 호출하라" 지시 → 전문가 페르소나 레지스트리에서 기존 감정평가사 페르소나(SP_appraiser)를 찾아 SP-27b를 그 페르소나로의 어댑터로 재설계(PR #7) → ⑤ "라우팅 패치 진행하라" 지시로 gopang 저장소의 worker.js에 엔드포인트를 새로 만들려다 그 저장소가 아카이브된 것을 발견 → 실제 백엔드(hondi 저장소)를 찾아보니 해당 엔드포인트가 이미 동작 중이었고, 진짜 빈 자리는 하드코딩된 시스템 프롬프트 쪽이었다는 걸 확인 → 그 프롬프트만 확장해 반영(hondi#163), 순서로 진행됐다.

Lesson ①
실패한 클론을 "빈 저장소"로 오인 — 실제 서비스 덮어쓰기

git clone --depth 1 https://github.com/Openhash-Gopang/city.git을 실행했을 때 출력에 remote: Enumerating objects...· Receiving objects... 줄이 아예 없었다 — 성공한 클론이면 반드시 찍히는 로그다. 그런데 이걸 놓치고, 받은 디렉터리에 .git만 있고 파일이 없는 것만 보고 "빈 저장소"라고 단정했다. 실제로는 이 저장소에 2026-09-04~06 사이 만들어진 실제 K-City(SP-27_kcity_v0_1.txt, "시민 복지 총합 최적 도시 설계", 공용 인증 모듈 연동까지 된 webapp.html)가 있었다.

이 오판 위에서 독립 서비스를 설계·배포했고(index.html· webapp.html을 새로 작성해 PR #4로 머지), 그 결과 실제 운영 중이던 서비스의 콘텐츠가 통째로 사라졌다 — 커밋 로그에는 "5 files changed, ... 390 deletions(-)"라고 이미 찍혀 있었는데, "당연히 새 파일이니 삭제 줄이 있을 리 없다"는 전제 때문에 그 숫자를 눈여겨보지 않았다.

재발 방지
git clone이 remote: Enumerating objects... 로그 없이 조용히 끝나면 클론 실패를 의심하고 재시도할 것 — 빈 디렉터리를 "빈 저장소"의 증거로 삼지 않는다. git add . 뒤에는 반드시 git status·git diff --stat로 "생성"인지 "수정/삭제 포함"인지 먼저 확인한다 — 삭제 줄 수가 0이 아니면 멈추고 확인한다.
Lesson ②
되돌리기 — git revert, 브랜치 보호 임시 해제, GitHub Pages 인증서 재발급

git revert -m 1 <머지커밋> --no-edit로 되돌리기 커밋을 만들고 PR로 머지해 콘텐츠를 복구했다. 이 과정에서 두 가지 추가 문제를 만났다.

Pages 커스텀 도메인이 HTTPS 인증서를 발급하지 못함

되돌리기 이후 city.hondi.net이 HTTP로는 뜨는데 HTTPS는 SEC_E_WRONG_PRINCIPAL로 실패했다. gh api repos/.../pages 응답에 https_certificate 필드 자체가 없었다 — DNS는 정상(GitHub Pages IP로 정확히 풀림)인데 인증서 발급 자체가 멈춰있었다. 커스텀 도메인을 -F cname=null로 껐다 켜서 재발급을 트리거하려 했더니 "Unable to commit CNAME because the Pages branch is protected." 에러가 났다 — legacy Pages는 커스텀 도메인 설정 변경 시 CNAME 파일을 직접 커밋하려 하는데, 브랜치 보호 규칙이 그 커밋 자체를 막고 있었다.

브랜치 보호를 안전하게 껐다 켜기

gh api repos/.../branches/main/protection으로 기존 규칙을 먼저 백업한 뒤 DELETE로 해제, 도메인 재설정, 그리고 백업해둔 내용으로 복원하는 순서로 진행했다. 여기서 두 번 더 걸렸다: 복원용 JSON을 PowerShell Set-Content -Encoding utf8로 저장했더니 BOM이 붙어 GitHub API가 "Problems parsing JSON"으로 거부했다(-Encoding ascii로 해결). 또한 GET 응답 스키마(enforce_admins: {enabled: true} 같은 중첩 객체)와 PUT 요청 스키마(enforce_admins: true, 평평한 값)가 다르다는 것도 미리 확인하지 않았으면 그대로 재전송해서 또 실패했을 것이다.

재발 방지
GitHub Pages 커스텀 도메인을 만졌는데 이상 동작이 나오면 브랜치 보호부터 의심한다(legacy Pages는 CNAME 파일 커밋을 시도한다). 브랜치 보호를 임시로 풀 땐 반드시 GET으로 먼저 백업하고, 그 응답을 PUT 스키마로 수동 변환해서 복원용 파일을 만들어둔다 — GET 그대로 재전송하면 실패한다. Windows에서 GitHub API에 보낼 JSON 파일은 -Encoding ascii(내용이 순수 ASCII일 때) 또는 utf8NoBOM으로 저장한다.
Lesson ③
새로 만들지 않고 위임 — 이미 있던 감정평가사 페르소나(SP_appraiser) 재사용

도시정비 모듈(SP-27a)에 처음엔 자체 3방식(원가법·거래사례비교법· 수익환원법) 감정가 추정 로직을 직접 서술했다. "도시정비 모듈이 자체 감정평가 기능을 가질 필요가 없다, 감정평가가 필요할 때 감정평가 모듈을 호출하라"는 지시로 별도 모듈(SP-27b)로 분리했고, 이어서 "인간 감정평가사와 같은 역할을 수행해야 한다"는 지시가 왔다.

여기서 SP-27b를 처음부터 다시 설계하는 대신, sp-catalog.json과 expert-registry 파일들을 뒤져 이미 SP_appraiser_v1_9.md (카탈로그 키 SP_appraiser, K-Law 소속, HT-1 등급)가 존재함을 확인했다 — 3방식 적용, 실거래가 웹검색 강제, 확신도 이원화(방법론× 데이터), 소송·상속·과세 상황 강제 인간전환, L1/L2/L3 사용자 등급까지 갖춘 성숙한 페르소나였다(9번의 개정을 거침). SP-27b를 이 페르소나로의 어댑터로 재설계해, 실체 판단 로직은 전부 위임하고 ①호출 형식 변환 ②원래 없던 "재개발 분담금 참고" 목적 추가 ③응답 형식 변환만 새로 맡겼다.

재발 방지
"인간 전문가와 같은 역할을 하는 AI"가 필요하면, 새로 짜기 전에 sp-catalog.json과 expert-registry를 먼저 검색한다 — Hondi는 이미 505개 전문가 페르소나 체계를 갖추고 있다. 있는 걸 두 번 만들면 단일출처원칙이 깨지고, 나중에 어느 쪽이 최신인지 헷갈리는 문제가 생긴다.
Lesson ④
Windows 인코딩 3종 세트 — CRLF, UTF-8 BOM, PowerShell 함수 스코프

라이브 스모크테스트용 PowerShell 스크립트를 한글 문자열과 함께 전달했더니 "Unexpected token '6.'" 같은 파싱 오류가 반복됐다 — Windows PowerShell 5.1이 non-ASCII 문자가 섞인 .ps1 파일을 UTF-8 BOM 없이 읽으면 시스템 기본 코드페이지(CP949)로 잘못 해석한다. BOM을 붙여 재전달해도 같은 증상이 반복돼, 결국 스크립트 내용을 전부 ASCII로만 작성하고 한글 검증 문자열은 Base64로 인코딩해 실행 시점에 [System.Text.Encoding]::UTF8.GetString(...)로 복원하는 방식으로 바꾸고 나서야 해결됐다 — 파일 자체가 순수 ASCII면 어떤 코드페이지로 열려도 깨질 수 없다.

그 스크립트를 고치는 과정에서 별도의 순수 로직 버그도 있었다: 함수 안에서 $results += [pscustomobject]$row를 했는데, PowerShell은 함수 스코프가 기본적으로 부모 스코프에 쓰기 접근을 안 하기 때문에 매번 로컬 사본만 쌓이고 버려지고 있었다 — 그 결과 "테스트 실행됨, 그런데 결과가 0/0"이라는, 실패조차 아닌 거짓 성공이 나왔다. $script:results로 스코프를 명시하고 나서야 실제로 기록됐다.

재발 방지
한글이 섞인 .ps1 파일을 Windows 사용자에게 전달할 땐 처음부터 ASCII+Base64 패턴을 쓴다(BOM 재시도로 시간 낭비하지 않는다). PowerShell 함수 안에서 바깥 스코프 변수를 누적(+=)해야 하면 반드시 $script:를 명시한다 — "0/0 통과" 같이 실패조차 아닌 결과가 나오면 그 자체를 의심 신호로 받아들인다.
Lesson ⑤
아카이브된 저장소에 계속 PR을 시도할 뻔함 — gopang → hondi 이관

"감정평가 라우팅을 배선하라"는 지시로 Openhash-Gopang/gopang의 worker.js(31,512줄)를 읽고, handleKlawRelay· callDeepSeek 패턴을 조합해 새 엔드포인트를 만들어 커밋까지 했다. git push에서야 "This repository was archived so it is read-only."가 떴다 — gopang은 이미 2026-09-02에 아카이브됐고, 실제 백엔드는 hondi 저장소로 옮겨진 뒤였다.

hondi의 worker.js를 확인해보니, 만들려던 엔드포인트(/kcity/relay)는 이미 2026-09-04부터 존재하고 정상 동작 중이었다 — 전화번호 인증, GDC 과금, DeepSeek 호출까지 다 갖춰진 상태로. 처음에 "미해결 과제"라고 짚었던 근거는 city 저장소 webapp.html에 남아있던 오래된 주석("아직 hondi-proxy에 등록되지 않았을 수 있습니다") 하나뿐이었는데, 실제 배선 상태를 직접 확인하지 않고 그 주석만 믿었다. 진짜 빈 자리는 라우팅이 아니라, 그 엔드포인트가 쓰는 하드코딩된 KCITY_SYSTEM_PROMPT 문자열이 오늘 만든 두 하위 모듈을 몰랐다는 것 — 그 문자열 하나만 확장해서 해결했다(hondi#163).

재발 방지
여러 저장소로 나뉜 프로젝트에서 백엔드를 고치기 전엔 gh api repos/<org>/<repo> --jq .archived로 그 저장소가 살아있는지부터 확인한다. 클라이언트 코드에 남은 주석 ("아직 등록 안 됨" 등)은 언제 쓰인 건지 모르는 이상 신뢰하지 말고, 서버 코드를 직접 열어 실제로 그 라우팅이 있는지 확인한 뒤에 작업을 시작한다.
Lesson ⑥
배포는 됐는데 404 — Cloudflare 부정 캐싱

이 문서 자체를 배포한 직후 겪은 일이다. gh api repos/.../pages/builds/latest로 빌드가 "built" 상태이고 last-modified가 방금 커밋 시각과 일치하는 것까지 확인했는데도, 실제 URL은 계속 404였다. GitHub Pages 원본(openhash-gopang.github.io/hondi/...)을 직접 찔러보니 301로 hondi.net으로 정상 리다이렉트됐다 — 즉 GitHub Pages 쪽엔 파일이 확실히 있었다. 원인은 그 사이에 있는 Cloudflare 캐시였다: 파일이 생기기 전에 그 URL을 요청한 적이 있으면 Cloudflare가 그 404 응답 자체를 캐싱해두고, 파일이 생긴 뒤에도 한동안 캐시된 404를 계속 돌려준다. 쿼리스트링을 하나 붙여서(?cachebust=1) 캐시를 우회하니 바로 200이 나왔고, 잠시 후 원래 URL도 자연스럽게 캐시가 갱신되며 200으로 바뀌었다.

재발 방지
새로 추가한 파일이 배포 직후 404면, 빌드 상태("built")를 확인했다고 바로 "실패"로 단정하지 않는다 — ①GitHub Pages 원본 도메인 (<org>.github.io/<repo>/...)으로 직접 확인해 Pages 자체엔 있는지 먼저 가른다 ②있는데도 커스텀 도메인에서만 404면 캐시버스팅 쿼리(?t=...)로 우회 확인한다 ③그걸로 200이 뜨면 그냥 시간이 지나면 풀리는 부정 캐싱이니 기다리거나 필요하면 Cloudflare에서 해당 URL만 Purge한다 — 배포 자체를 되짚어 고칠 필요는 없다.
