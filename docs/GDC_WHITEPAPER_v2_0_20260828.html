GDC 인프라 종합 백서 — 백지 상태에서 재구축 가능한 기술 명세

GDC(Gopang Digital Currency)는 혼디(Hondi) 플랫폼의 내부 통화 단위로, 원화(KRW) 충전 즉시 1:1로 발행되어 AI 사용료 결제·마켓 상품 구매· 사용자 간 이체에 쓰인다. 이 문서는 2026년 6~8월 설계 논의와 2026-08-28 세션의 실사용 재현 테스트·라이브 디버깅에서 확인된 모든 사실을 통합한 것으로, 설계 의도만 있고 아직 라이브로 검증되지 않은 부분은 설계 의도 배지로 명시적으로 구분했다.

발행 저장소 Openhash-Gopang/gopang 인프라 Cloudflare Workers(hondi-proxy) + PocketBase(L1, Oracle Cloud VM) 기준 환율 KRW 1 = GDC 1 (현재 라이브 관측치) 최종 갱신 2026-08-28
Overview
개요 — GDC란 무엇인가

GDC는 혼디 플랫폼 이용자의 지갑(gopang-wallet.js, 로컬 IndexedDB 기반)에 귀속되는 내부 통화 단위다. 사전 발행이 없다 — 사용자가 실제로 원화를 고정 계좌에 입금해야만, 그 금액만큼 GDC가 L1(PocketBase)의 /api/mint 엔드포인트를 통해 그 자리에서 발행된다. 발행된 GDC는 세 가지 용도로 쓰인다:

  • AI 사용료 결제 — 무료 한도 초과분의 DeepSeek 등 LLM 사용료를 GDC로 차감(_settleAiUsage)
  • 마켓 상품 구매 — K-Market에서 실물/서비스 구매 시 GDC로 결제(/api/tx)
  • 사용자 간 P2P 이체 — 혼디 코드 스캔 등으로 상대를 특정해 GDC 송금(/wallet/gdc-transfer)

핵심 철학은 다음 두 문장으로 요약된다: "GDC는 충전 용도만이 아니라 사용자와 사용자 간의 결제 수단으로도 이용된다"(2026-08-28 세션에서 재확인)와 "어느 한 재무제표를 위변조하려면 세상의 모든 재무제표를 동시에 위변조해야 한다"(결합 재무제표 원칙, 2026-06월 설계). 후자는 아직 라이브로 전면 검증되진 않았으나 설계 방향으로 계속 유지되고 있다.

① Architecture
시스템 아키텍처 3계층

        │  HTTPS (fetch)
        ▼

  · 라우팅 테이블: export default { async fetch(request, env, ctx) {...} }
  · 인증·요율제한·CORS·비즈니스 로직 전부 이 파일 하나에 있음(수만 줄)
  · env로 시크릿 주입, ctx로 Cloudflare 실행 컨텍스트(waitUntil 등) 접근
        │  Bearer 토큰 인증 fetch
        ▼
L1 — PocketBase (Oracle Cloud VM, 포트 8091)
  · pb_hooks/main.pb.js — 커스텀 라우트(/api/mint, /api/tx, /api/balance 등)
  · 컬렉션: profiles, charge_requests, ledger_entries, seller_verifications 등
  · 각 지역/노드(hanlim 등)가 systemd 서비스로 독립 프로세스 운영

워커(hondi-proxy)는 비즈니스 로직과 시크릿 검증을 전담하고, L1(PocketBase)은 원장(ledger)의 유일한 진실 공급원 역할을 한다. 클라이언트는 절대 L1에 직접 접근하지 않고 반드시 워커를 거친다 — L1 Admin 토큰(_l1AdminToken(env))은 워커 내부에서만 발급·보관된다.

중요
L1 노드는 여러 지역 인스턴스(예: l1-hanlim)로 분산 운영되며, pb_hooks/main.pb.js는 모든 노드가 같은 코드를 공유하지만 배포는 노드별로 개별 systemd 서비스 재시작이 필요하다 (핫리로드 없음). 워커의 L1_DEFAULT 상수가 실제로 트래픽을 받는 노드를 가리킨다(현재 https://l1-hanlim.hondi.net).
② Wallet & Auth
지갑·인증 — Ed25519, TOFU, 잔액 재구성

지갑 생성

가입 시 gopang-wallet.js가 기기에서 Ed25519 키페어를 자동 생성하고, 공개키를 서버에 TOFU(Trust On First Use) 방식으로 최초 등록한다. 개인키는 로컬(IndexedDB)에만 저장되며, 백업 키(4단어 시드)로 기기 분실 시 복원 가능하다(_exportBackupKey/ _restoreFromBackupKey).

로컬 캐시와 서버 재대사

gopang-wallet.js는 로컬 재무제표(bs-cash 등)를 IndexedDB에 캐시한다. hydrateFromServer()가 서버 실잔액으로 이 캐시를 교정하고, refreshBalanceUI()(2026-08-28 신설)가 그 결과로 헤더(#gdc-balance)·설정 화면 (#gdc-balance-display) DOM까지 함께 갱신한다.

발견된 근본 문제(2026-08-28 이전)
hydrateFromServer()는 원래 로그인·가입 시점에만 호출됐다. AI 채팅 차감이나 계좌입금 충전이 일어나도 이후 갱신 트리거가 전혀 없어, 사용자가 재로그인하기 전까지 화면 잔액이 영원히 갱신 전 값으로 남았다. §⑫에서 수정 이력 상세.

잔액 재구성 (computeBalance)

L1은 클라이언트가 보고하는 balance_claimed를 신뢰하지 않는다. 대신 computeBalance()가 해당 계정의 모든 블록을 리플레이해 잔액을 재구성하고, 이 값과의 불일치가 있으면 거부한다 — 이중지불 방지의 핵심 메커니즘.

④ Top-up Pipeline
충전 파이프라인 — 전화번호 매칭키

왜 전화번호 매칭키인가

최초 설계는 사용자가 은행 이체 시 "보내는 분 표시"에 무작위 발급 코드(HD+6자리)를 입력하는 방식이었다. 그러나 실사용 재현 테스트에서 은행이 예금주 실명을 그 필드 앞에 자동으로 붙이고, 필드 전체가 10자로 잘린다는 게 확인됐다(이름 3자 + 코드 8자 = 11자로 항상 초과). 한국인 이름이 대개 2~4자인 이상 이건 특정 사용자만의 문제가 아니라 모든 실사용자에게 구조적으로 재현되는 결함이었다.

해결책(2026-08-28, 주피터 지시): 사용자가 이미 알고 있는 본인 전화번호 뒷 8자리를 매칭키로 쓴다. 예금주 이름을 안 적어도 되므로(사용자가 그 필드를 지우고 숫자 8자리만 남기면) 10자 제한 안에 항상 들어간다. 한국 휴대폰 번호는 010-XXXX-XXXX 형식상 뒷 8자리가 전국적으로 고유하다는 전제.

전체 흐름

1. POST /biz/charge-request { guid, krw_amount }
   → _phoneMatchKey(env, guid): L1 profiles.e164 뒤 8자리 추출
   → 이 guid의 기존 pending 레코드 전부 status=cancelled로 정리
     (전화번호 매칭키는 항상 같은 값이라 여러 pending이 쌓이면
      "엉뚱한 예전 신청이 확정"되는 부작용 방지 — 2026-08-28 발견)
   → charge_requests에 새 pending 레코드 생성, match_code=전화번호뒷8자리
   → 응답: { match_code, match_code_is_phone: true, bank_account_info, guide }

2. 사용자가 고정계좌에 입금, "보내는 분 표시"에 match_code 포함

3. 확정 채널 (4종, 전부 _mintAndRecordCharge 공유):
   a) manual_admin        — 관리자가 은행 명세서 직접 확인, POST /biz/charge-confirm
   b) auto_openbanking    — 오픈뱅킹 API 폴링 (⚠ 미구현 스켈레톤, §⑪)
   c) auto_pg_webhook     — PG 가상계좌 웹훅 (⚠ 미구현 스켈레톤, §⑪)
   d) auto_notification_capture — 관리자 폰 알림캡처 앱이 은행 SMS를
      가로채 POST /biz/charge-confirm-notification 호출 (✅ 라이브 검증 완료)

4. _extractChargeMatchCodeFromText(raw_text)로 원문에서 매칭키 추출
   → charge_requests에서 match_code + status=pending 검색(sort=-created)
   → 있으면 그 레코드로 확정
   → 없으면(사전 신청 없이 바로 입금한 경우) _findGuidByPhoneMatchKey()
     로 profiles.e164 역조회 → 찾으면 그 guid로 즉시 발행
     (existingRequestId 없이 새 charge_requests 레코드 생성)

5. _mintAndRecordCharge() → L1 /api/mint 호출 → GDC 발행
   → charge_requests를 status=matched로 갱신(또는 신규 생성)
   → ledger_entries에 mint 기록(§⑦)
   → ctx.waitUntil(_sendPushToGuid(...))로 Web Push 발송(§⑤)

매칭키 추출 정규식 (최종본, 2026-08-28)

function _extractChargeMatchCodeFromText(text) {
  const s = String(text);
  // 우선순위 1: 독립된 숫자 8자리(전화번호 매칭키)
  // "*"(마스킹된 계좌번호) 바로 뒤 숫자는 제외 — 아래 버그 참고
  const phoneMatch = s.match(/(?<![\d*])\d{8}(?!\d)/);
  if (phoneMatch) return phoneMatch[0];
  // 우선순위 2(하위호환): 2026-08-28 이전 발급된 무작위 코드
  const legacyMatch = s.match(/HD\d{6}/);
  return legacyMatch ? legacyMatch[0] : null;
}
버그 — 마스킹 계좌번호 오탐
실제 은행 SMS는 항상 마스킹된 계좌번호(예: 315***02804011)를 포함하는데, 최초 정규식(/(?<!\d)\d{8}(?!\d)/)은 "*" 뒤에 남는 8자리 숫자까지 매칭키로 오인했다 — 매칭키가 전혀 없는 일반 입금 알림에서도 오발동해 실제 매칭키를 가진 입금을 놓치는 원인이 됐다. "*" 바로 뒤 숫자를 제외하는 부정 후방탐색 (?<![\d*])으로 수정.
⑤ Push Notification
실시간 알림 인프라 — VAPID Web Push

발송 경로

_sendPushToGuid(env, guid, {title, body, tag, url})가 단일 진입점이다. 대상 계정의 profile.push_subscription (여러 기기 지원, _parseDeviceSubscriptions)을 조회해 각 구독에 _sendWebPush()로 VAPID 서명된 푸시를 보낸다. 저잔액 알림(_checkLowBalanceAndNotify)과 GDC 충전 확정 알림(태그 gdc-charge-confirmed)이 이 함수를 공유한다.

근본 버그 — ctx.waitUntil() 누락으로 푸시 유실

처음 구현 시 _sendPushToGuid(...).catch(...)를 await 없이 발사했다. Cloudflare Workers는 fetch 핸들러가 Response를 반환하는 즉시 실행 컨텍스트를 종료할 수 있는데, ctx.waitUntil()로 명시적으로 수명을 연장하지 않은 promise는 내부의 L1 프로필 조회·VAPID 서명·FCM 발송 fetch가 끝나기도 전에 통째로 잘려나간다. 이 저장소에는 이미 동일 클래스 버그가 "43건 중 8건 유실"로 기록돼 있었다 (worker.js 1388번 줄 근처, device-link 서명요청 관련).

수정: ctx를 라우팅 테이블 → handleChargeConfirm/handleChargeConfirmNotification/ handleChargeWebhookPG/_pollOpenBankingAutoConfirm(cron) → _mintAndRecordCharge까지 전부 관통시키고, 푸시 발송을 ctx.waitUntil()로 감쌌다(ctx 없는 극히 드문 경로는 직접 await로 폴백).

우선순위(Urgency) 설정

_sendWebPush(env, subscription, payload, urgency='normal')의 기본값은 'normal'이다. Android는 앱이 백그라운드/Doze 상태일 때 normal 우선순위 FCM 메시지를 배터리 절약 목적으로 몇 분씩 배칭·지연시킨다 — 실사용 재현에서 PWA 잔액 반영이 3~5분 걸리는 증상으로 관찰됨. 'high'로 명시하면 즉시 깨우기를 요청한다. GDC 충전 알림·저잔액 알림 모두 'high'로 발송하도록 수정 완료.

실시간 브로드캐스트 (탭이 열려있는 동안)

sw.js의 push 이벤트 핸들러가 tag === 'gdc-charge-confirmed'를 감지하면, OS 알림 표시와 별개로 열려있는 모든 탭에 즉시 postMessage({type: 'REFRESH_GDC_BALANCE'})를 브로드캐스트한다(기존 SYNC_AI_SETTING/ CHECK_FOR_UPDATE 패턴 재사용). gopang-app.js가 이 신호를 받아 window.gopangWallet.refreshBalanceUI()를 즉시 호출하고, Gopang Wallet 시트가 열려있으면 openGopangWallet()을 재호출해 내용까지 다시 그린다.

iOS / PWA 제약

플랫폼 제약(우회 불가)
iOS Safari는 일반 브라우저 탭 상태에서 웹 푸시 자체가 플랫폼 차원에서 불가능하다(iOS 16.4+ 포함, 예외 없음). 반드시 "홈 화면에 추가"로 설치된 standalone 앱이어야 구독이 성립한다. 클라이언트 판별: window.matchMedia('(display-mode: standalone)').matches || window.navigator.standalone === true. 미설치 상태에서는 권한 요청 자체를 시도하지 않고 설치를 먼저 안내해야 한다(시도해도 100% 실패하므로 무의미).
버그 — window.open이 standalone 컨텍스트를 깸
iOS에서 홈 화면에 설치된 standalone 앱 안에서 window.open()으로 새 탭을 열면 Safari로 튕겨져 나가면서 standalone 컨텍스트 자체가 깨진다(iOS PWA의 알려진 제약 — 여러 창/탭 미지원). _openUsagePage() 수정: standalone으로 이미 실행 중이면 window.location.href로 같은 창 안에서 이동하고, 일반 브라우저 탭에서는 기존처럼 새 탭으로 연다.
⑥ Commerce
GDC 상거래 — 이체·구매·AI 사용료

P2P GDC 이체

POST /wallet/gdc-transfer — 혼디 코드 스캔 등으로 상대를 특정해 송금. handleBizOrder의 검증된 로직을 그대로 물려받음(수수료 검증 등). 설계 의도 purpose='purchase'일 때 memo(품목명) 필수, 금액이 ₮50 초과 + 미인증 판매자면 SELLER_NOT_VERIFIED로 거부(판매자 인증 문턱).

마켓 상품 구매

/api/tx(L1)가 구매자·판매자 양측 claim을 계산해 블록에 기록하고, ledger_entries에 source: 'market'로 양쪽 다 기록한다(구매자 debit, 판매자 credit).

AI 사용료 차감

_settleAiUsage(env, guid, bill, meta, ctx) — K-Law· Business·Government 등 각 relay의 onAfterRecord 콜백에서 호출된다. 무료 한도 게이트는 _gdcFreeQuotaGate 공용 헬퍼가 네 진입점(K-Law· Business·Government relay·일반 채팅) 전부에 동일하게 적용된다 — "DeepSeek 호출 전에 반드시 게이트를 통과해야 한다"는 비용 순서 불변식이 있음(2026-07-28 세션에서 14개 시나리오로 검증). 정산 결과는 ledger_entries에 source: 'ai_usage', fs_account: 'pl-purchase', direction: 'debit'로 기록.

판매자 인증

설계 의도 /seller/verify-submit (사업자등록증 해시 제출) → 관리자 승인(admin/seller-verify.html, admin_guids 등록자만) → /seller/verify-status가 verified로 전환. 미인증 판매자는 ₮50 초과 구매 결제를 못 받는다(위 P2P 이체 문턱과 동일 로직 공유).

⑦ Ledger
통합 회계원장 — ledger_entries

ledger_entries(L1 PocketBase 컬렉션)는 GDC의 모든 거래 유형을 하나의 복식부기 원장으로 통합 기록한다 — 이게 바로 "GDC는 충전뿐 아니라 결제 수단"이라는 요구사항을 실제로 뒷받침하는 단일 진실 공급원이다.

필드설명
guid거래 당사자(claimant)
directioncredit(입금/수입) 또는 debit(출금/지출)
amount거래 금액
fs_account계정과목 — bs-cash(자산), pl-purchase(비용), pl-revenue(수익) 등 IASB 정렬
counterpart거래 상대방(P2P 이체·구매 시)
sourcemint(충전) · market(구매) · gdc_transfer(이체) · ai_usage(AI사용료)
tx_id, block_hash원장 추적용 식별자
l1_node기록을 발생시킨 L1 노드

쓰기 경로 3곳(전부 pb_hooks/main.pb.js)

  • /api/tx — 마켓 구매·P2P 이체(source가 purpose 유무로 gdc_transfer/market 결정)
  • /api/mint — GDC 충전(direction: credit, fs_account: bs-cash, source: mint)
  • /api/ai-charge — AI 사용료(direction: debit, fs_account: pl-purchase, source: ai_usage)

세 경로 모두 market-proxy의 LedgerWriter DO (guid 단위 직렬화)를 거쳐 기록한다 — PocketBase 내부에서 직접 dao().saveRecord()를 호출하면 해시체인 훅을 건너뛰고 동시쓰기 경합이 생기는 문제가 있어 HTTP 호출로 우회한다. skip_ledger=true 플래그로, 에스크로처럼 호출자가 자기만의 3행(buyer/seller/platform) 원장을 이미 따로 기록하는 경우 자동 기장을 건너뛸 수 있다(이중기장 방지).

/ledger/reconcile(대사용)은 요약 통계만 반환하고 개별 원본 행을 노출하지 않으므로, 지갑 화면용으로 별도 신설한 것. Gopang Wallet은 이 엔드포인트와 /biz/charge-status (pending 상태만)를 합쳐 하나의 타임라인으로 렌더링한다(§⑨).

BIVM 불변식

설계 의도 Σ차변 = Σ대변 불변식 검증(src/openhash/bivm.js) — 출금 합과 입금 합이 다른 거래는 자동 거부되어야 한다는 원칙. GDC 저장소 자체엔 "BIVM"이라는 정확한 명칭의 구현이 확인되지 않았고, 위반 시 슬래싱(페널티) 로직도 미확인 상태 — 후속 검증 필요 항목으로 남겨둔다.

⑨ Frontend
프론트엔드 — Gopang Wallet

Gopang Wallet 시트 (webapp.html → settings.js)

openGopangWallet()(src/gopang/ui/settings.js)이 렌더링을 전담한다. 열릴 때마다 wallet.refreshBalanceUI()로 서버 재대사 후, /biz/charge-status(pending만 필터)와 /wallet/ledger-history(확정된 모든 거래)를 병합해 하나의 시간순 타임라인을 만든다. 지출/수입 합계는 죽은 필드 (fs['pl-purchase']/fs['pl-revenue'] — 실제로 값을 쓰는 코드가 전무했던 필드)를 버리고 ledger_entries의 실제 direction으로 정직하게 재집계한다.

거래 상세 슬라이드아웃 패널

타임라인 항목을 탭하면 _openTxDetail(idx)가 #charge-detail-overlay(기존 .account-delete-overlay와 동일한 backdrop+drawer+translateX 슬라이드아웃 패턴, z-index 1001로 설정 시트 위에 뜸)를 채운다. 6하원칙(누가/언제/어디서/ 무엇을/어떻게/왜) 형식이며, ledger_entries의 counterpart·source·direction을 그대로 매핑해 서버 재조회 없이 즉시 렌더링한다.

usage.html — 충전 신청 화면

충전 신청 후 5초 간격으로 /biz/charge-status를 폴링하다 matched가 되면 즉시 안내 문구를 띄운다. 모바일 브라우저가 백그라운드 탭의 타이머를 억제하는 문제 대응으로, document.visibilitychange 이벤트로 탭이 다시 보이는 순간 즉시 한 번 더 확인하는 로직도 추가돼 있다.

푸시 구독 필수화

usage.html 로드 시 Notification.permission이 'default'(미확인)면 자동으로 구독을 시도한다. 거부/미등록 상태면 화면 상단에 눈에 띄는 경고 배너 + "지금 켜기" 재시도 버튼을 계속 노출한다. iOS 미설치 상태에서는 권한 요청 대신 설치 안내로 완전히 문구를 바꾼다(§⑤).

시크릿 재설정 시 원칙

  • Cloudflare Workers 시크릿은 쓰기 전용 — CLI로 값을 조회할 방법이 없다(wrangler secret list는 이름만 보여줌). 두 값이 같아야 하는 경우(예: MINT_SECRET) 추측 대신 새 값을 생성해 양쪽에 동일하게 재설정하는 게 가장 확실하다.
  • ADMIN_ACTION_SECRET 교체 시, 그 값을 쓰는 모든 클라이언트(관리자 알림캡처 안드로이드 앱 등)도 함께 갱신해야 한다 — 안 하면 조용히 403 FORBIDDEN으로 실패한다.
  • 진단이 막히면 SHA-256 해시만 비교하는 임시 디버그 엔드포인트를 만들어 원문 노출 없이 두 값의 일치 여부를 확인할 수 있다(단, 확인 후 반드시 제거).

⑫ Troubleshooting
실전 버그 8선 — 근본원인·수정
2026-08-28 세션에서 실사용 재현으로 발견·수정한 순서대로
  1. hydrateFromServer 로그인시만 호출 — AI 채팅 차감·충전 후 화면 잔액 미반영. refreshBalanceUI() 신설로 AI 응답 완료·설정 패널·지갑 시트 진입 시마다 재대사하도록 배선.
  2. 스트리밍 응답의 구조적 제약 — SSE 스트림은 이미 클라이언트로 전달된 뒤 서버 정산이 fire-and-forget으로 도는 구조라, 서버가 응답에 새 잔액을 실어 보낼 방법이 없음. 클라이언트가 완료 1.5초 후 재조회하는 방식으로 우회.
  3. 은행 "보내는 분 표시" 10자 제한 — 예금주 실명 자동 첨부로 무작위 코드가 항상 잘림. 전화번호 뒷 8자리 매칭키로 전면 재설계(§④).
  4. 전화번호 매칭키의 다중 pending 확정 오류 — 매칭키가 사용자당 고정값이라 여러 신청 중 엉뚱한(오래된) 게 확정됨. 새 신청 시 이전 pending 자동 취소 + sort=-created 이중 방어.
  5. 마스킹 계좌번호 오탐 — "*" 뒤 숫자 8자리를 매칭키로 오인. 부정 후방탐색으로 제외(§④).
  6. 모바일 백그라운드 타이머 억제 — 은행 앱 왕복 중 폴링 타이머가 멈춰 확정을 못 잡음. visibilitychange 이벤트로 탭 복귀 즉시 재확인.
  7. ctx.waitUntil() 누락으로 푸시 유실 — 가장 근본적인 버그(§⑤). fire-and-forget promise가 Workers 실행종료로 잘려나감. ctx 관통 배선으로 해결.
  8. 거래내역·last_tx_id 죽은 필드 — 마켓 구매용으로 설계됐다가 실제로 값을 쓰는 코드가 전무. 실제 회계 원장 ledger_entries 기반으로 전면 교체(§⑦, §⑨).
공통 교훈
8개 버그 중 절반 이상이 "코드 리뷰만으로는 안 보이고 실사용 재현 테스트를 해야만 드러나는 종류"였다(은행 SMS 실제 포맷, 모바일 OS의 백그라운드 정책, Cloudflare Workers의 실행 컨텍스트 수명). 신규 기능은 반드시 실제 기기·실제 은행 계좌로 엔드투엔드 재현 테스트를 거칠 것 — 시뮬레이션(PowerShell로 가짜 텍스트 전송 등)만으로는 이런 클래스의 버그를 못 잡는다.
