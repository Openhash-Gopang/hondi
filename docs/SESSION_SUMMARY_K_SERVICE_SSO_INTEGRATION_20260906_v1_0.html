"한 시스템에 인증하면 다른 K-서비스도 제한 없이 접근할 수 있어야 한다"는 요청에서 출발해, 먼저 현재 상태를 조사했다. 결과: K-Plan·K-Law·K-Mail·hondi.net GDC 대시보드 네 곳이 똑같은 전화번호 OTP 로그인을 각자 복붙 구현해 서로 몰랐고, 원래 크로스 도메인용으로 있던 고팡 지갑 SSO는 토큰 파라미터명 불일치 버그로 고장난 채 방치돼 있었다. 전화번호 인증 방식을 표준으로 확정하고, .hondi.net 도메인 쿠키로 세션을 공유하는 단일 공용 모듈(k-service-auth-client.js)을 만들어 네 곳 모두 교체했다. 배포 과정에서 겪은 압축파일 인코딩 사고까지 포함해, 다음에 이 영역을 다시 건드릴 사람이 같은 조사를 반복하지 않도록 정리한다.

Overview
이 문서가 왜 있는가

"인증 모듈을 하나로 통합하고 SSO가 되게 하라"는 요청은 겉보기엔 단순했지만, 막상 조사해 보니 이미 SSO용으로 설계된 시스템이 있었는데 아무도 모르게 고장나 있었고, 그래서 다들 각자 새로 만들어 쓰고 있었다는 것이 실제 원인이었다. 이 문서는 (1) 그 조사 과정과 발견, (2) 왜 기존 시스템을 고치는 대신 새 방식을 택했는지, (3) 실제로 무엇을 얼마나 바꿨는지, (4) 배포 중 겪은 사고까지 순서대로 기록한다. 다음에 K-서비스를 하나 더 추가하거나 로그인 관련 버그를 마주친 사람은 이 문서 하나로 전체 그림을 파악할 수 있어야 한다는 목표로 썼다.

① 현재 상태 조사
왜 SSO가 전혀 안 되고 있었는가

서버 쪽 신원(guid, PocketBase profiles 컬렉션)은 이미 하나로 통합돼 있었다. 문제는 그 guid에 도달하는 클라이언트 프로토콜이 두 종류였고, 그중 하나는 서비스마다 따로 구현돼 있었다는 것이다.

프로토콜 A — 고팡 지갑 SSO(Ed25519, 원조 시스템)

hondi.net/auth/silent-auth.html + subsystem-auth.js + gopang-sso.js. 원래 크로스 도메인 SSO를 위해 설계된 유일한 경로였다(iframe + postMessage 릴레이로 hondi.net의 로그인을 서브도메인에 전파). 그런데 silent-auth.html이 반환하는 파라미터명이 gopang_token인데 gopang-sso.js가 기대하는 이름은 gwp_token — 이름 불일치로 무한 리다이렉트 루프에 빠지는 버그가 있었다. K-Plan·K-Mail 코드에는 이 버그를 우회하려 data-required="false"로 꺼둔 주석이 그대로 남아 있었다.

프로토콜 B — phone_verify_token(SMS OTP)

POST /biz/phone-otp-verify → 서버가 서명한 토큰 발급 → e164로 profiles에서 guid 조회. K-Plan·K-Law·K-Mail 세 곳이 각각 독자적으로 재구현했고, 토큰을 저장하는 sessionStorage 키도 전부 달랐다: kplan_phone_verify_token / klaw_phone_verify_token / kmail_phone_verify_token(모두 오리진별로 격리됨). 크로스 도메인 릴레이가 아예 없어서 한 곳에 로그인해도 다른 곳은 몰랐다 — 같은 프로토콜을 셋이 각자 베껴 쓴 것뿐이었다. hondi.net 대시보드의 GDC 잔액 모달도 같은 프로토콜을 쓰지만 세션 저장조차 안 하는 1회성 조회였다(4번째 독립 구현).

판별 포인트
"인증 모듈이 여러 개"였던 게 아니라, 똑같은 프로토콜 B를 4곳이 복붙해서 따로 만들었고, 원래 크로스 도메인용이던 프로토콜 A는 버그로 죽어 있던 것이 실제 상황이었다. 앞으로 로그인 관련 이슈를 진단할 때는 먼저 어느 프로토콜을 쓰는 코드인지부터 확인한다.
② 설계 결정
iframe 릴레이 대신 도메인 쿠키를 택한 이유

두 가지 선택지가 있었다: (A) 프로토콜 A(고팡 지갑 SSO)의 이름 불일치 버그를 고쳐서 그걸 기반으로 통일, (B) 프로토콜 B(전화번호 방식)를 기반으로 새 크로스 도메인 세션 공유를 만들고 프로토콜 A는 그대로 둔다. B를 선택했다 — 사용자 경험상 이미지로 제시된 plan.hondi.net 방식(전화번호 뒷자리 8자)이 더 단순했고, 모든 K-서비스와 hondi.net이 같은 워커(worker.js)를 공유하고 전부 *.hondi.net 서브도메인이라는 점을 이용하면 iframe·postMessage 없이도 SSO가 가능했기 때문이다.

메커니즘 — .hondi.net 도메인 쿠키

로그인 성공 시 phone_verify_token을 document.cookie에 Domain=.hondi.net으로 직접 써 넣는다. 이 도메인 속성을 가진 쿠키는 hondi.net·plan.hondi.net·klaw.hondi.net·mail.hondi.net 등 모든 서브도메인에서 브라우저가 자동으로 공유한다 — 서버 쪽 변경(worker.js 수정)이 전혀 필요 없다. 각 서비스는 공용 클라이언트 모듈 하나만 불러오면, 그 모듈이 쿠키에서 토큰을 읽어 "이미 로그인됨"을 자동 인식한다.

검증됨
이 메커니즘은 순수 클라이언트 로직이라 Secure 속성이 붙은 쿠키는 HTTPS 환경에서만 정상 동작한다 — 로컬 HTTP 테스트에서는 브라우저가 쿠키 자체를 조용히 거부해 처음에 실패한 것처럼 보였다(§⑤ 검증 방법 참고, 자체 서명 인증서로 우회해 재현·검증함).
③ 신설
공용 모듈 — auth/k-service-auth-client.js

배포 위치는 https://hondi.net/auth/k-service-auth-client.js다. K-Plan의 device-link(웹푸시 승인) + OTP 흐름을 그대로 흡수해 하나의 자체 완결형 모듈로 만들었다 — 페이지에 로그인 오버레이 HTML을 미리 준비할 필요가 없다, 모듈이 필요할 때 스스로 DOM을 주입한다.

사용법

<script>
  window.K_AUTH_CONFIG = {
    serviceLabel: 'K-Law',       // 로그인 UI에 표시될 서비스명(선택)
    enableDeviceLink: false,     // 웹푸시 승인 로그인 지원 여부(선택, 기본 true)
  };
</script>
<script src="https://hondi.net/auth/k-service-auth-client.js"></script>

공개 API (window.KAuth)

  • await KAuth.ensureLogin() — 로그인 안 돼 있으면 오버레이를 띄우고 완료까지 대기, 토큰 문자열 반환
  • KAuth.getToken() — 현재 유효한 토큰(없으면 null), 오버레이 없음
  • KAuth.hasValidLogin() — boolean
  • KAuth.logout() — 로그아웃(쿠키 삭제)
  • await KAuth.fetchWithAuth(url, opts) — phone_verify_token을 자동 첨부해 fetch, 일시적 인증 오류는 조용히 재시도, 진짜 만료·무효일 때만 재로그인 오버레이 표시

이 모듈에 넣지 않은 것

서버측 판정 로직(worker.js의 _resolveGuidFromPhoneVerifyToken, src/worker/k-service-auth.js)은 그대로 뒀다 — 이미 여러 K-서비스가 공유하는 별도 서버 모듈이고, 이번 작업 범위는 클라이언트 쪽 중복 제거와 SSO였다. 두 문서를 같이 보면 인증 스택 전체가 그려진다(§관련 문서 참고).

④ 전환
K-Plan·K-Law·K-Mail·GDC 대시보드 4곳

네 곳 모두 같은 패턴으로 전환했다: 자체 로그인 오버레이 HTML/CSS와 OTP·device-link 함수, 서비스별 sessionStorage 토큰을 제거하고, KAuth.getToken() / KAuth.hasValidLogin() / KAuth.ensureLogin() 호출로 치환했다. 각 서비스의 재시도·재로그인 판단 로직(일시적 오류는 같은 토큰으로 재시도, 진짜 만료일 때만 재로그인 유도)은 그대로 보존했다 — 이건 여러 사고실험을 거쳐 다듬어진 로직이라 새로 짤 이유가 없었다.

K-Plan(plan/webapp.html)

device-link + OTP 로그인 UI/로직 전체 제거, 깨져 있던 고팡 SSO(subsystem-auth.js) 로드도 제거.

K-Law(klaw/webapp.html)

OTP 로그인 UI/로직 제거. 참고: 이 페이지는 고팡 SSO를 필수 모드로 로드하고 있었는데(다른 곳은 data-required="false"였음), 제거하면서 klawUser/_klawGuid()/ window._onGopangAuth(닉네임 표시·PDV 로깅에 쓰이던 지갑 guid)가 더 이상 채워지지 않게 됐다 — 실제 상담 인증에는 원래도 영향 없었다(서버가 phone_verify_token에서 직접 guid를 도출하고 클라이언트가 보낸 guid는 버림). 코드에 주석으로 남겨뒀고, 닉네임 표시 품질 저하가 문제되면 별도 후속 작업이 필요하다.

K-Mail(mail/webapp.html)

device-link + OTP 로그인 UI/로직 제거. 삭제된 로그인 오버레이 엘리먼트를 참조하던 죽은 이벤트 리스너도 함께 정리. 참고: 병합 시점에 다른 협업자가 로그인 팝업 전화번호 입력창에 인라인 아이콘을 붙이는 개선을 이미 올려둔 상태였는데, 이번 통합으로 그 UI가 공용 오버레이로 자연스럽게 대체됐다(의도된 결과, 회귀 아님).

hondi.net GDC 대시보드(desktop.html)

"내 GDC 대시보드" 모달이 매번 자체 OTP를 새로 돌리는 대신 KAuth.ensureLogin()을 쓰도록 변경 — 전화번호·인증번호 입력 패널을 "확인 중…" 로딩 패널로 대체했다. "다른 번호로 조회" 버튼은 KAuth.logout() 후 재로그인하도록 변경.

⑤ 검증
로컬 크로스 도메인 SSO + Playwright 시나리오

크로스 서브도메인 쿠키 공유 검증

실제 *.hondi.net 환경 없이 메커니즘을 검증하기 위해, /etc/hosts에 a.testauth.local· b.testauth.local 두 가짜 서브도메인을 만들고, 자체 서명 HTTPS 서버(Secure 쿠키 검증을 위해 plain HTTP가 아닌 HTTPS 필요)로 서빙했다. 모듈의 쿠키 도메인은 K_AUTH_CONFIG.cookieDomain으로 오버라이드 가능하게 만들어 테스트 전용으로 .testauth.local을 지정했다(프로덕션 기본값은 .hondi.net). Playwright로 A에서 로그인 → 쿠키가 .testauth.local 도메인으로 설정됨 확인 → B를 방문했을 때 같은 토큰으로 즉시 로그인 상태임을 확인했다.

GDC 대시보드 실사용 시나리오(Playwright)

desktop.html을 로컬로 띄우고 OTP 엔드포인트를 모킹해 두 시나리오를 재현했다: (1) 처음 "내 GDC 대시보드"를 열면 로그인 오버레이가 뜨고, 인증 후 잔액이 표시된다. (2) 모달을 닫았다 다시 열면 로그인 절차 없이 곧바로 잔액이 표시된다 — 요청하신 "한 곳에서 인증하면 다른 곳도 자동 로그인"이 실제로 동작함을 스크린샷과 함께 확인했다.

아직 안 한 것
로컬 검증은 가짜 서브도메인으로 메커니즘 자체(쿠키 도메인 공유)를 확인한 것이고, 실제 배포된 hondi.net· plan.hondi.net·klaw.hondi.net·mail.hondi.net 간 실사용자 환경에서의 SSO 확인은 아직 안 됐다. 다음에 이 기능을 다루는 사람은 실제 도메인에서 한 번 확인해 볼 것.
⑥ 배포 사고
압축 파일 한글 파일명이 Windows에서 깨짐

패치 5개를 zip(Linux CLI)으로 묶어 전달했는데, 받는 쪽 PowerShell의 Expand-Archive가 "경로에 잘못된 문자가 있습니다" 오류로 압축을 아예 풀지 못했다. 원인: Linux zip이 한글 파일명을 zip 항목 헤더에 쓸 때 UTF-8 플래그를 확실히 세팅하지 않아, Windows의 .NET 압축 해제기가 이를 오인식 — 압축을 새로 만들 때 파일명을 순수 영문/숫자로만 지어야 이런 문제를 원천 차단한다는 것을 실사로 확인했다.

부작용은 없었다 — 압축이 안 풀려 patch 파일 자체를 못 찾았을 뿐이라, git am이 전부 "파일 없음"으로 실패했고, 이후 git push· gh pr create는 커밋 없는 빈 브랜치로 진행돼 "No commits between main and feature/…"로 자동 실패했다 — 저장소에는 아무 영향이 없었다. 다만 그 사이 다른 협업자들이 plan·klaw·mail의 같은 파일에 상당한 변경(각 300~700줄)을 올린 상태였어서, 재배포 전에 최신 main 기준으로 패치가 여전히 충돌 없이 적용되는지 재검증이 필요했다(4개 저장소 모두 재검증 후 문제없이 병합됨).

체크리스트
다음에 patch나 파일 묶음을 압축해 전달할 때: (1) 압축 내부 파일명은 영문/숫자/하이픈만 사용, (2) 한글 설명은 파일 내용(커밋 메시지·문서 본문)에만 담는다, (3) 가능하면 Python zipfile 모듈로 압축하면 Windows 호환성이 가장 안정적이다(Linux zip CLI의 기본 인코딩 동작보다 예측 가능).
⑦ 조사 결과
대상 아님으로 확인 — K-Telecom 등 5개 저장소

"아직 인증 게이트가 없는 나머지 K-서비스에도 적용"이라는 다음 단계를 진행하기 전, K-Telecom·K-Search·K-Biz·K-Watch· K-Job(각자 별도 저장소) index.html을 직접 열어 확인했다. 전부 자체 로그인 기능이 전혀 없는 순수 소개 페이지였다 — "hondi.net 지갑 로그인 필요"라고 안내만 하고, 실제 이용은 hondi.net/desktop.html#k-services(K-서비스 탭)에서 이루어지는 구조다. 그 K-서비스 탭 (pages/k-services.html) 자체도 인증이 필요한 기능이 없어, 이번 통합 대상에서 제외했다 — 별도 조치가 필요하지 않다.

Lessons
교훈
  • "인증 시스템이 여러 개"로 보이면, 먼저 서버 쪽 신원이 이미 통합돼 있는지부터 확인한다. 이번 경우 guid는 하나였고 클라이언트 프로토콜만 갈라져 있었다 — 문제의 크기를 정확히 알아야 과잉 리팩터링(서버까지 다 뜯어고치는 것)을 피할 수 있다.
  • "원래 있던 SSO가 왜 안 쓰이고 있었는가"를 반드시 묻는다. 다들 우회해서 새로 만들고 있다면, 십중팔구 원래 것이 고장나 있다는 신호다 — 고장난 이유를 모르고 그 위에 또 새 걸 얹으면 나중에 셋이 된다.
  • 브라우저 쿠키의 Domain 속성은 서브도메인 SSO에 서버 변경 없이도 충분할 수 있다. iframe· postMessage 릴레이는 강력하지만 그만큼 실패 지점이 많다(이번 사례가 정확히 그것으로 고장났다) — 더 단순한 메커니즘으로 같은 목표를 달성할 수 있는지 먼저 검토한다.
  • 로컬에서 크로스 도메인 기능을 검증하려면 /etc/hosts + 가짜 서브도메인 + (Secure 쿠키가 걸려 있다면) 자체 서명 HTTPS가 필요하다. plain HTTP로는 재현되지 않는 실패를 "안 된다"고 오판할 수 있다.
  • 배포용 압축 파일의 내부 항목명은 항상 순수 ASCII로 짓는다. 압축 도구·OS 조합에 따라 비ASCII 파일명 인코딩이 깨질 수 있고, 실사용자 환경(Windows)에서 재현하기 전까지는 이 문제가 잘 드러나지 않는다.
  • 공유 파일에 다른 협업자의 최신 변경이 있을 수 있다는 걸 항상 가정한다. 패치를 만든 시점과 적용하는 시점 사이에 시간차가 있으면, 적용 직전에 최신 main 기준으로 재검증하는 습관이 사고를 막는다.
