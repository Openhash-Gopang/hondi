PDV 저장 구조 조사

2026-11-07 · 기준: Openhash-Gopang/hondi main, Openhash-Gopang/mail main · 코드 읽기 기반(운영 서버·DB는 직접 확인하지 못함)

1. 핵심 결론

PDV 원문은 지금 "그 기기의 브라우저 IndexedDB"에만 있습니다. 서버(L1 PocketBase)에는 해시와 메타데이터만 올라갑니다(PR #461 "해시전용 재설계"). 기기 간 동기화와 클라우드 보관본이 없습니다. 그래서 PC로 로그인해도 폰의 PDV는 보이지 않고, PC에서 만든 서류 초안은 PC에만 남습니다.

3. 이 구조에서 생기는 일

  1. PC 로그인은 PDV 접근이 아닙니다. KAuth 로그인은 토큰(30일)만 주고, 기기마다 IndexedDB가 따로이므로 PC의 PDV는 비어 있습니다. key_transfer로 개인키를 옮겨도 PDV 데이터는 따라오지 않습니다.
  2. 초안·첨부가 기기에 묶입니다. PC에서 쓰던 서류 초안을 폰에서 이어 쓸 수 없습니다(그 반대도 같음).
  3. 브라우저 데이터 삭제 = PDV 소실. 서버에는 해시뿐이라 복구할 원문이 없습니다. IndexedDB는 브라우저가 저장 공간 부족 시 정리할 수도 있습니다(영구 저장 요청 여부는 확인하지 못함).
  4. "사용자마다 PDV 저장 공간을 할당하고 LLM 이용 이력을 이후 지시·질의에 참조"(2026-10-26 요구)는 현재 구조로 불가. 서버가 평문을 못 읽는 원칙과 충돌하므로, 서버 보관은 클라이언트에서 암호화한 사본이어야 합니다.
  5. 폰 분실 시 PDV도 함께 사라집니다. 지갑 백업 키가 선택 저장(2026-11-06)으로 바뀐 만큼, 키와 PDV의 복구 경로를 같이 설계해야 합니다.

4. 설계 선택지

A. 폰 원본 + PC는 폰에서 가져오기B. 클라우드 암호화 사본(E2E)C. 하이브리드 (권장 검토)
구조원본은 폰. PC가 필요할 때 폰에 요청(승인 시 전달)모든 기기가 암호화한 PDV 사본을 서버에 올리고 내려받음. 서버는 암호문만 보관폰이 원본. 클라우드엔 암호화 백업 사본. PC는 폰 승인 후 사본을 내려받아 세션 동안만 복호화해 사용
키필요 없음(전달 시 일회용 키)지갑 개인키에서 PDV 암호화 키를 유도(HKDF). 키를 잃으면 사본도 못 엽니다B와 같음 + PC에는 키를 영구 보관하지 않음
장점서버에 PDV 사본 없음. 구현 단순PC 단독 사용, 분실·초기화 복구, LLM 이력 참조에 적합PC 로그인=폰 승인 원칙과 일치. 분실 복구와 기기 간 이어쓰기 가능
단점폰이 꺼져 있으면 PC가 못 씀. 분실 시 복구 불가. 대용량(첨부) 전송 부담키 관리 부담이 큼(키 분실=영구 소실). 암호문도 보관·삭제 정책·비용이 생김구현량이 가장 큼. 동기화 충돌 처리 필요

5. 정해야 할 것

  1. PC가 PDV 원문을 볼 수 있어야 하는가 — 예: 서류 초안 이어쓰기, 길잡이 기록. 아니오면 A(또는 현 구조 유지).
  2. 서버에 암호화 사본을 둘 것인가 — 분실 복구와 LLM 이력 참조를 원하면 필요. "서버는 평문을 못 읽는다" 원칙은 유지됩니다(클라이언트 암호화).
  3. PC에 개인키를 영구 보관할지(key_transfer) — 아니오(세션만)로 하면 PC 로그인 단순화와 맞고, PDV 복호화도 세션 단위가 됩니다.
  4. 저장 대상 범위 — 상호작용 로그, 서류 초안·첨부, IDV 자격증명 중 무엇을 동기화할지. IDV는 민감도가 높아 별도 결정 권장.
  5. 복구 방식 — 키 분실 시 PDV는 어떻게 할지(백업 키 선택 저장 연계).

확인하지 못한 것: PocketBase pdv_records 실제 스키마·용량, 브라우저의 영구 저장(navigator.storage.persist) 요청 여부, 서버에 암호문 저장 컬렉션 존재 여부(코드 검색에서는 발견되지 않음).
