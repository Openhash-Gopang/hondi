재무제표는 "판다는 것"만 기록했다 — 산다는 것은 아무도 적어두지 않았다

대시보드에 재무제표 탭(손익계산서·대차대조표·현금흐름표)을 새로 달면서, 기존 handleSettleLedger가 판매자 매출만 집계하고 구매자 매입은 서버에 아예 적재되지 않는다는 걸 발견했다. 고치는 김에 "재무제표가 바뀔 때마다 그 순간을 git commit처럼 해시체이닝해서 OpenHash에 앵커링하고, 언제든 재현·검증할 수 있게 하라"는 지시를 받아 구현했다. 100건 라이브 스모크 테스트로 검증하는 과정에서, 코드는 몇 주 전부터 있었지만 실제로는 단 한 번도 실행된 적 없던 인프라 결함을 두 개 더 찾아 고쳤다.

Overview
이 문서가 왜 있는가

이 문서는 재무제표 탭이나 OpenHash 앵커링의 사용법을 다루지 않는다. 오늘 세션에서 반복적으로 확인된 패턴 — "거래는 항상 양방향인데, 한쪽만 기록하는 코드는 절반의 진실만 말한다"와 "코드가 저장소에 존재하는 것과 실제로 실행되는 것은 완전히 다른 주장이며, 후자는 반드시 별도로 확인해야 한다"는 두 교훈을 기록해두기 위한 것이다.

이 문서를 읽어야 하는 상황
두 당사자(구매자/판매자, 발신자/수신자 등)가 관여하는 거래를 한쪽 관점에서만 기록하는 코드를 리뷰할 때 / PocketBase에 새 컬렉션을 쓰는 코드를 배포했는데 조용히 실패할 때 / Cloudflare Worker의 scheduled() 핸들러가 실행되는지 의심스러울 때 / 검증(verify) 로직을 새로 만들었는데 "너무 쉽게 통과"해서 찜찜할 때 / 로컬 작업트리에 여러 작업이 섞여 있는 상태로 새 브랜치를 팔 때.
Goal
오늘 세션의 목표와 흐름
  1. 출발점 — 대시보드에 재무제표 탭(손익계산서/대차대조표/현금흐름표)을 신설해 달라는 요청. 기존 GDC 재무 인프라 (/biz/balance, /biz/financials, /biz/settle-ledger, /biz/tx-history)를 그대로 재사용해 UI만 새로 붙임.
  2. 설계 오류 발견 — "재무제표는 구매자와 판매자 모두 작성하며, 반드시 거래 전표를 상호 교차검증해야 한다"는 지시를 받고 코드를 다시 보니, 판매자 쪽 (pl-revenue/pl-cogs)만 pending_claims에 적재되고 구매자 쪽 (pl-purchase)은 handleBizOrder에서 그냥 버려지고 있었음 → 대칭적으로 수정.
  3. 결제 보안 메커니즘 확인 — "GDC 이체/결제 시 보안 메커니즘을 찾아보라"는 지시로 /api/tx의 TOFU·tx_hash 검증·Ed25519 서명·prev_settle_hash 체이닝· 이중지불 탐지·computeBalance 원장 재생 6단계를 확인. 이 6단계는 "결제 순간의 무결성"만 지키고 "그 결제가 재무제표에 정확히 반영됐는가"는 별도 문제로 뚫려 있다는 게 드러남.
  4. OpenHash 앵커링 신설 — "재무제표 변동 시점마다 git commit과 동일한 구조(content_hash + prev_hash 체이닝 → commit_hash)로 OpenHash에 기록하고, 언제든 재현·검증 가능하게 하라"는 지시. 기존 PDV 머클 앵커링 (anchorL1MerkleRoot)과 완전히 동일한 패턴을 복제해 fs_snapshots/fs_merkle_anchors 전용 파이프라인 신설.
  5. mockup 스모크 테스트 — 실제 SMS 인증 계정 대신, ADMIN_ACTION_SECRET으로 보호되는 /admin/test-register-profile을 신설해 구매자· 판매자 mockup 계정을 즉석 생성 → 100건 실거래로 대칭 기록 검증.
  6. 인프라 결함 2건 발견·수정 — 스모크 테스트 도중 fs_snapshots 컬렉션 자체가 PocketBase에 없었던 것, wrangler.toml에 cron 트리거 선언이 아예 없어 scheduled()가 배포 이후 한 번도 자동 실행된 적 없었던 것을 발견·수정.
  7. 네거티브 테스트 — "너무 쉽게 통과한 게 이상하다"는 지적에, 없는 seq/guid를 넣어 실제로 거부되는지 확인 → 검증 로직 자체의 신뢰성 확인.
Lesson ①
판매만 기록하고 구매는 버리는 장부 — buyer_claim 누락

pb_hooks/main.pb.js의 /api/tx는 거래 하나가 성사될 때마다 buyerClaim과 sellerClaim을 완전히 대칭으로 만들어 Worker에 돌려주고 있었다 (fs_account: "pl-purchase" vs "pl-revenue", 부호만 반대). 그런데 worker.js의 handleBizOrder는 seller_claim만 pending_claims에 적재하고 buyer_claim은 그냥 버렸다 — 데이터는 이미 만들어지고 있었는데, 저장하는 코드 한 줄이 비대칭이었다.

증상
같은 guid가 "구매자"로만 활동해도 손익계산서엔 지출이 하나도 안 잡히고 pl-revenue가 계속 0으로 남았다 — "설계 오류"라고 지적받기 전까지는 손익계산서 자체가 항상 텅 비어 보이는 게 정상인 줄 알기 쉬운 상태였다.

수정

  • handleBizOrder — seller_claim 적재 블록과 완전히 대칭으로 buyer_claim도 claimant: from_guid로 별도 pending_claims 레코드에 적재.
  • handleSettleLedger — 집계 루프에 pl-purchase(debit) 분기 추가, 당기순이익 = 매출총이익 − 판관비 − 매입으로 재계산. 매입(구매 시점 지출 전체)과 매출원가(판매 시점에 매칭된 원가만)는 기준이 다르다는 점을 주석·UI 각주로 명시 — 같은 재고를 사고 되팔면 두 계정에 걸쳐 보일 수 있으며, 이건 재고자산 계정이 아직 없어 생기는 의도적 범위 제한이다.

검증

100건 실거래 후: 구매자 pl-purchase = 100(기대값 정확히 일치), 판매자 pl-revenue ≈ 96.99999999999991 (플랫폼 수수료 3% 차감 후 기대값 97.0과 부동소수점 표시오차 수준에서 정확히 일치).

Lesson ②
재무제표를 git commit처럼 — 해시체이닝 + OpenHash 앵커링

지시받은 요구사항: 재무제표가 바뀔 때마다 그 hash를 OpenHash 네트워크에 기록해, (a) 저장된 재무제표 해시와 OpenHash에 기록된 해시가 일치하는지, (b) 그 해시가 실제 재무제표 데이터에서 인출되는지 — 두 가지를 언제든 검증할 수 있게 하라. git commit(내용 해시 + 부모 해시 → 커밋 해시, 언제든 재계산 가능)과 동일한 구조다.

새 메커니즘을 발명하지 않고, 이미 있던 PDV 머클 앵커링 (anchorL1MerkleRoot / GET /merkle/verify, 2026-07-14 신설)을 그대로 복제했다 — leaf가 PDV의 block_hash 대신 재무제표 스냅샷의 commit_hash라는 점만 다르다.

구성 요소역할
fs_snapshots (신규 컬렉션)handleSettleLedger가 pl 재집계 때마다 기록. content_hash(이번 pl+bs 내용) + prev_hash(직전 스냅샷의 commit_hash) → commit_hash
anchorFsSnapshotsMerkleRoot10분 주기 크론. 미앵커링 commit_hash들을 머클트리로 묶어 fs_merkle_anchors에 저장
GET /fs/verify?guid=&seq=(a) anchor_valid — 앵커의 머클루트를 배치 안에서 재계산해도 같은가 / (b) self_consistent — 저장된 snapshot 원본에서 content_hash·commit_hash를 다시 계산해도 저장값과 같은가. 서명 불필요(guid만으로 조회 — /biz/balance와 동일한 공개 조회 원칙)

buyer/seller가 같은 10분 창에 스냅샷을 만들면 같은 merkle_root·anchored_at을 공유한다 — 여러 거래가 같은 블록에 포함되면 같은 블록해시를 갖는 것과 같은 원리이며, 이는 정상 동작이지 버그가 아니다(이 지점을 두고 실제로 "너무 쉽게 통과한 것 아니냐"는 의심이 나왔고, 아래 Lesson ⑤에서 별도로 확인했다).

Lesson ③
코드는 있는데 테이블이 없었다 — PocketBase 컬렉션 마이그레이션 누락

handleSettleLedger가 fs_snapshots에 INSERT를 시도하는 코드는 처음부터 맞게 짜여 있었지만, 정작 그 컬렉션을 PocketBase에 만드는 pb_migrations/*.js 파일을 빠뜨렸다. INSERT는 try/catch로 감싸 실패해도 결제 자체를 막지 않도록 설계돼 있었는데(의도적으로 안전하게 만든 부분), 그 부작용으로 모든 settle-ledger 응답에서 "fs_snapshot": null이 계속 찍히는데도 아무도 알아채지 못했다 — 처음 100건 스모크 테스트가 끝날 때까지 발견되지 않았다.

수정
기존 pdv_records/pdv_merkle_anchors 마이그레이션을 그대로 모델 삼아 1793900300_created_fs_snapshots.js, 1793900400_created_fs_merkle_anchors.js 신설. 이 저장소는 pb_migrations/**가 main에 push되면 deploy-pb-migrations.yml이 자동으로 L1(hanlim) 서버에 SSH로 적용하도록 이미 구성돼 있어(2026-07-16 사고 재발 방지용), push 한 번으로 해결됐다.

일반화되는 교훈

"실패해도 주 기능을 막지 않도록 try/catch로 감싼 부가 기능"은 안전장치인 동시에 침묵의 실패를 만드는 장치다. 부가 기능이 실제로 성공하는지는 응답 필드(fs_snapshot가 계속 null인지)를 최소 한 번은 직접 눈으로 확인해야 한다 — "에러가 안 났다"는 "성공했다"의 증거가 아니다.

Lesson ④
scheduled()가 코드에 있어도 cron 선언이 없으면 절대 안 돈다

fs_snapshots 마이그레이션을 고친 뒤에도 /fs/verify가 15분 넘게 계속 NOT_ANCHORED_YET을 돌려줬다. 원인은 wrangler.toml에 [triggers]/crons 선언 자체가 없었던 것 — worker.js의 scheduled(event, env, ctx) 핸들러(안에 anchorL1MerkleRoot·anchorFsSnapshotsMerkleRoot 둘 다 있고, 코드 주석엔 "10분마다 돈다"고 적혀 있었음)는 wrangler.toml에 cron이 선언돼야만 Cloudflare가 실제로 호출한다. 선언이 없으면 함수가 존재해도 대시보드에서 수동으로 트리거를 설정해두지 않은 이상 배포 이후 단 한 번도 자동 실행된 적이 없다.

더 넓은 파급 — PDV 앵커링도 같은 상태였을 가능성
이 결함은 오늘 신설한 기능만의 문제가 아니다 — anchorL1MerkleRoot(PDV 머클 앵커링)는 2026-07-14부터 존재했는데, 같은 wrangler.toml을 공유하므로 대시보드에 별도 수동 Cron Trigger 설정이 없었다면 그 기능도 지금까지 한 번도 자동 실행되지 않았을 가능성이 높다. PDV 앵커링 상태를 별도로 점검할 필요가 있다(후속 과제 참고).

수정

[triggers]
crons = ["*/10 * * * *"]

wrangler.toml push만으로는 부족하고, wrangler deploy를 직접 실행해야 Cloudflare가 새 트리거를 반영한다 — 배포 로그 마지막 줄에 Deployed hondi-proxy triggers ... schedule: */10 * * * *가 찍히는 것으로 확인했다.

일반화되는 교훈

  • Cloudflare Workers에서 scheduled() 핸들러를 추가할 때는 코드 리뷰만으로 끝내지 말고, 반드시 wrangler.toml의 [triggers]와 배포 로그의 schedule: 줄까지 확인할 것.
  • "주석에 몇 분마다 돈다고 적혀 있다"는 "실제로 그 주기로 돈다"의 증거가 아니다 — 인프라 설정(IaC) 파일에 선언이 있는지가 유일한 증거다.
Lesson ⑤
"쉽게 통과"를 믿지 말고 네거티브 테스트로 검증 로직 자체를 검증하라

/fs/verify가 buyer/seller 둘 다 한 번에 valid: true를 돌려주자, "너무 쉽게 통과한 것 아니냐"는 의심이 제기됐다. 정상 케이스만 확인해서는 검증 로직이 진짜 동작하는지, 아니면 뭘 넣어도 통과시키는 허수아비인지 구분할 수 없다.

입력기대 결과실제 결과

4종 모두 정확히 구분됐고, 응답에 content_hash와 recomputed_content_hash, commit_hash와 recomputed_commit_hash, merkle_root와 anchor_recomputed_root가 각각 나란히 노출되도록 설계해뒀기 때문에, "서버가 그렇다고 말해서 믿는" 게 아니라 두 값이 실제로 같다는 걸 호출자가 직접 대조할 수 있었다.

일반화되는 교훈

검증(verify) 기능을 새로 만들 때는 정상 케이스 하나로 끝내지 말고, 최소 "존재하지 않는 대상", "필수값 누락" 두 가지는 반드시 같이 테스트할 것. 그리고 검증 응답에는 서버의 결론 (boolean)뿐 아니라 그 결론에 이른 재료(재계산값 vs 저장값)를 함께 노출해, 호출자가 서버의 판정을 맹신하지 않고 스스로 대조할 수 있게 설계할 것.

Lesson ⑥
브랜치 작업 전 git status 확인 — 무관한 커밋이 반복해서 묶여 들어간 사고

오늘 세션 중 git checkout -b로 새 브랜치를 팔 때마다, 로컬 작업트리에 남아있던 다른 무관한 작업(지문 인증 강화, profiles.e164 평문 제거 등)이 같이 커밋돼 같은 PR로 squash-merge되는 일이 두 번 반복됐다(PR #105, #107). gh pr create 시점에 뜬 Warning: 19 uncommitted changes가 그 흔적이었다.

내용 자체는 잘 만들어진 정당한 작업들이었지만, 의도한 변경과 무관한 작업이 별도 리뷰 없이 같은 PR에 묶여 들어갔다는 점은 문제다 — PR 하나가 "무엇을 위한 변경인지"를 더 이상 정확히 말해주지 못하게 된다.

일반화되는 교훈

  • git checkout -b 전에 항상 git status로 uncommitted 변경사항이 있는지 먼저 확인할 것.
  • 있다면, 그 변경사항부터 원래 있어야 할 브랜치에 먼저 커밋(또는 git stash)한 뒤 새 브랜치를 팔 것.
  • 이미 묶여 들어갔다면, git cherry-pick으로 필요한 커밋만 골라 옮기는 방식으로 복구 가능 — 오늘 두 번 다 이 방식으로 안전하게 정리했다(예: devdoc-session-summary-20260907 브랜치에 잘못 커밋됐던 fs_snapshots 마이그레이션을 git cherry-pick으로 main에만 옮김).
결과 — 검증된 사실
  • 검증됨 구매자·판매자 재무제표 대칭 기록 — 100건 실거래, 구매자 pl-purchase·판매자 pl-revenue가 플랫폼 수수료(3%)까지 정확히 반영되어 대칭 기록됨.
  • 검증됨 OpenHash 앵커링 — git-commit식 해시체이닝이 실제로 앵커링되고, 데이터→해시 재현(self_consistent)과 앵커→머클루트 재현(anchor_valid) 둘 다 독립 재계산으로 확인됨.
  • 검증됨 네거티브 테스트 4종 전부 정확히 구분 — 검증 로직이 허수아비가 아님을 확인.
  • 수정됨 fs_snapshots/fs_merkle_anchors PocketBase 컬렉션 마이그레이션 신설(1793900300, 1793900400).
  • 수정됨 wrangler.toml에 cron 트리거 (*/10 * * * *) 선언 추가 + 재배포로 반영 확인.

Reproduce
재현 방법 — 스모크 테스트 스크립트

아래 3개 스크립트가 오늘 세션에서 만든 순서대로다. 전부 PowerShell에서 python <파일명>로 실행한다 (사전 설치: pip install cryptography requests --break-system-packages).

1) smoketest_gdc_100tx.py — 1차 테스트(재무제표 대칭 기록)

ADMIN_SECRET에 ADMIN_ACTION_SECRET 값을 채운 뒤 실행. mockup 구매자·판매자 계정을 /admin/test-register-profile로 즉석 생성 → N_TX건 거래 → 양쪽 settle-ledger 재집계·financials 조회 → 수수료 반영 기대값과 자동 대조. balance_claimed은 항상 null로 보낸다(서버가 강제하지 않는 참고용 값이라 Python↔JS 부동소수점 표기 차이로 인한 TX_HASH_MISMATCH 위험을 없앰). 간헐적 실패는 새 nonce로 자동 재시도(최대 8회), 그래도 실패하면 그 거래만 건너뛰고 계속 진행한다.

2) verify_openhash_anchoring.py — 2차 테스트(OpenHash 앵커링)

1차 테스트에서 나온 guid로 /fs/verify를 호출. NOT_ANCHORED_YET이면 30초 간격으로 최대 15분간 자동 재시도(10분 크론 주기 + 여유). self_consistent· anchor_valid 둘 다 확인.

3) negative_test_fs_verify.py — 검증 로직 자체의 신뢰성 확인

존재하지 않는 seq/guid, 빈 guid 3종 + 정상 케이스 대조군 1종을 /fs/verify에 넣어, 비정상 입력이 실제로 거부되는지 확인.

주의
이 스크립트들은 프로덕션 hondi-proxy Worker와 실제 L1 원장에 진짜 블록을 남기는 라이브 테스트다. 처음 실행할 땐 N_TX를 3 정도로 낮춰 결과를 먼저 눈으로 확인한 뒤 100으로 올릴 것.
