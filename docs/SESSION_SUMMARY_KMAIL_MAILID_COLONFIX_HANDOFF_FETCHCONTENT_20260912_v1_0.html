발단은 사소했다 — K-Mail이 보여주는 "내 메일 주소"가 2601:db80:...@hondi.kr처럼 실사용 불가능한 형태라는 지적. 이걸 고치려고 사람이 읽을 수 있는 mail_id를 만들었는데, 그 과정에서 처음 만든 라이브 스모크테스트가 실제 발송 자체가 콜론 때문에 매번 실패하고 있었다는, 서비스 시작 이후 한 번도 걸린 적 없던 훨씬 심각한 버그를 우연히 잡아냈다. 그 수정을 검증하다 보니 이번엔 K-Address가 "메일 좀 보내줘"에 안내만 하고 끝내는 게 눈에 띄었고, 이건 혼디의 최상위 원칙(U0) 자체에 "다른 SP가 할 일이면 직접 호출하라"는 조항을 새로 못박고 실제 호출 경로(KADDR_HANDOFF_TO_KMAIL)를 만드는 데까지 이어졌다. 마지막엔 "저장소 URL 요약해서 보내줘" 요청이 엉뚱한 도구를 오용하는 걸 발견해, GitHub 저장소는 REST API로 우회하는 범용 콘텐츠 조회 기능까지 새로 만들었다. 매 단계 라이브 스모크테스트로 검증하며 진행했다.

Overview
이 문서가 왜 있는가

이번 세션은 서로 이어지는 6개의 작업이 한 실로 꿰여 있다 — "메일 주소가 못생겼다"는 지적 하나가 "발송이 아예 안 되고 있었다"는 발견으로, 그게 다시 "다른 서비스를 대신 호출하는 원칙이 없다"는 더 근본적인 지적으로 이어졌다. 각 절은 독립 적으로 읽을 수 있지만, 순서대로 읽으면 왜 다음 작업이 필요했는지가 자연스럽게 보인다. 실제 코드 위치·PR 순서· 라이브 검증 결과까지 재현 가능한 수준으로 남긴다.

① 2026-09-12 오전
K-Mail ID(mail_id) 신설 — 콜론투성이 guid를 사람이 쓸 수 있는 주소로

실제 발신 주소는 스푸핑 방지를 위해 <guid>@hondi.kr 로 고정돼야 했지만, guid 자체가 2601:db80:c342:fd1b:bc4a:2dce:9ed8:04b6처럼 IPv6 형태라 사람이 부르거나 외울 수 없었다. 해결책은 guid 위에 사람이 고르는 별칭(mail_id)을 얹는 것 — 전역 유일성은 가입 시 자동배정(HMAC 기반 8자리 hex, 충돌 시 카운터로 재시도) + 사용자 직접 지정 두 경로를 하나의 검증 로직으로 묶었다.

구현

  • GET/POST /kmail/settings·GET /kmail/mail-id/check· POST /kmail/mail-id/auto 신설
  • pb_hooks/main.pb.js — 가입(profiles 생성) 직후 자동배정, best-effort(실패해도 가입은 막지 않음)
  • K-Mail 채팅(SP-25 §2-8·§2-14) — mail_id 유무로 분기, 없으면 guid를 노출하는 대신 설정 화면 유도 팝업 태그
발견한 버그
/kmail/settings가 처음부터 지갑 서명 전용 인증만 받고 있어서, 지갑 SSO를 안 쓰는 현재 웹앱에서는 애초에 호출 자체가 불가능한 죽은 코드였다 — 다른 kmail 엔드포인트와 동일한 공용 인증 게이트(_kAuth.resolveGuid) 로 맞춰 수정.
② 라이브 스모크테스트로 발견
발신 주소의 콜론이 이메일 로컬파트로 무효 — K-Mail 발송이 처음부터 실패하고 있었을 가능성

mail_id 기능을 검증하려고 처음 만든 라이브 스모크테스트(자기 자신에게 실제 발송)가 502 EMAIL_SEND_FAILED: Invalid email address로 실패했다. 원인을 추적한 결과: guid는 예외 없이 콜론 8그룹 형식인데(src/gopang/core/auth.js _generateRandomGuid()), 콜론은 이메일 로컬파트에서 따옴표 없이는 쓸 수 없는 문자다. _kmailSendOneEmail· _kmailSendAutoReply가 이 값을 그대로 from/replyTo에 써왔으므로, 즉시발송·캠페인 발송·부재중 자동응답 — K-Mail의 모든 실제 발송 경로가 서비스 시작 이후 한 번도 성공한 적이 없었을 가능성이 높다. 기존 라이브 테스트가 전부 mock 데이터 기반이라 실제 env.EMAIL.send()를 태운 적이 없어 지금까지 발견되지 않았다.

수정

콜론을 하이픈으로 치환해 유효한 로컬파트를 만든다 (_guidToEmailLocalPart). guid가 항상 4자리 hex 8그룹 고정 형식이라 구분자 치환은 모호성 없이 무손실 — 값 자체를 해시 등으로 바꾸지 않은 이유는 기존에 쌓인 ai_messages·kmail_campaigns 등의 guid 참조와 정합성이 깨지기 때문이다. 발신 5곳 + 인바운드 파싱의 역변환(_emailLocalPartToGuid) 1곳을 함께 고쳐야 한다 — 발신만 고치면 회신이 전부 엉뚱한(존재하지 않는) guid로 가서 조용히 유실된다.

실사 검증
외부 실주소(Gmail)로 실제 발송 → 도착 확인 완료. 자기 도메인 자기발송(자가발송)은 Cloudflare 정책상 반송되는 게 정상 동작(버그 아님)이라는 것도 실사로 확인 — 그 반송 알림도 인바운드 파이프라인 전체를 정상 통과했다.
③
세션 슬라이딩 갱신 — Gmail처럼 활동 중엔 로그아웃되지 않게

K-Law↔K-Mail 로그인 공유(.hondi.net 쿠키)와 30일 TTL은 이미 있었지만, 만료 임박 시 조용히 갱신하는 경로가 없어서 "30일째 되는 순간 활동 중이어도 강제 재인증"되는 간극이 있었다. POST /auth/refresh-token 신규 — 유효한 토큰이면 같은 e164로 새 30일 창을 재발급한다. k-service-auth-client.js의 fetchWithAuth가 만료 7.5일 전부터 요청 직전에 조용히 이 엔드포인트를 호출 — 여러 탭 동시 요청은 in-flight 갱신 하나로 합친다.

④
주소록 — 카테고리뿐 아니라 태그별로도 브라우징

"팀 주피터" 태그로 57명을 등록했는데 화면 카테고리 버튼에 안 보인다는 문의에서 시작 — category(KSIC 21종 고정값)와 tags(자유 그룹명)는 원래 다른 개념인데, 태그를 눌러볼 방법 자체가 화면에 없었다. GET /kmail/contacts/tag-counts 신설 — category처럼 "값마다 perPage=1 조회"하는 트릭을 못 쓰므로(자유값이라 사전 목록이 없음), fields=tags로 최소 payload만 페이지네이션해 서버가 직접 집계한다. 카테고리 버튼 아래에 태그 버튼 목록을 나란히 표시.

⑤ 플랫폼 최상위 원칙 개정
UNIVERSAL-INTEGRITY U0 항목(11) 신설 + K-Address→K-Mail 직접 호출

K-Address 채팅에 "팀 주피터 멤버들에게 개발 상황 요약해서 보내줘"라고 요청하자 "저는 발송 기능이 없으니 K-Mail 탭에서 직접 하세요"라고 안내만 하고 끝냈다. 이건 모든 SP가 상속하는 최상위 문서(UNIVERSAL-INTEGRITY) U0("안내로 끝내지 않는다, 대신 진행한다")의 명백한 위반이지만, 그때까지 U0에는 "형제 K-서비스에 넘기기"에 대한 항목이 없었다.

UNIVERSAL-INTEGRITY v1.9 → v1.10

항목(11) 신설 — "내 업무가 아니다"는 멈추는 이유가 아니라, 그 업무를 수행하는 SP를 찾아 직접 호출하는 다음 행동의 기준이라고 명문화. 항목(9)("전문 분야는 AC가 직접 판단하지 않고 EXPERT를 부른다")의 구조를 "형제 K-서비스"에도 그대로 적용 — 호출 경로가 있으면 실제로 호출·전환까지 하고, 없으면 그 격차를 신설 요청으로 이어간다.

실제 메커니즘 — KADDR_HANDOFF_TO_KMAIL

SP-26 §2-8 신설. K-Address는 이메일 목록을 미리 뽑아 넘기지 않고 instruction(자연어 한 문장)만 K-Mail에 넘긴다 — 두 SP의 필터 개념(태그·카테고리 취급 방식)이 100% 일치한다는 보장이 없어, K-Mail이 자신의 KMAIL_LOOKUP_CONTACTS로 대상을 다시 확인하는 편이 안전하다고 판단했다. 프론트엔드는 기존 "내 캠페인 → 채팅으로 넘어가 물어보기"(_campAskChatAboutThis) 와 동일한 탭전환+대신발화 패턴을 재사용 — 액션을 받으면 "새 캠페인" 탭으로 전환하고 그 즉시 instruction을 K-Mail 채팅에 대신 입력·전송한다.

⑥
KMAIL_FETCH_CONTENT 신설 — 본문 작성용 URL 조회, GitHub는 REST API로 우회

핸드오프로 넘어간 K-Mail이 "혼디 저장소 최근 상황 요약해서 보내줘" + 저장소 URL을 받자, 원래 수신자 이메일을 찾는 용도로만 만들어진 KMAIL_FETCH_PAGE를 오용해 응답이 이상하게 끝났다. 그 함수는 페이지 첫 4000자만 가져오고 "이메일만 찾아라" 프레이밍으로 후속 처리되는데다, GitHub 저장소 화면은 자바스크립트로 렌더링되는 SPA라 애초에 그 4000자 안에 실제 콘텐츠가 거의 안 담긴다.

구현

  • 신규 태그 KMAIL_FETCH_CONTENT(SP-25 §2-1i) — KMAIL_FETCH_PAGE와 완전히 분리된 별개 경로
  • _performUrlFetchForSummary — GitHub 저장소 URL(github.com/{계정}/{저장소}) 감지 시 api.github.com REST API로 우회, 그 외는 일반 텍스트 조회(12000자)
  • _fetchGithubRepoSummary — 저장소 설명·기본 브랜치·최근 커밋 20건. env.GITHUB_TOKEN(선택) 설정 시 비인증 60건/시간 → 5000건/시간

같은 사고에서 K-Mail SP §0-1에도 별도 수정을 넣었다 — "팀 주피터" 같은 이름 붙은 그룹을 언급받으면, 사용자에게 되묻기 전에 반드시 KMAIL_LOOKUP_CONTACTS로 주소록을 먼저 조회하도록 명시(실사고: 57명이 이미 등록돼 있었는데도 조회 없이 "멤버가 누구인지 알려주세요"라고 되물었음).

교훈
  • mock 기반 테스트는 실제 인프라 통합 버그를 못 잡는다 — 콜론 버그는 서비스 시작 이후 계속 있었지만, 실제 env.EMAIL.send()를 태우는 테스트가 하나도 없어 발견이 안 됐다. "진짜로 한 번은 끝까지 실행해보는" 테스트가 최소 하나는 있어야 한다.
  • 구분자 치환은 값을 보존하면서 형식만 고치는 가장 안전한 수정이다 — 콜론을 해시 등으로 바꾸지 않고 하이픈으로만 치환해, 기존에 쌓인 데이터와의 정합성을 그대로 유지했다.
  • "이건 제 소관이 아닙니다"는 그 자체로 완결된 답이 아니다 — 안내로 끝내는 순간, 그게 "만들면 되는데 안 만들어진 경로"인지 "원래 안 되는 일"인지부터 구분해야 한다. 전자라면 격차를 명시하고 신설로 이어가야 한다(U0 항목(11)).
  • 전용 도구를 범용으로 재사용하려는 유혹을 경계할 것 — KMAIL_FETCH_PAGE는 "이메일 찾기"라는 목적에 맞춰 4000자·특정 프레이밍으로 최적화돼 있었다. 비슷해 보이는 새 요구가 오면 기존 도구를 억지로 늘리기보다, 처음부터 새 도구로 분리하는 게 더 안전했다.
  • 매니페스트 갱신은 배포의 일부이지 선택이 아니다 — SP 파일과 worker.js는 배포됐는데 매니페스트 포인터만 이전 버전에 멈춰 있어 스모크테스트가 한 번 오탐했다. 새 SP 버전은 항상 "새 파일 + 매니페스트 갱신"을 한 단위로 묶어 배포할 것.
  • 라이브 스모크테스트는 만들 때마다 새로운 버그를 하나씩 잡아냈다 — 이번 세션에서만 3개(콜론, U0 위반, 매니페스트 누락)를 실제로 찾아냈다. 신규 기능마다 실제 왕복을 확인하는 하네스를 같이 만드는 게 비용 대비 효과가 크다는 게 다시 확인됐다.
