"갈 곳 없는 질문"은 없다 — AC 라우팅 모델을 2,000개로 검증하다

사용자 1,000개 + 개발자 1,000개 질문을 만들어 QnA·K-Search·전문가 페르소나 세 시스템에 분류해봤더니 절반이 "갈 곳 없음"으로 나왔다. 틀린 결론이었다 — AC(AGENT-COMMON)가 실제로 호출할 수 있는 대상은 3개가 아니라, ① 명명된 K-서비스 자신의 SP(26개, sp-catalog.json 내부 탑재형과 별도 서브도메인 연합형으로 갈림) ② AC 자기 자신 ③ qna.hondi.net ④ 오늘 만든 hondi-search 개발자 문서 범위까지 포함해야 했다. 이 문서는 그 시행착오와 최종 분류 결과, 그리고 이걸 코드로 검증 가능하게 만든 ac-intent-router.js 설계까지 정리한다.

Overview
2,000개 질문이 드러낸 진짜 문제

혼디 생태계(55개 저장소)를 전수 조사해 사용자용 1,000개, 개발자용 1,000개 질문을 만들고, 이 질문들을 실제로 답할 SP가 있는지 확인하는 과정에서 라우팅 모델 자체의 결함이 드러났다. 처음엔 "QnA 게시판 / K-Search / 전문가 페르소나" 세 곳에 안 걸리면 전부 공백으로 처리했는데, 그 결과 2,000개 중 993개 (49.7%)가 "갈 곳 없음"으로 나왔다 — 이 숫자 자체가 말이 안 된다는 지적을 받고서야 모델이 틀렸다는 걸 알았다.

① Wrong Model
처음에 틀렸던 라우팅 모델

첫 모델은 아래 3개 버킷만 놓고 분류했다:

  • QnA(당시 "일반 질문게시판"으로 잘못 가정)
  • K-Search(개인 데이터 검색)
  • 전문가 페르소나(552명, 전문 상담)
교훈
"K-Mail이 있으니 K-Mail 사용법은 당연히 K-Mail 자신이 답한다"는 가장 기본적인 경로를 완전히 빠뜨렸다. AC가 라우팅할 수 있는 대상 전체 목록을 확인하지 않고, 임의로 정한 3개 버킷 기준으로 "여기 없으면 공백"이라고 단정한 게 근본 원인이었다.
② Correct Model

AC(AGENT-COMMON)가 사용자 발화 하나를 받았을 때 갈 수 있는 곳은 실제로 6가지다:

③ Internal vs Federated
K-서비스 내부(internal) vs 연합(federated) 실측 분류

prompts/sp-catalog.json(650개 엔트리)을 직접 대조해 확인한 결과, 26개 K-서비스가 두 종류로 갈린다:

  • internal(13개) — K-Mail(SP-25_kmail), K-Health(SP-04_khealth), K-Job, K-Plan, K-Public(SP-10_kpublic), K-Police(SP-03_kpolice), K-Traffic(SP-06_ktraffic), K-Democracy(SP-12_kdemocracy), K-Logistics(SP-13_klogistics), K-Insurance(SP-16_kinsurance), K-Search(SP-18_ksearch), K-Telecom(SP-23_ktelecom), K-Watch — AC가 카탈로그에서 SP를 직접 불러 그 자리에서 답함
  • federated(8개) — K-Law, K-Biz, K-Tax, K-Security, K-School, K-Stock, K-City, K-911 — 완전히 분리된 서브도메인 사이트로 이동해야 함. klaw 저장소를 직접 클론해 확인한 결과, 판결 방법론(v15.1)과 다중 LLM(Anthropic/Gemini/Groq/DeepSeek) 호출 로직까지 자체적으로 갖춘 완결된 백엔드였다 — hondi 쪽 카탈로그엔 K-Law가 전혀 없다.
  • not_yet_built(2개) — K-JIT, K-Const — SP도 사이트도 아직 없는 진짜 초안
④ QnA Discovery
qna.hondi.net 재발견 + 도메인 라우팅 버그

qna 저장소를 직접 클론하기 전까지 "일반 질문게시판"으로 잘못 가정하고 있었다. 실제로는 Gopang 시스템 자체(전략·특허· 서브시스템)에 대해 답하는 문서 기반 지식 어시스턴트였다. 이 과정에서 별개의 실제 버그도 하나 찾아 함께 고쳤다: desktop.html의 _selectDomainSP()가 2026-06-09 SP 분할(SP-LAW → SP-LEGAL+SP-IP) 이후 갱신되지 않아, 법률·특허·민원·교육 질문 4개 도메인이 전부 존재하지 않는 파일(SP-LAW.txt, SP-CIVIC.txt)로 라우팅되고 있었다. webapp.html은 이미 올바르게 참조하고 있어 desktop.html만 뒤처져 있던, 이 저장소가 반복해서 겪은 "PC/모바일 중복 구현 중 한쪽만 갱신" 패턴이었다.

⑥ Router Design
ac-intent-router.js 설계 및 검증

지금 AC는 사용자 발화 + sp-catalog.json 전체(650개 엔트리)를 매번 LLM에 통째로 넘겨 판단하게 하는 구조다 (call-ai.js의 _handleKSearchExecutionTag 등 _handle*Tag 계열 함수들이 LLM이 낸 태그를 사후 파싱하는 것으로 봐서, 사전 결정론적 분류기가 없다는 뜻이다). 이건 매 요청 토큰 비용과, "K-Mail 예약 발송 되나요?"처럼 답이 뻔한 요청까지 매번 LLM 추론을 거치는 낭비를 낳는다.

data/ac-routing-registry.json + src/gopang/ai/ac-intent-router.js를 신설했다 — 확신도 높은 케이스만 즉시 확정하고(LLM 호출 생략 또는 SP 하나만 로드), 애매하면 기존 LLM 판단으로 폴백하는 "빠른 사전 필터"다. call-ai.js에는 아직 배선하지 않았다 — 1만 2천 줄이 넘는 파일이라 이번 세션에서 직접 손대는 대신, 독립 모듈 + 유닛테스트로만 제공하고 통합은 팀 리뷰 후 진행하는 걸 권장한다.

검증 방법

오늘 만든 2,000개 질문(사람이 여러 차례 교정해 최종 수렴시킨 정답 데이터)을 그대로 정답 세트로 재사용했다 — tests/live_smoketest/ac-intent-router.test.mjs. 100% 일치를 요구하지 않고, confidence='high'로 판정한 것만 정답과 대조한다.

# 실행 node tests/live_smoketest/ac-intent-router.test.mjs

결과: high-confidence 판정 782건(전체의 39.1%), 그중 정답 일치 744건 — 정밀도 95.1%. 나머지 60.9%는 스스로 확신 없다고 판단해 기존 LLM 폴백으로 넘긴다.

검증 중 실제로 잡은 버그 3건
이 과정에서 분류기 자체의 결함도 발견해 고쳤다 — 전부 오늘 다른 저장소(qna, hondi-search-relay)에서 겪은 것과 같은 계보:
1) K-Telecom 키워드에 "요금제"가 너무 일반적이라 혼디 자체 구독요금제까지 삼킴
2) K-Mail 키워드 "메일"이 "이메일"의 부분일치로 오탐
3) "job 레포의"처럼 유니코드 환경에서 레포\b가 한글 조사 앞에서 단어 경계로 인식 안 되는 문제(오늘 세 번째 같은 유형의 버그)
Known Limits
알려진 한계 — 남은 38건
  • 얕은 질문 vs 깊은 기술 질문 구분 불가 — "GDC 충전 한도가 얼마인가요"(AC_CORE가 맞음)와 "GDC 신용평가가 신용정보원 데이터를 쓰나요"(QNA/SP-ECONOMY가 더 적합)를 같은 "GDC" 키워드로는 구분 못 한다. 순수 규칙 기반의 근본적 한계 — 의미 이해가 필요한 지점.
  • 초안 서비스의 사용자 질문 vs 개발자 질문 구분 불가 — "K-JIT 있어요?"(NOT_YET_BUILT가 맞음)와 "K-JIT의 목적함수 설계 근거가 뭔가요"(DEV_DOCS가 더 적합)를 구분하려면 audience(user/dev) 컨텍스트가 필요한데, 지금 classifyIntent()는 이 신호를 받지 않는다 — hondi-search의 scope 파라미터처럼 향후 추가할 만하다.
