# 인수인계서 — gov-router CLARIFY runnerUp 2단계 분리, A1~A5 라이브 검증 (2026-09-18)

**전제**: 이전 세션이 크레딧 소진으로 A1(국 레벨) 실사 직전에 중단됐고, 이 세션이 그 실사부터 이어받아 A2~A5까지 신규로 확장 검증했다. 이 문서는 다음 세션이 바로 시작할 수 있게 요점만 압축한 것 — 각 배치의 원본 결과는 `results/live-smoketest-gov-clarify-a{1..5}` 브랜치의 `results/gov-clarify-a{N}/live_results.json`에 그대로 남아있다.

## 배경

`gov-router.js`의 `_govClassifyFn`(→ `pages/regional-gov.html`)이 CLARIFY 자기선고("애매하면 CLARIFY:코드1,코드2로 답하라")에서 code+runnerUp 2단계 분리(PR #345)로 재설계됐다 — `subject-gate.js`(EXPERT 게이트)에서 검증된 것과 동일한 설계: "확신 있게 하나 고르기"와 "동시에 의심하기"를 한 호출에서 요구하면 항상 전자만 이행되므로, 부담 적은 "차선책 보고(runnerUp)" + 별개의 예/아니오 확인으로 쪼갠다.

이 설계를 쓰는 코드 경로가 gov-router.js 안에 **다섯 갈래** 있다는 걸 A1~A5를 진행하며 확인했다:

| 배치 | 코드 경로 | 애매함의 종류 |
|---|---|---|
| A1 | `_classifyFallback` | 국(局) 레벨 — 같은 계층 이웃 부서 |
| A2 | `_classifyDivisionFallback` | 과(課) 레벨 — 같은 계층 이웃 부서 |
| A3 | `_classifyTeamFallback` | 읍면동 팀 레벨 — 같은 계층 이웃 팀 |
| A4 | `_classifyDivisionFallback` 재사용(`policyBodyGuess` 충돌) | 국가 정책기관 ↔ 지방행정 계층충돌 |
| A5 | `_classifyDivisionFallback` 재사용(`natMatch` 충돌) | 국가 지사형 집행기관 ↔ 지방행정 계층충돌 |

## 후속 갱신 2 (2026-09-18, 같은 날 이어서) — diag-04류 비결정성 직접 검증 완료

이전 절의 "비결정성" 관찰은 서로 다른 max_tokens 설정 간 비교였고, 같은 조건 반복호출 비교가 아니었다. 그래서 retry-prone 발화 2건(조천읍 보훈 welfare/outreach, 한부모 GENDER/WELFARE)을 각각 `max_tokens=12000, temperature=0` **완전히 고정**한 채 6회씩 반복 호출해서 직접 검증했다(`scenarios_gov_clarify_nondeterminism_20260918.json`, `live-smoketest-gov-clarify-nondeterminism.yml`).

결과:

| 발화 쌍 | CORRECT | FAIL |
|---|---|---|
| 조천읍 보훈(welfare/outreach) | 5/6 | 1/6 |
| 한부모 성평등/복지가족(GENDER/WELFARE) | 5/6 | 1/6 |

**결론: 비결정성은 실재한다 — 동일 입력·동일 파라미터에서도 두 쌍 모두 정확히 1/6(~17%) 비율로 실패했다.** 이번엔 max_tokens 캡에 걸린 게 아니다(토큰 사용량이 176~4190까지 요동쳤지만 전부 12000 한도 안에서 여유 있게 종료). 즉 앞 절의 "max_tokens 차이 때문에 결과가 갈렸다"는 가설은 틀렸고, `deepseek-v4-flash`가 temperature=0에서도 완전한 결정성을 보장하지 않는다는 게 직접 확인됐다(추론모델에서 흔한 현상 — MoE 라우팅이나 배치 추론의 부동소수점 비결정성 등이 원인일 수 있음, 모델 제공사 쪽 특성이라 이 코드베이스에서 고칠 수 있는 문제가 아니다).

실패한 1/6도 오탐(엉뚱한 코드를 확정)이 아니라 애매함을 놓치고 한쪽만 확신 있게 답한 것(LIVE-FAIL)이었다 — runnerUp 2단계 설계 자체의 구조적 결함이라기보다 모델 고유의 잔여 실패율로 보는 게 맞다. 따라서 우선순위 2번도 "조사 완료, 구조적 조치 불필요"로 종료한다.

## 후속 갱신 3 (2026-09-18, 같은 날 이어서) — institution 레벨 착수, A1~A5와 다른 성격의 결함 발견·수정 (A6)

우선순위 1번(institution 레벨)에 착수하면서 먼저 "이 계층이 애초에 classifyFn(runnerUp)을 거치기는 하는가"부터 코드로 확인했다. 결과, `JEJU_AGENCY_DIVISION_TABLE`/`JEJU_ORG_DIVISION_TABLE`(기관 산하 division/팀) 자체는 classifyFn과 무관한 별도의 직접 코드 해석 경로였지만, **기관(직속기관 03-do-agency/출자출연기관 07-org) 자체와 도청 L2(실·국) 사이의 충돌 감지**는 `_resolveInstitutionMatch`(gov-router.js ~3087행)가 A2/A4/A5와 동일하게 `_classifyDivisionFallback`을 재사용하고 있었다 — 다만 지금까지 다섯 배치(A1~A5) 목록엔 없던 여섯 번째 코드 경로다.

`_resolveInstitutionMatch`를 읽다가 **A1~A5와는 성격이 다른 문제**를 발견했다: 이 함수는 기관 키워드 매칭이 `topScore===1`(약한 매칭, 키워드 1개)일 때만 도청 L2 1등 후보를 합쳐서 classifyFn 되묻기 기회를 줬고, `topScore>=2`(강한 매칭, 키워드 2개 이상)는 **L2 비교도 classifyFn 호출도 전혀 없이 즉시 확정**했다(`if (tied.length === 1 && topScore >= 2) return best;`). 2026-08-23 신설된 국가기관↔지방행정 충돌 안전망(`_localGovCollisionCandidate`, A4/A5로 검증)과 정확히 같은 클래스의 문제인데, institution↔L2 사이에서는 매칭 강도 2 이상 구간에 그 안전망이 아예 이식이 안 돼 있었다.

이건 LLM 비결정성과 무관하게 **코드 추적만으로 결정론적으로 재현**됐다(production 키워드 테이블 그대로 Node 스크립트로 스코어링 재현, LLM 호출 없이 확정): "소상공인 창업 지원을 받고 싶어요" 등 3개 발화가 `SP-ORG-JEDA`(제주경제통상진흥원)에 키워드 2개(소상공인+창업 지원) 매칭돼 즉시 확정되는데, `SP-DO-ECON`(도청 경제활력국, L2)에도 '소상공인' 매칭 근거가 실제로 있었다.

**수정(PR #356)**: `topScore>=2` 분기에서도 L2가 진짜로 겹칠 때만(L2 topScore>0) `topScore===1`과 동일한 안전망(L2 후보 병합 + classifyFn)을 태우도록 했다 — L2가 안 겹치면 불필요한 LLM 호출 없이 기존처럼 즉시 확정(회귀 없음).

**A6 라이브 검증 결과 (5건, `scenarios_gov_clarify_a6_institution_l2_20260918.json`):**

| 시나리오 | 기대 | 실제 |
|---|---|---|
| 강한매칭 충돌 3건 (JEDA↔ECON) | CLARIFY 발동 | **3/3 정확히 되묻기 발동** |
| 통제 2건 (JEDA 단독 / ECON 단독) | 확신 있게 단일 확정 | **2/2 정상** |

오탐(과잉 되묻기) 0건, 누락 0건 — 5/5 완벽.

**A1~A5와의 차이를 분명히 해둔다: A1~A5는 "runnerUp 설계 자체가 code+runnerUp 2단계로 잘 작동하는가"를 검증했고 전부 통과했다. A6는 그와 달리 "애초에 그 설계(classifyFn)에 도달하지 못하게 막는 코드 분기가 있었다"는, 설계 이전 단계의 구조적 결함이었다** — runnerUp 메커니즘 자체의 문제는 아니다. institution 레벨 검증은 이 한 건(agency/org↔L2 강한매칭)으로 일단락하고, JEJU_AGENCY_DIVISION_TABLE/JEJU_ORG_DIVISION_TABLE(기관 산하 division/팀 동점) 쪽 `_resolveDoAgencyDivision`/`_resolveOrgDivision`도 `_classifyDivisionFallback`을 재사용하는 코드 경로이지만 이번 라운드에선 아직 라이브 검증 안 함(구조는 A2와 동일 패턴이라 위험도는 낮게 본다).

## 진행 방식 관련 주의사항 (이 세션에서 확인된 것)

- 이 세션(클라우드)은 `Openhash-Gopang/hondi`에 대해 **읽기(clone)만 허용**되고 push·GitHub API 쓰기는 세션 권한 밖이라 403으로 막힌다 — patch 파일(`git format-patch`)을 만들어 사용자에게 전달하고, 사용자가 로컬에서 `git am`으로 적용 → 브랜치 push → `gh pr create --fill` → `gh pr merge --auto --squash`로 병합하는 방식으로 전량 진행했다(main 직접 push 아님 — 동시 세션 충돌 방지).
- patch를 만들 때마다 **origin/main을 다시 fetch해서 그 위에 커밋을 얹고**, 별도 worktree(`git worktree add ... origin/main -f`)에서 `git am`이 깨끗하게 붙는지 먼저 검증한 뒤에 전달했다 — 세션 진행 중 다른 프로세스(build-version bump 자동커밋 등)가 계속 main을 움직였기 때문에 이 확인이 실제로 여러 번 필요했다.
- 결과 확인은 `results/live-smoketest-gov-clarify-a{N}` 브랜치를 `git fetch`해서 `live_results.json`을 직접 읽는 방식 — GitHub Actions UI/API는 이 세션에서 접근 불가.
