# 인수인계서 — gov-router CLARIFY runnerUp 2단계 분리, A1~A5 라이브 검증 (2026-09-18)

**전제**: 이전 세션이 크레딧 소진으로 A1(국 레벨) 실사 직전에 중단됐고, 이 세션이 그 실사부터 이어받아 A2~A5까지 신규로 확장 검증했다. 이 문서는 다음 세션이 바로 시작할 수 있게 요점만 압축한 것 — 각 배치의 원본 결과는 `results/live-smoketest-gov-clarify-a{1..5}` 브랜치의 `results/gov-clarify-a{N}/live_results.json`에 그대로 남아있다.

## 배경

`gov-router.js`의 `_govClassifyFn`(→ `pages/regional-gov.html`)이 CLARIFY 자기선고("애매하면 CLARIFY:코드1,코드2로 답하라")에서 code+runnerUp 2단계 분리(PR #345)로 재설계됐다 — `subject-gate.js`(EXPERT 게이트)에서 검증된 것과 동일한 설계: "확신 있게 하나 고르기"와 "동시에 의심하기"를 한 호출에서 요구하면 항상 전자만 이행되므로, 부담 적은 "차선책 보고(runnerUp)" + 별개의 예/아니오 확인으로 쪼갠다.

이 설계를 쓰는 코드 경로가 gov-router.js 안에 **다섯 갈래** 있다는 걸 A1~A5를 진행하며 확인했다:

| 배치 | 코드 경로 | 애매함의 종류 |
|---|---|---|
| A1 | `_classifyFallback` | 국(局) 레벨 — 같은 계층 이웃 부서 |
| A2 | `_classifyDivisionFallback` | 과(課) 레벨 — 같은 계층 이웃 부서 |
| A3 | `_classifyTeamFallback` | 읍면동 팀 레벨 — 같은 계층 이웃 팀 |
| A4 | `_classifyDivisionFallback` 재사용(`policyBodyGuess` 충돌) | 국가 정책기관 ↔ 지방행정 계층충돌 |
| A5 | `_classifyDivisionFallback` 재사용(`natMatch` 충돌) | 국가 지사형 집행기관 ↔ 지방행정 계층충돌 |

## 결과 종합

| 배치 | 건수 | 애매함 정확 인식 | 오탐(통제) | 빈 응답 |
|---|---|---|---|---|
| A1 국 | 17건(배치1+2 합산) | 10/15 (67%) | 0/2 | 3/17 (18%) |
| A2 과 | 10건 | 5/8 (62.5%) | 0/2 | 0/10 |
| A3 읍면동 팀 | 8건 | 5/6 (83%) | 0/2 | 1/8 (12.5%) |
| A4 국가↔지방(정책기관) | 8건 | 5/6 (83%) | 0/2 | 0/8 |
| A5 국가↔지방(집행기관) | 6건 | 1/4 (25%, ★아래 주의) | 0/2 | 1/6 (17%) |

**핵심 결론 — runnerUp 2단계 분리는 다섯 갈래 코드 경로 전부에서 일관되게 작동한다.** 어느 배치에서도 통제 시나리오(정답이 하나뿐인 경우) 오탐이 0건이었다. A4는 특히 의미가 있는데, 2026-08-30 수정 커밋 코멘트에 남아있던 실제 재현 버그 발화("소상공인 정책자금 대출 상담하고 싶어요" → 예전엔 무조건 MSS로 오확정)를 그대로 시나리오로 썼고, 오늘 실사에서 정확히 되묻기가 발동했다.

**★ A5는 수치를 곧이곧대로 믿지 말 것.** 03·04번(환경영향평가·반려동물 검역)은 국가기관 쪽이 사실상 유일한 정답에 가까울 수 있는 쌍이었다 — A4의 MSS처럼 "실제 재현된 버그"나 "양쪽 다 처리 가능하다는 코드 내 명시적 근거"가 없이, 키워드 이름만 보고 겹칠 거라 짐작해서 만든 시나리오다. `JEJU_NATIONAL_TABLE`(gov-router.js 1334행~) 자체가 과잉매칭 회피 원칙으로 설계돼 지방행정과 안 겹치게 키워드를 골라놨기 때문에, natMatch 계열에서 A4급 근거 있는 쌍을 더 찾기는 어려워 보인다 — 억지로 배치를 늘리면 A5 03·04번 같은 저품질 데이터만 쌓인다.

## 다음 세션이 할 일 — 우선순위 순

1. **빈 응답(추론모델이 max_tokens를 reasoning에 다 쓰고 실제 답을 못 내는 현상) 근본 원인 조사.** A1(2000→4000으로 올려도 18% 잔존)·A3(12.5%)·A5(17%)에서 반복 재현됐다 — 토큰 예산보다 발화 자체의 길이/복잡도가 추론을 더 유발하는 것 같다는 게 A1 세션의 가설(이전 세션 메모: "같은 성평등/복지가족 쌍이라도 발화를 바꾼 재시도는 성공"). max_tokens를 더 올리는 미봉책보다, 실패한 발화들의 공통점을 모아서 진짜 원인을 좁혀볼 필요가 있다.
2. **A2~A5의 표본 규모를 넓힐지 결정.** 지금까지는 배치당 6~17건 소규모 표본이다. 방향성(오탐 0건, runnerUp 재현)은 이미 다섯 갈래 전부에서 일관되게 나왔으니, 규모를 더 키우는 것보다 1번(빈 응답)을 먼저 잡는 게 우선순위가 높다고 판단한다.
3. **"확신도 임계값(예: 80%)까지 계속 되묻기" 제안은 채택하지 않기로 했다(사용자 논의 결론, 이전 세션).** 대신 오늘 검증된 구조("확신 있는 선택 + 부담 적은 차선책 보고 + 단일 이진 확인")를 원칙으로 최상위 공통 SP에 명시하는 방향으로 진행하기로 함 — 이 작업 자체가 이번 세션 범위에 포함됐었는지는 재확인 필요.
4. **institution 레벨(직속기관·출자출연기관, `JEJU_AGENCY_DIVISION_TABLE`/`JEJU_ORG_DIVISION_TABLE`)과 EXPERT 쪽(subject-gate.js) 페르소나 게이트는 아직 이 라운드에서 안 건드렸다** — gov-router 다섯 갈래와 다른 시스템이라 범위 밖으로 남겨둠. 필요하면 별도 라운드로.

## 진행 방식 관련 주의사항 (이 세션에서 확인된 것)

- 이 세션(클라우드)은 `Openhash-Gopang/hondi`에 대해 **읽기(clone)만 허용**되고 push·GitHub API 쓰기는 세션 권한 밖이라 403으로 막힌다 — patch 파일(`git format-patch`)을 만들어 사용자에게 전달하고, 사용자가 로컬에서 `git am`으로 적용 → 브랜치 push → `gh pr create --fill` → `gh pr merge --auto --squash`로 병합하는 방식으로 전량 진행했다(main 직접 push 아님 — 동시 세션 충돌 방지).
- patch를 만들 때마다 **origin/main을 다시 fetch해서 그 위에 커밋을 얹고**, 별도 worktree(`git worktree add ... origin/main -f`)에서 `git am`이 깨끗하게 붙는지 먼저 검증한 뒤에 전달했다 — 세션 진행 중 다른 프로세스(build-version bump 자동커밋 등)가 계속 main을 움직였기 때문에 이 확인이 실제로 여러 번 필요했다.
- 결과 확인은 `results/live-smoketest-gov-clarify-a{N}` 브랜치를 `git fetch`해서 `live_results.json`을 직접 읽는 방식 — GitHub Actions UI/API는 이 세션에서 접근 불가.
