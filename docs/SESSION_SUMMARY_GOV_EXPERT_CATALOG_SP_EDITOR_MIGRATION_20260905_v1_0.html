Overview
이 문서가 왜 있는가

오늘 세션은 "K-JIT·K-City라는 신규 K-서비스 두 개를 추가한다"는 비교적 좁은 요청에서 시작해, 이미 있는 두 개의 대형 카탈로그 페이지(전문가 페르소나·K-정부)를 전면 재설계하는 데까지 번졌다. 공통점은 매번 "이게 실제로 반영되고 있는 게 맞나?"라고 한 번 더 확인했더니, 코드나 데이터가 실제로는 다른 곳을 보고 있었거나 조용히 실패하고 있었다는 것이다 — 교수 세부전공 174명이 자기가 "교수"라는 정체성도 모른 채 대화하고 있었던 것, 이번 세션 내내 hondi에 커밋한 콘텐츠 수정이 실제로는 폐기된 gopang 저장소를 계속 가리키던 코드 때문에 서비스에 반영되지 않고 있었던 것, 특정 도(道)의 부서를 눌러도 접속자의 실제 위치로 응답이 새고 있었던 것, 입법 탭이 스크립트 실행 순서 문제로 영원히 빈 채로 남아있었던 것. 다음에 이 영역을 다시 건드릴 사람이 같은 과정을 반복하지 않도록 정리한다.

① 신규 K-서비스
K-JIT·K-City — SP 초안부터 사이트·백엔드까지

K-JIT(사회효용 우선 적시조달 메커니즘, SP-26)와 K-City(시민 복지 총합 최적 도시 설계, SP-27) 초안을 작성하고, Openhash-Gopang/jit· /city 저장소를 신설했다. 각각 index.html (소개 페이지)·webapp.html(로그인+채팅 앱, 공용 subsystem-auth.js 인증 모듈 사용)을 구축하고, worker.js에 /kjit/relay· /kcity/relay 백엔드 핸들러를 신설했다.

발견·수정한 결함

  • SSO 무한 리다이렉트 루프 — subsystem-auth.js를 필수 모드로 두면, 오프너 창 없이 URL을 직접 열었을 때 silent-auth.html과 무한 루프에 빠지는 플랫폼 공용 버그에 걸렸다. data-required="false"로 전환해 해결(K-Plan이 이미 같은 이유로 이렇게 쓰고 있었음).
  • K-서비스 탭 전체 먹통 — k-services.html에 K-JIT·K-City 탭을 추가하며 SVC_CONTENT 객체 리터럴에 쉼표 하나를 빠뜨려, 그 스크립트 블록 전체가 파싱조차 안 되고 있었다. 원인 진단 중 애초에 <script> 태그가 3개인 파일에서 첫 번째(무관한) 블록만 문법 검증하고 있었던 검증 방식 자체의 결함도 함께 발견.
미완료
jit.hondi.net·city.hondi.net DNS·GitHub Pages 연결까지는 완료했으나, HTTPS 인증서 발급은 시간이 걸리는 자동 절차(Let's Encrypt)라 세션 종료 시점에 완료 여부 미확인.
② 전문가 페르소나
카탈로그 전면 재설계 — 505명을 검색+아코디언으로

pages/expert-personas.html이 63개 직업군 중 대표 예시만 정적으로 나열하던 것을, 레지스트리(expert-registry-*.js)를 직접 파싱해 505개 페르소나 전부를 검색+아코디언 카탈로그로 표시하도록 재구축했다. 반복적으로 디자인 방향이 바뀌었다 — Material Design(카테고리별 tonal color) → 원자로/MRI 제어반 스타일(헤어라인 격자·모노스페이스 숫자·절제된 인디케이터 색) 순으로 재작업.

부가 기능

  • 자연어 트리거 검색 — 레지스트리에 이미 있던 triggers 배열(자연어 호출 문구)을 검색에 반영, 새 AI 호출 없이 순수 문자열 매칭으로 "직업명을 몰라도 관련 문구로 찾기" 지원.
  • 세부분야 1개 섹션의 직행 링크화 — 세부분야가 자기 자신뿐인 섹션(치과의사 등 58개)은 아코디언 대신 곧바로 상담으로 이동하는 링크로 전환.
  • 실제 상담 연결 + SP 편집 아이콘 — 처음엔 모든 링크가 GitHub SP 원문(정적 문서)으로 연결되고 있었다 (실제 채팅이 시작되지 않는 상태). expert-chat.html?persona=로 교체하고, 최말단 세부분야 칩까지 채팅/SP편집 아이콘을 각각 따로 붙였다.
③ 실결함
교수 세부전공 174명 — 정체성 없이 구동되던 결함

expert-chat.html의 composeExpertPrompt()가 "EXPERT_BASE → 부모 1단계 → 본인" 3단까지만 상속을 지원하도록 하드코딩돼 있었다. 그런데 교수 세부전공(예: 반도체공학)은 실제로 "교수 → 중계열(재료 중계열) → 소계열(반도체공학)" 4단 체인이라, 부모(중계열)가 "또 부모(교수)를 가지고 있으면" 조용히 건너뛰는 코드 때문에 174명 전원이 최상위 정체성(교수라는 자각·핵심 원칙)을 아예 못 받은 채 세부전공 지식만 가지고 대화하고 있었다.

수정
부모 체인을 하드코딩된 2단이 아니라 끝까지 재귀적으로 따라가도록 고쳤다. 0~1단 체인(기존 60여 개 페르소나)은 동작이 그대로이고, 3단 이상인 경우도 중간 계층을 하나도 빠뜨리지 않는다. 독립 시뮬레이션으로 (교수→재료 중계열→반도체공학 순서) 검증 완료.
④ K-정부
카탈로그 신설 — 행정부 648개→701개, 16개 지역 탭

전문가 페르소나와 같은 방식으로 k-government.html에 행정부 기관 카탈로그를 신설했다. 정책기구·공공기관·공기업· 출자출연기관·기타 총 648개로 시작해, division-tables.js를 추가로 뒤져 26개를 더 발견(701개), 강원·대구 도 부서 데이터를 실제 조직도 검색으로 신규 작성해 채웠다. 이후 사용자 지시로 "중앙정부 + 16개 지역" 탭 구조로 재구성했다.

바로잡은 오분류

"출자출연기관" 268개를 전부 중앙정부 카테고리에 뭉뚱그려 넣었던 게 실제로는 전부 지역 소속이었다 (부산경제진흥원은 부산 것이지 중앙정부 것이 아님) — 지역 탭으로 재배치하며 자연히 바로잡혔다.

⑤ 가장 중대한 발견
gopang(폐기)을 여전히 콘텐츠 허브로 참조하던 15곳

SP 편집기를 만들던 중, gov-router.js의 파일 fetch 기본 저장소가 Openhash-Gopang/hondi가 아니라 폐기된 Openhash-Gopang/gopang으로 하드코딩돼 있는 것을 발견했다. 확인해보니 worker.js 10곳을 포함해 총 5개 파일 15곳이 같은 문제였다 — 즉 이번 세션 내내 hondi에 커밋한 gov-tree 콘텐츠 수정(강원·대구 데이터 등)이 실제 서비스에는 전혀 반영되지 않고 있었을 가능성이 있었다.

안전하게 전환한 절차

  1. gopang과 hondi의 prompts/ 전체(2,808개 파일)를 전수 대조 — 0건 누락 확인(hondi가 완전한 상위집합).
  2. sp-catalog.json 내용 비교 — gopang은 SP-25_kmail_v1_0에 멈춰있고 hondi는 v1_10으로 최신임을 확인.
  3. 5개 파일 15곳을 Openhash-Gopang/hondi로 일괄 치환 후, raw.githubusercontent.com으로 실제 강원 데이터가 응답하는 것까지 직접 재확인.
영향 범위
이번 세션에서 만든 K-JIT/K-City SP, 전문가 페르소나 확장, K-정부 도별 데이터, 국가기관 카탈로그 등 — hondi에만 반영하고 배포했던 콘텐츠 전부가 이 수정 전까지는 실제로 서빙되지 않고 있었을 가능성이 있다.
⑥ 입법·사법
카탈로그 신설 + 초기화 순서 버그

정책기구 폴더를 다시 뒤져 입법 6개(국회 및 소속기관)·사법 5개(법원 계통)를 찾아 별도 탭으로 분리했다. 이 과정에서 코드명 혼동(JPRI≠JRTI)으로 사법연수원 1건이 계속 "중앙정부"에 잘못 남아있던 것도 함께 바로잡았다.

발견된 버그 — 입법 탭이 항상 비어 있었음
<script> 블록이 3개로 나뉜 파일에서, 초기 렌더 호출(renderBranch('legislative'))이 두 번째 블록 끝에 있었고 그 렌더가 참조하는 데이터 (GOV_LEGISLATIVE 등)는 세 번째 블록에 있었다. var 선언은 끌어올려져도 값 할당은 실행 순서를 따르므로, 페이지 로드 시 undefined를 참조하며 조용히 실패하고 있었다. 초기 호출을 모든 정의가 끝나는 지점으로 옮겨 해결 — 두 블록을 이어붙여 Node로 실행 시뮬레이션까지 해서 검증했다.
⑦ 라우팅 결함
지역 정체성이 접속 위치로 새던 버그 3종

"서울 기획조정실을 눌러도 제주로 응답한다"는 사용자 보고를 추적해 세 가지 독립된 원인을 찾았다.

1) window.HONDI_PROVINCE_CODE 우선순위 누수

_resolveProvinceCode()가 접속자의 실제 위치 기반 전역값을 최우선으로 보는 바람에, directCode로 이미 도가 확정된 경로에서도 _loadDoSp()가 그 값을 무시하고 접속 위치로 도청 정체성을 로드하고 있었다. _loadDoSp(explicitProvinceCode)로 명시적 인자를 받게 고치고, directCode 경로의 7개 호출부 전부를 수정했다.

2) do-dept/do-agency 코드 충돌

여러 도가 같은 도메인 코드(SP-DO-PLAN 등)를 공유해, 도를 명시하지 않으면 항상 첫 번째로 등록된 도(제주)로만 연결되는 구조였다. {도코드}:{code} 형식을 지원하도록 확장해 카탈로그에서 특정 도의 특정 부서로 정확히 연결되게 했다.

3) directCode를 무시하던 정적 인사말

regional-gov.html의 초기 인사말 조건이 GWP_CTX만 확인하고 카탈로그가 쓰는 _govDirectCode는 안 봐서, 특정 기관이 이미 확정된 상태로 들어와도 "전국 지방행정 AI입니다"라는 일반 인사말이 먼저 떴다. expert-chat.html에서 이미 쓰던 방식과 동일하게, 자기소개를 요청하는 시드 발화를 조용히 대신 보내도록 바꿨다.

⑧ 신규 도구
SP 편집기 — SP-EDITOR 메타-SP + 전용 화면

기존 SP-AUTHOR는 "아직 없는 기관 SP를 처음부터 조사해 만드는" 용도이며 문서 자체에 "실제 조사·작성은 여전히 사람이 수행한다"고 명시돼 있어, "이미 있는 SP를 대화로 고치는" 워크플로우와는 맞지 않았다. 그 공백을 메우기 위해 SP-EDITOR(신규 메타-SP)와 pages/sp-editor.html (파일 첨부+편집기+대화창)을 신설했다.

  • AI가 개정안을 코드블록으로 내면 "이 개정본으로 편집창 교체" 버튼으로 즉시 반영 — 단, 저장·GitHub 반영은 이 화면이 하지 않으며 언제나 사람이 patch+PR로 한다.
  • K-정부·전문가 페르소나 카탈로그 양쪽에 편집 아이콘(✎)을 채팅 화살표(↗)와 별도로 추가 — sp-catalog.json과 디렉터리 인덱싱으로 715개(K-정부)·351개(전문가 페르소나) 경로를 전부 자동 매핑했다.

교훈
  • "만들었다"와 "반영됐다"는 다른 문장이다. 코드를 올바른 저장소에 커밋해도, 그 코드가 런타임에 데이터를 fetch하는 대상 저장소 자체가 다르면 아무 의미가 없다 — 의심스러우면 raw.githubusercontent.com으로 직접 실물을 확인한다.
  • 여러 <script> 블록이 있는 파일은 정의 순서를 반드시 눈으로 추적한다. var 호이스팅은 선언만 끌어올리지 값 할당까지 끌어올리지 않는다 — 초기 실행 호출은 항상 그 호출이 참조하는 모든 것의 정의보다 뒤에 있어야 한다.
  • 여러 계층을 상속하는 구조는 "몇 단까지"를 하드코딩하지 않는다. 지금 데이터가 2단이라고 코드도 2단으로 고정하면, 나중에 3단 데이터가 추가되는 순간 조용히 깨진다 — 재귀로 짜면 깊이가 늘어도 안전하다.
  • 전역 상태(접속 위치 등)를 우선하는 함수는, 이미 결정된 값이 있는 호출 경로에서는 명시적으로 그 값을 넘겨 우회할 수 있게 만든다. 그렇지 않으면 "이미 정해진 답이 있는데 굳이 다시 추측해서 틀리는" 상황이 반복된다.
  • 사고실험(가상의 클릭 경로를 코드로 추적하는 것)은 실제 클릭만큼 신뢰하되 완전히 대체하지는 않는다. 로직 추적으로 대부분의 버그를 잡았지만, 실제 최종 확인은 결국 사용자의 스크린샷과 클릭이었다.
