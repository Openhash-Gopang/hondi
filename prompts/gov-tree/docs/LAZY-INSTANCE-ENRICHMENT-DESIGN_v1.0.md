## 0. 배경 — 왜 이 문서가 필요한가

`NATIONWIDE-INSTANCE-ROLLOUT-PLAN`은 애초에 "사전에 도청·시청·읍면동·
국가기관 인스턴스를 전부 완성해놓고 서비스한다"는 전제로 설계됐다(§3-1~4).
1단계 파일럿(해운대구)도 그 전제대로 Research로 전체 조직도를 미리
조사해 한 번에 반영했다.

그런데 실제로 원하는 방식은 다르다:

1. **인스턴스는 처음 호출되는 시점에 원형 클래스를 그대로 복제해 생성된다**
   (지금의 "완성본을 미리 커밋"이 아니라 "빈 틀이 그때그때 채워진다").
2. **대화 중 AI가 실제로 알아낸 정보를 즉시 인스턴스에 반영**하고, 그
   반영은 잠정적이다.
3. **사람이 추후 검증**해서 그 잠정 반영을 확정한다.
4. 시간이 지나면 각 인스턴스(부산시청·제주도청·울산시청 등)가 서로 다른
   만큼 채워진, 고유한 상태가 된다 — 정보를 추가·삭제하는 과정이 자연스럽게
   반복되는 게 정상 상태다.

**기존에 만들어둔 인스턴스(해운대구 등, 183개 시/군/구 메타데이터 포함)는
폐기하지 않는다** — 이것들은 "완성본"이 아니라 이 새 메커니즘 아래에서의
**표지석(milestone)**, 즉 이미 상당히 채워진 상태로 출발하는 인스턴스로
재해석한다. 새 메커니즘은 이 표지석 위에 계속 덧붙여지는 방식으로
동작한다.

| 계층 | 저장소 | 역할 | 반영 시점 |
|---|---|---|---|
| **초안(draft)** | PocketBase(신규 컬렉션) | 대화 중 AI가 알아낸 정보를 즉시 기록 | 실시간, 배포 불필요 |
| **확정본(confirmed)** | git(`*-master-data.json`) | 실제로 라우팅·안내에 쓰이는 "진실" | 사람이 검증 후 승격(patch) |

**왜 하이브리드인가** (사용자 승인 완료, 2026-07-24 대화 기록):
- git 단독으로는 안 된다 — 커밋→push→재배포 사이클이 있어 "즉시 반영"이
  구조적으로 불가능하다. 지금까지 이 프로젝트 전체가 patch 워크플로우를
  써온 이유이기도 하다(사람이 매 단계 검토).
- PocketBase 단독으로는 안 된다 — 버전 이력·리뷰·롤백이 없고, 무엇보다
  §4-2("라우팅-콘텐츠 이원화")가 형태만 바뀌어 재발한다. git JSON과 DB가
  둘 다 "이게 진실이다"라고 주장하면 나중에 어느 쪽이 맞는지 판단하기
  어려워진다.
- 이 프로젝트에 **이미 동일 철학의 전례가 있다** — 재발명하지 않고
  재사용한다(§2).

## 2. 재사용할 기존 전례 — AGY_VAULT_STORE / META_TABLE_UPDATE

`worker.js`의 `handleGovRelay`(342개 국가기관 전부의 공용 진입점)에
이미 다음 패턴이 구현·검증돼 있다:

```
LLM 응답에 [TAG_NAME: key=value, key=value, ...] 브래킷이 포함됨
  → 서버가 정규식으로 감지(_parseXxxTag)
  → PocketBase에 비동기 기록(ctx.waitUntil, 응답 흐름 안 막음)
  → 태그를 사용자에게 보이는 응답 텍스트에서 제거
```

- `AGY_VAULT_STORE`: 상담 종료 시 6하원칙을 `owner_pdv`에 기록(AGENCY-AC-COMMON
  §1(5)).
- `META_TABLE_UPDATE`: 업무 처리 이력을 `meta_table_records`에 기록
  (AGENCY-AC-COMMON §6, `_writeMetaTableRecord`).

**이 설계는 새 메커니즘을 발명하지 않고, 이 정확히 같은 패턴을 재사용한다**
— 다만 저장 대상 데이터가 "상담 이력"이 아니라 "인스턴스 필드 보정"이라는
점만 다르다.

## 3. 신설 요소

### 3-1. 새 태그: `INSTANCE_ENRICH`

```
[INSTANCE_ENRICH: layer=city, province=busan, instance_id=haeundae,
  field=상하수도_capability_문구, value="안내만 수행 (부산시 상수도사업본부 소관 확인됨)",
  source=user_reported|web_search|inference, confidence=low|medium|high,
  note="사용자가 민원 접수 중 직접 확인해줌"]
```

필드 설계:
- `layer`: `do`(도청 실국) / `city`(시청) / `citydept`(시청 국) / `emd`(읍면동) /
  `national`(국가기관 지사) — 어느 계층의 인스턴스인지.
- `province`, `instance_id`: 어느 인스턴스인지(예: busan/haeundae,
  busan/haeundae/econ).
- `field`: 마스터데이터 JSON의 어느 필드를 보정하는지(기존 스키마의
  필드명을 그대로 씀 — 새 필드명을 마음대로 만들지 않는다).
- `value`: 새로 알아낸 값.
- `source`: 이 정보의 출처 성격 — **신뢰도 판단에 직결**(§5 참고).
- `confidence`: AI 자신이 매기는 잠정 신뢰도.
- `note`: 사람이 검증할 때 참고할 맥락(자유 텍스트).

### 3-2. 신규 PocketBase 컬렉션: `instance_enrichment_drafts`

```
id, layer, province, instance_id, field, value, source, confidence, note,
submitted_by_guid_hash, submitted_at, status(draft|promoted|rejected),
reviewed_by, reviewed_at, review_note
```

`_writeMetaTableRecord`와 동일한 구조(간단한 POST, 실패해도 응답 흐름은
안 막음)로 `_writeInstanceEnrichmentDraft(env, fields)` 함수를 신설한다.

### 3-3. 서버측 처리 위치

`handleGovRelay` 안, 기존 `AGY_VAULT_STORE`/`META_TABLE_UPDATE` 처리 블록
바로 옆에 세 번째 블록으로 추가한다(같은 함수, 같은 파일, 같은 패턴 —
새 진입점을 만들지 않는다). `META_TABLE_UPDATE`처럼 `canDelegate` 여부와
무관하게 모든 기관 세션에 적용해서, `AGY_VAULT_STORE`가 갖고 있는 "위임
발생 시 조기 return에 잡힘" 한계(§11736 주석 참고)를 처음부터 피한다.

### 3-4. 어느 SP가 이 태그를 방출하는가

개별 SP 템플릿(SP-CITY-TEMPLATE, SP-DEPT-*-TEMPLATE 등)마다 지시를
따로 넣지 않는다 — U0-1/U0-2와 동일하게 **UNIVERSAL-common에 새 조항
(가칭 U0-3 또는 별도 번호)을 하나 추가**해서, "인스턴스 데이터의 특정
필드가 실제와 다르거나 비어있다는 걸 대화 중 알게 되면 INSTANCE_ENRICH
태그를 남긴다"고 한 번만 규정한다. 이렇게 하면 이미 인스턴스화된
모든 도청·시청·국가기관 SP가 자동으로 이 능력을 갖는다(개별 SP 파일을
일일이 고칠 필요 없음 — AGY_VAULT_STORE가 65개 이상 SP에 이미 자동
적용된 것과 동일한 이유).

## 4. 승격(promotion) 절차 — "사람이 추후 검증"이 실제로 일어나는 지점

1. **조회**: `status='draft'`인 `instance_enrichment_drafts` 레코드를
   주기적으로(또는 요청 시) 조회한다. `GET /stats/agency-report`와
   유사한 형태의 조회 엔드포인트를 하나 신설하거나, 이 문서 작성자
   (Claude 세션)가 직접 PocketBase API로 조회한다.
2. **검증**: 사람(또는 검증을 위임받은 별도 세션)이 각 초안을 §2 원칙
   (지어내지 않기, 1차 출처 대조, 복수 출처 교차검증)에 따라 확인한다.
   `source=user_reported`인 항목은 특히 주의(§5).
3. **승격**: 검증된 항목은 이 대화 세션 전체에서 써온 **patch 워크플로우
   그대로** git의 `*-master-data.json`에 반영한다(새 절차를 만들지
   않는다 — 지금까지의 배포 규칙을 그대로 적용).
4. **정리**: 승격되면 `status='promoted'`로 갱신(레코드 자체는 감사
   추적을 위해 삭제하지 않는다). 반려되면 `status='rejected'` +
   `review_note`에 사유 기록.

## 5. 신뢰도 처리 — `source`가 왜 필수 필드인가

이 설계에서 가장 위험한 지점은 **`source=user_reported`**다. 정부기관
AC는 대부분 별도의 웹서치 도구가 있는지 확인되지 않았다(열려있는
질문, §7 참고) — 열려있지 않다면 "대화 중 AI가 알아낸 정보"의 상당수는
결국 **사용자가 그 자리에서 말해준 것**일 수 있다. 이건:

- 악의적이지 않아도 틀릴 수 있다(사용자도 잘못 알고 있을 수 있음).
- 악의적으로 오염시키려는 시도의 경로가 될 수 있다(예: 가짜 연락처를
  흘려서 인스턴스에 심으려는 시도).

**그래서 `source=user_reported`인 항목은 절대 자동 승격되지 않고,
반드시 사람이 §2의 교차검증 원칙(복수 독립 출처)을 통과시킨 뒤에만
승격한다.** `source=web_search`(AC가 직접 검색 도구로 확인한 경우)도
마찬가지로 사람 검증을 거치되, 이미 최소 1차 출처를 거쳤다는 점에서
우선순위를 높게 둘 수 있다.

## 6. 이번 설계에서 의도적으로 미루는 것

- **읽기 경로(read path) 변경 없음.** 라우터(`gov-router.js`)는 지금처럼
  git 원본(`_fetchByManifestKeyFromGithub` 등)만 읽는다 — PocketBase
  초안을 승격 전에 미리 읽어서 응답에 반영하는 "오버레이" 방식은 이번
  설계에 포함하지 않는다. 승격되기 전까지 초안은 "쓰기 전용 대기소"일
  뿐이다. 이렇게 하는 이유:
  - §4-2("라우팅-콘텐츠 이원화")를 새로운 형태로 재발시키지 않기 위해 —
    "이 응답이 git 데이터에서 온 건지 PocketBase 초안에서 온 건지"를
    매 요청마다 판단해야 하는 복잡도를 지금 단계에서 들이지 않는다.
  - 검증 안 된 정보가 (설령 낮은 확률이라도) 즉시 다른 사용자에게
    노출되는 경로를 원천 차단한다 — §5의 오염 위험과 직결.
  - 나중에 정말 필요하면("승격 전에도 반영 속도를 높이고 싶다") 별도
    설계 결정으로 다시 논의한다 — 지금 정보가 부족한 상태에서 미리
    정하지 않는다(이 프로젝트 전체가 유지해온 원칙).
- **어느 필드까지 이 메커니즘으로 고칠 수 있는지의 화이트리스트.** 지금은
  "기존 마스터데이터 스키마의 필드명 그대로만"이라고 원칙만 정했고,
  구현 시 실제로 어떤 필드까지 허용할지(예: 라우팅 키워드 자체는
  포함하지 않는다 — 그건 §4-2 리팩터링 이후에나 검토) 세부 목록은
  구현 착수 시점에 확정한다.

## 7. 구현 전 확인이 필요한 질문 (열려있는 채로 남김)

1. **정부기관 AC가 실제로 web_search 같은 도구를 갖고 있는가?** 갖고
   있다면 `source=web_search` 경로가 실제로 의미 있고, 없다면 사실상
   전부 `source=user_reported`가 되어 §5의 신뢰도 문제가 훨씬 커진다 —
   이건 이 설계의 실효성을 좌우하는 전제라 구현 착수 전 반드시 확인.
2. **승격 빈도·담당** — 사람이 직접 주기적으로 확인할지, Claude 세션에
   위임할지, 임계치(예: 같은 필드에 대해 서로 다른 출처로 3회 이상
   보고되면 우선순위 상향) 같은 자동 트리아지를 둘지.
3. **국가기관(national) 계층은 도별 인스턴스가 아니라 34개 싱글턴 +
   지사 디렉터리 구조다**(`09-national/NATIONAL-AGENCY-CLASS-INSTANCE-ARCHITECTURE_v1.0.md`
   참고 — 2026-07-24 재정정: `SP-NAT-{DOMAIN}-TEMPLATE` 자체가 전국에
   정확히 하나뿐인 인스턴스이고, `national-agency-master-data.json`의
   도별 레코드는 별개 인스턴스가 아니라 그 싱글턴이 §7 PDV_REQUEST
   흐름에서 참조하는 조회용 지사 디렉터리 항목이다). 따라서 같은
   필드(예: 콜센터번호)에 대한 초안이 여러 도의 지사 디렉터리 항목에서
   동시다발적으로 쌓일 수 있는 건 마찬가지이지만, 승격 UI/절차는
   "도별 인스턴스"가 아니라 **"지사 디렉터리 항목별"**로 나눠 보여줘야
   한다 — `instance_id` 필드에 도청/시청처럼 지역 코드를 넣는 대신,
   국가기관 계층에서는 `layer=national`일 때 `instance_id`가 지사
   디렉터리 레코드의 (도메인, 도코드) 키를 가리키는 것으로 스키마를
   맞추면 된다(구현 세부사항, 착수 시 결정 — 원칙만 여기서 정정).

## 8. 롤아웃 계획과의 관계

이 설계가 확정·구현되면, `NATIONWIDE-INSTANCE-ROLLOUT-PLAN_v1.0.md`의
§3-1~4(사전 완성 방식)는 폐기하지 않되 성격이 바뀐다 — "완성해서
제출하는 작업"에서 "표지석을 놓는 작업"으로. 즉 앞으로의 신규 인스턴스
작업(2단계 국가기관 확대 등)도 계속 진행하되, 그 산출물은 "최종본"이
아니라 "이후 이 메커니즘이 다듬어 나갈 시작점"으로 문서상 재규정한다.
롤아웃 계획 문서에도 이 사실을 반영하는 짧은 개정을 추가한다(별도 patch).
