# scenarios_jeju_70dept_requests_v1.json — 제주도청 부서별 민원/내부지시 코퍼스

## 개요
2026-09-16 세션에서 작성한 `jeju_dept_report.md`(15실·국 70과 실태 보고서)를
기반으로, 확인된 **68개 부서(과/담당관/추진단 단위)** 각각에 대해
**민원 5건 + 내부지시 5건 = 10건**을 템플릿 기반으로 생성한 코퍼스다
(총 680건). `departments.py`의 `DEPARTMENTS` 배열이 각 부서의 실제 소관업무
(보고서·division SP §CAPABILITIES에서 그대로 가져온 문구)를 담고 있고,
`generate.py`가 이를 5개 민원 템플릿·5개 내부지시 템플릿에 대입해 생성한다.

## 정확히 70이 아니라 68인 이유
`jeju_dept_report.md`에서 이름 또는 업무가 확인된 부서가 68개였다(정원상
70과와의 차이 2건은 이번 세션에서도 채우지 못한 완전 미확인 공백). 목표
개수를 채우려고 부서를 지어내지 않고, 확인된 개수 그대로 생성했다.

## 신뢰도 등급 그대로 승계
각 레코드의 `확인상태` 필드는 `jeju_dept_report.md`의 등급(①~⑤)을 그대로
가져왔다. **① 제주 확정 / ② 제주 개편 확인**만 실제 업무에 활용 가능한
신뢰도이고, **③ 통상 정의(제주 미확인) / ④ 이름만 확인**은 jeju.go.kr
원본 사무분장으로 재검증되기 전까지는 이 텍스트 자체를 실제 SP 라우팅
테스트 정답지로 쓰면 안 된다 — 어디까지나 "이런 형태의 요청이 들어올
것이다"라는 구조적 자리표시자다.

## 관할(jurisdiction) 검토 방식과 한계
각 레코드의 요청 문구는 **그 부서 자신의 소관업무 문구에서만** 생성했으므로
구조적으로 타 부서 업무가 섞여 들어갈 여지가 없다(부서 A의 텍스트에 부서
B의 고유 업무 키워드가 등장하지 않음). 다만 이것은 "생성 단계에서의 교차
오염 방지"일 뿐, `jeju_dept_report.md` §3(불일치·중복 4건 — 특히
교통항공국의 제2공항 관련 조직 3개의 실제 관계, 총무과 소속 이중성)에서
이미 지적한 **부서 정의 자체의 불확실성**은 해결하지 못한다. 이 코퍼스에서
그 4개 지점에 해당하는 부서(도로과/제2공항상생지원단/총무과 2건)의
레코드는 여전히 "재검증 필요" 상태로 표시돼 있다.
