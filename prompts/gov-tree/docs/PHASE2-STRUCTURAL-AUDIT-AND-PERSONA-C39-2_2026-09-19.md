# Phase 2 구조 감사 + 페르소나 C39-2 롤아웃 감사 — 2026-09-19

## 0. 방법론에 대한 정직한 고지 (먼저 읽을 것)

원 계획은 "330여개 SP × 10개 시나리오를 작성해 실제로 평가"였다. 실행 중
확인해보니 342개 SP(정정된 인벤토리, §1 참조) × 10건 = 3,420건을 대화
하나하나 시뮬레이션하는 것은 이번 세션 범위에서 불가능했다 — 대신
**전체 SP 파일에 대한 구조적 정합성 스캔**(존재 여부, 필수 섹션 유무,
확정 상태)으로 대체했다. 이는 ALL-SP-SCENARIO-EXPERIMENT-REPORT가 쓴
방법론과 같은 계열이며, 그 리포트가 자인했던 함정("파일 자체에 키워드가
있는지만 보고 상속 원칙을 놓친다")을 피하려고 이번엔 상속 구조(공통 SP
4개 문서, 오늘 재확인된 실제 라이브 체인)를 먼저 확정한 뒤 스캔했다.
**개별 SP가 실제 대화에서 시나리오에 어떻게 응답할지까지는 검증하지
못했다** — 이건 별도의(훨씬 큰) 실사 세션이 필요하다.

### 2-2. PARTIAL 109건 — 대부분 같은 패턴 하나
**과·팀 단위 SP 중 다수(주로 직속기관·출자출연기관·도청 일부 과)가

명시하지 않은 SP가 저장소 안에 섞여 있다 — 후자는 실제 대화에서 자기
권한 밖의 일도 스스로 처리하려 들 위험이 있다(오늘 정비한 kgov
§처리 파이프라인의 STEP B "처분권 소재" 판단과 직결되는 결함).
이건 개별 SP 100여 개를 하나씩 고치는 문제라 이번 세션에서 손대지
않고 **다음 배치 작업 후보**로 남긴다.

예외 2가지(다듬을 필요 없음, 확인만):

  심사·보완) 파일럿 구현이라 의도된 다른 구조. 결함 아님.
- `SP-ORGDIV-JTO-PLANNING`(제주관광공사 경영기획본부): 내용이 짧고 §3에서
  "세부 본부·부서명은 확인하지 못했다"고 스스로 정직하게 고지하고 있다 —
  완성도가 낮을 뿐 결함으로 볼 것은 아니다.

## 3. 페르소나(SP_common_guardrails 하위) C39-2 롤아웃 감사

**747개**라는 숫자 자체가 이미 문제였다 — 실제로는 이 폴더(`prompts/`
최상위)에 **구버전이 archive 안 되고 계속 쌓여있는 것**이 대부분이다

## 5. 관제탑 원칙(정보 안내가 아니라 목적 달성) 준수 여부 — 근본 원인 발견 및 템플릿 수정

혼디의 존재 이유(정보 안내가 아니라 사용자 목적 달성)를 기준으로 §2
"완결 처리 업무"의 실제 내용을 다시 스캔했다. §2는 "이 부서가 직접
답변(=STEP R 실행)한다"는 뜻인데, 실제 내용이 "절차·자격 요건을
안내한다"는 순수 정보 전달 문장으로만 채워진 SP가 **319개 중 112개
(35%)** 발견됐다.

동일한 문장("아래 업무는 일반적인 절차·자격·문의처 안내를 이 레이어가
직접 제공한다...")이 도청 국 단위 SP 24개와 **§2 원형 근거가 되는
템플릿 17개(SP-DEPT-*-TEMPLATE 계열 + SP-DIV-TEMPLATE)에 전부 똑같이
박혀있었다** — 즉 112건은 112개의 개별 저작 실수가 아니라, **템플릿
자체가 관제탑 원칙 위반 문장을 표준으로 정의해뒀던 것 하나의 결과**다.

### 조치
템플릿 17개(2026-09-19)의 §2 보일러플레이트를 정정 — "절차·안내"가
아니라 "이 부서가 접수·조립·제출까지 실제로 대신 처리하는 업무를
구체적으로 쓸 것, 정보 나열로 끝나면 반려 대상"으로 명시하고 kgov
§처리 파이프라인 STEP R을 직접 인용했다. **이걸로 새로 작성될 SP는
막히지만, 이미 생성된 112개 기존 SP는 그대로 남아있다** — 각 부서가
실제로 무엇을 대신 처리해줄 수 있는지는 부서별 지식이 필요해서
기계적 일괄 치환이 불가능하다. 다음 배치 작업 후보 1순위로 올린다.

카테고리별 분포: DO_BUREAUS 49(국 24+과 25) · DO_ORGS 41 · DO_AGENCIES 16
· JEJUSI_BUREAUS 5 · SEOGWIPO_BUREAUS 1.
